00Why OOP exists

Procedural code keeps data and the functions that touch it in separate places. As a program grows, nothing stops any function from corrupting any data. OOP's move is to lock the two together and expose only a safe door.

The real problem, in one example

Imagine a bank balance in procedural style — the balance is a loose variable that any code can reach:

// procedural: balance is public property of the whole program
double balance = 5000;

void withdraw(double amt) { balance -= amt; }

// ...500 lines later, in a totally unrelated file:
balance = -99999;        // nothing stops this. The bug is now invisible.

In OOP the balance lives inside the account and the only way in is a method that can refuse:

class Account {
    private double balance = 5000;      // nobody outside can touch this

    public void withdraw(double amt) {
        if (amt <= 0 || amt > balance)        // the rule lives WITH the data
            throw new IllegalArgumentException("invalid amount");
        balance -= amt;
    }

    public double getBalance() { return balance; }
}

// account.balance = -99999;  -> compile error. The bug is now impossible.
Definition

Object-oriented programming models a program as a set of objects that each hold their own state and expose behaviour, instead of as a list of procedures operating on shared data.

The payoff is not "code reuse" (that is a side effect) — it is containment: a bug in one class can only damage what that class owns.

ConcernProceduralObject-oriented
Data and logicSeparateBundled in a class
Who can change a valueAnyoneOnly the owning class
Adding a new variantEdit every if/elseAdd a subclass, change nothing

Asked

"Is Java a pure object-oriented language?" — No, and this is the expected answer. A pure OO language would have everything as an object. Java has 8 primitive types (byte short int long float double char boolean) that are not objects, it has static members that belong to a class rather than an object, and it allows standalone-looking utility classes. Smalltalk is the usual "pure" example.

01Class, object, reference — three different things

People use these words interchangeably and then get confused by ==. They are three separate things living in two different memory areas.

Definition

Class — the blueprint. A design, loaded once into Metaspace. Costs no per-object memory.

Object — one built instance of that blueprint, living on the heap. Created only by new (or reflection / deserialization / clone).

Reference — a variable on the stack that holds the address of an object. Not the object itself.

Car c1 = new Car("Swift");
Car c2 = c1;                       // copies the ADDRESS, not the car
Car c3 = new Car("Swift");   // a second, separate car

System.out.println(c1 == c2);      // true  - same object
System.out.println(c1 == c3);      // false - different objects

c2.setSpeed(80);
System.out.println(c1.getSpeed()); // 80  <- c1 and c2 ARE the same car
Trap

"I made a copy" — Car c2 = c1; does not copy the object. You now have two remotes for one TV. Changing the channel through either remote changes the same TV. To get a real copy you need a copy constructor or clone().

Declaring is not creating. Car c; creates a reference holding null. No object exists until new runs. Using it throws NullPointerException.

Asked

"How many objects are created here?"

String s1 = "hi";
String s2 = "hi";
String s3 = new String("hi");

Two. s1 and s2 share one object in the String Constant Pool (literals are interned), so s1 == s2 is true. new String() always forces a fresh heap object, so s1 == s3 is false — but s1.equals(s3) is true.

02Constructors

Definition

A constructor is a special block that runs once, immediately after the object's memory is allocated, to bring it to a valid starting state. Its name must exactly match the class name and it has no return type — not even void.

Real-world framing

A constructor is the showroom delivery checklist. A car cannot leave the showroom without an engine number and a registration — those are mandatory. Colour and music system are optional extras. That is exactly constructor overloading:

class Car {
    private final String engineNo;    // mandatory
    private final String regNo;       // mandatory
    private String colour;             // optional

    // full constructor - the single real one
    Car(String engineNo, String regNo, String colour) {
        if (engineNo == null || regNo == null)
            throw new IllegalArgumentException("cannot deliver without both");
        this.engineNo = engineNo;
        this.regNo    = regNo;
        this.colour   = colour;
    }

    // convenience constructor delegates - never duplicates the checks
    Car(String engineNo, String regNo) {
        this(engineNo, regNo, "white");   // MUST be the first statement
    }
}

The default constructor

If you write no constructor at all, the compiler inserts a no-arg one for you. The moment you write any constructor, that gift is withdrawn.

class A { }                        // compiler adds:  A() { super(); }

class B {
    B(int x) { }                   // you wrote one...
}
// new B();  -> COMPILE ERROR: no suitable constructor. Nothing is inserted now.
Under the hood
  • In bytecode a constructor is a method named <init>. A static initialiser becomes <clinit>.
  • Every constructor's first act is a call to a super constructor. If you do not write super(...) or this(...), the compiler silently inserts super(); — which is why an unbroken chain of constructors up to Object always runs.
  • The compiler-generated default constructor gets the same access modifier as the class: a public class gets a public one, a package-private class gets a package-private one.
Trap

A "constructor" with a return type is just a method. This compiles fine and is a classic trick question — void Car() is an ordinary method that happens to be named Car, and it will never run on new Car().

this(...) and super(...) must each be the first statement, and you cannot use both in one constructor — there is only one first line.

Constructors are not inherited. A subclass does not get its parent's constructors; it can only call them via super(...).

Asked

"Can a constructor be private? What is the use?" — Yes. A private constructor blocks new from outside the class, which is exactly what you want for a Singleton (section 21), a static utility class like Collections, and static factory methods such as Integer.valueOf() or a Builder.

"Can a constructor be final, static, or abstract?" — No to all three. final/abstract are meaningless because constructors are never inherited or overridden, and static contradicts the job of initialising a specific instance.

03this & super

Definition

this — a reference to the object currently executing the method. Passed invisibly to every instance method, which is why it does not exist in a static context.

super — a reference to the parent part of this same object. Not a different object: one object, two layers.

FormMeaningWhere it may appear
this.fieldDisambiguate a field from a same-named parameterAny instance method or constructor
this.method()Call another instance methodAny instance method or constructor
this(args)Call another constructor of the same classFirst line of a constructor only
super.fieldReach a parent field hidden by a same-named child fieldAny instance method

super(args)Call the parent constructorFirst line of a constructor only

The most common real use of this

class Employee {
    private String name;

    Employee(String name) {
        name = name;              // BUG: assigns the parameter to itself.
        this.name = name;         // correct: field  <-  parameter
    }
}

super.method() — extend, do not replace

Real case: a SavingsAccount wants the parent's withdrawal rules plus a minimum-balance rule. You do not copy the parent's code, you call it:

class Account {
    protected double balance;
    void withdraw(double amt) {
        if (amt > balance) throw new IllegalStateException("insufficient funds");
        balance -= amt;
    }
}

class SavingsAccount extends Account {
    private static final double MIN = 1000;

    @Override
    void withdraw(double amt) {
        if (balance - amt < MIN)
            throw new IllegalStateException("must keep " + MIN);
        super.withdraw(amt);       // reuse the parent's checks + the actual debit
    }
}
Trap

this in a static method → compile error. A static method belongs to the class and has no object, so there is nothing for this to point at. Same for super.

super.super.method() does not exist. You can reach one level up, never two. Java deliberately blocks it — skipping a level would let you bypass a parent's invariants.

04static vs instance

Definition

static members belong to the class: one copy, shared by every object, created when the class is loaded. Instance members belong to each object: a fresh copy per new.

Real-world framing

A college: every student has their own rollNo and name — instance fields. The collegeName is the same for all 3,000 students; storing it 3,000 times is pure waste — static field. And totalStudents is a property of the college, not of any one student:

class Student {
    static final String COLLEGE = "NIT Rourkela";  // one copy, ever
    static int totalStudents;                        // one counter for all

    private final int rollNo;                        // per student
    private final String name;                      // per student

    Student(int rollNo, String name) {
        this.rollNo = rollNo;
        this.name   = name;
        totalStudents++;              // shared state, bumped by every object
    }

    static int getTotal() { return totalStudents; }
}

new Student(1, "Subhranshu");
new Student(2, "Ankit");
System.out.println(Student.getTotal());   // 2   - called on the CLASS

Trap — why main is static

public static void main must be static because the JVM has to call it before any object exists. If it were an instance method, the JVM would face a chicken-and-egg problem: it would need an object of your class to run main, but your code creates that object inside main.

Asked

"Can we call a static method on a reference variable?" — Yes, it compiles (s1.getTotal()), and it is resolved at compile time using the reference's declared type, ignoring the object entirely. It even works on null:

Student s = null;
System.out.println(s.getTotal());   // 2   - NO NullPointerException!

It is legal but bad style, and IDEs warn about it. Always write Student.getTotal().

05Static control flow

"In what order does everything run?" is asked constantly, and almost everyone gets the parent/child ordering wrong. Static flow happens once per class, the first time the class is loaded — before any object exists.

Definition — the three passes

When a class is loaded, the JVM does static work in three distinct passes:

  1. Identification of all static members, top to bottom.
  2. Default value assignment — every static field is set to its zero value (0, false, null). Nothing you wrote has run yet.
  3. Original assignment — explicit initialisers and static blocks execute, in the order they appear in the source.

And crucially: the parent class is fully loaded first.

Your own file, traced

This is src/CompleteJava/OOPS/StaticControlFlow.java:

class Parent1 {
    static int x = 10;
    static { System.out.println("Parent1 static block"); }
}
class Child1 extends Parent1 {
    static int y = 20;
    static { System.out.println("Child1 static block"); }
}

public class StaticControlFlow {
    public static void main(String[] args) {
        Child1 child1 = new Child1();
    }
}
Output — and why 
Parent1 static block
Child1 static block

new Child1() forces Child1 to load. Loading Child1 requires Parent1 to be loaded first and completely, so Parent1's static block runs before Child1's. Static flow runs top-down: parent before child.

The read-before-write trick

This is the version interviewers actually use, because pass 2 and pass 3 are separate:

class Demo {
    static int i = m1();          // 3rd: runs m1() -> prints j, which is still 0
    static { System.out.println("static block, i = " + i); }
    static int j = 20;

    static int m1() {
        System.out.println("m1 sees j = " + j);   // j not assigned YET
        return 10;
    }

    public static void main(String[] a) { System.out.println("main, j = " + j); }
}
Output 
m1 sees j = 0          <- default value, pass 2 already happened
static block, i = 10
main, j = 20

Reading a static field before its original assignment gives you the default value, not a compile error. This is called read indirectly, write directly (RIWD).

Trap

Reading it directly before declaration is a compile error — "illegal forward reference":

static { System.out.println(j); }   // COMPILE ERROR
static int j = 20;

Only reading it through a method call (indirectly) is allowed — which is exactly what makes the trick question work.

Under the hood

All of pass 3 is compiled into one synthetic method called <clinit>. The JVM guarantees it runs exactly once and is thread-safe — the classloader holds a lock. That guarantee is what makes the "static holder" Singleton idiom in section 21 safe without any synchronized.

06Instance control flow

Same three passes, but per object, and triggered by new. The ordering surprise here is that the parent constructor finishes before the child's fields are initialised.

Your own file, traced

src/CompleteJava/OOPS/InstanceFlow.java — note the parent is abstract and the child is empty:

abstract class Parent {
    Parent() { System.out.println("Parent"); }
}
class Child extends Parent { }

public class InstanceFlow {
    public static void main(String[] args) {
        Child c = new Child();      // prints: Parent
    }
}
Why it prints "Parent"

Child has no constructor, so the compiler gives it Child() { super(); }. That super() runs Parent(), which prints. This proves two things people doubt: an abstract class does have a constructor, and it does run — you simply cannot call new Parent() directly.

Full ordering demo

class P {
    static { System.out.println("1 P static"); }
    { System.out.println("3 P instance block"); }
    P()  { System.out.println("4 P constructor"); }
}
class C extends P {
    static { System.out.println("2 C static"); }
    { System.out.println("5 C instance block"); }
    C()  { System.out.println("6 C constructor"); }
}
// new C(); new C();
// 1 2 3 4 5 6   then   3 4 5 6   (statics never repeat)
Trap — the partially built object

If a parent constructor calls a method the child overrides, the child's version runs before the child's fields are initialised. Everything looks null or 0:

class Parent {
    Parent() { show(); }                  // calls the CHILD's override
    void show() { }
}
class Child extends Parent {
    private String msg = "ready";
    @Override void show() { System.out.println("msg = " + msg); }
}
new Child();     // prints "msg = null"   <- NOT "ready"

Never call an overridable method from a constructor. Make such methods private, static or final, or move the work into a factory method that runs after construction.

07Encapsulation

Definition

Encapsulation = binding data and the methods that operate on it into one unit, and hiding the internal state so it can only change through code you control.

Hiding the data is called data hiding. Encapsulation without private fields is not encapsulation — it is just a class.

Real-world framing — the ATM

You never reach into the machine and move cash. You press buttons. The machine checks your PIN, checks your balance, checks the daily limit, and only then moves money. The buttons are the public methods; the cash drawer is a private field.

public class BankAccount {
    private double balance;              // the cash drawer - sealed
    private final String accountNo;
    private int failedPins;

    public BankAccount(String accountNo, double opening) {
        if (opening < 0) throw new IllegalArgumentException("negative opening");
        this.accountNo = accountNo;
        this.balance   = opening;
    }

    // read-only view: a getter with NO matching setter
    public double getBalance() { return balance; }

    // the ONLY doors in, each with its own rule
    public void deposit(double amt) {
        if (amt <= 0) throw new IllegalArgumentException("deposit must be > 0");
        balance += amt;
    }

    public void withdraw(double amt) {
        if (amt <= 0)       throw new IllegalArgumentException("invalid amount");
        if (amt > balance)  throw new IllegalStateException("insufficient funds");
        balance -= amt;
    }
}

Because balance is private with no setter, the balance can never be negative anywhere in the program. That guarantee is called an invariant, and it is the real product of encapsulation.

Trap — getters and setters are not encapsulation

This class is not encapsulated, it is a public field with extra typing:

private double balance;
public double getBalance()          { return balance; }
public void setBalance(double b)    { this.balance = b; }   // no rule at all

setBalance(-99999) still works. Encapsulation means the setter enforces something, or does not exist. Ask of every setter: "what would break if someone passed garbage here?"

Trap — leaking a mutable field

Returning a collection or array directly hands the caller your internals. They can now mutate your state behind your back:

private List<String> txns = new ArrayList<>();

public List<String> getTxns() { return txns; }                        // LEAK
// caller: account.getTxns().clear();   -> your history is gone

public List<String> getTxns() { return List.copyOf(txns); }           // safe
// or Collections.unmodifiableList(txns) for a live read-only view

Same applies in reverse: a constructor that stores a caller's list without copying lets them mutate it later. This is called a defensive copy.

Asked

"Difference between encapsulation and abstraction?" — the single most common OOP interview question. Encapsulation hides the data; abstraction hides the implementation. Encapsulation is about access (solved with private + methods). Abstraction is about design (solved with interfaces and abstract classes). Encapsulation is how you achieve one small part of abstraction.

Concretely: a car's engine internals being sealed away is encapsulation. "A car has a start() pedal and you do not care whether it is petrol, diesel or electric" is abstraction.

08Inheritance (IS-A)

Definition

Inheritance lets a class acquire the members of another class with extends, establishing an IS-A relationship. SavingsAccount extends Account asserts "a savings account is an account", and the compiler will now let you use one wherever an Account is expected.

class Vehicle {
    protected String brand;
    void start() { System.out.println(brand + " starting"); }
}

class Car extends Vehicle {
    private int doors;

    Car(String brand, int doors) {
        super();                 // implicit anyway

// v.openBoot();   -> COMPILE ERROR: Vehicle has no openBoot()
Under the hood

Every class without an explicit extends implicitly extends java.lang.Object. So every object you ever create already has toString(), equals(), hashCode(), getClass(), wait(), notify() and clone(). Object is the single root of the whole hierarchy — which is why Object o = anything; always compiles.

Trap — inheritance is the most abused feature in OOP

extends is the tightest coupling Java offers. The child depends on the parent's internals, and a change in the parent silently breaks every child. The classic broken example:

class Stack extends ArrayList<String> { ... }   // WRONG

A stack is not an array list — you have just given every caller get(5), remove(2) and add(0, x), destroying the only rule a stack has. Java's own java.util.Stack made this mistake in 1.0 and it is still there as a warning.

Use inheritance only when the child is genuinely substitutable for the parent (section 20, the L in SOLID). Otherwise use composition (section 16).

Asked

"Why does Java not support multiple inheritance of classes?" — ambiguity. If C extends A, B and both define m1(), the compiler cannot know which to run; and if both inherit a field from a common grandparent, the object would carry two copies of it. Java chose to remove the ambiguity rather than add C++'s virtual-inheritance machinery. Interfaces are allowed because (before Java 8) they carried no implementation and no state to conflict.

09Polymorphism

Definition

Polymorphism = "many forms": one name, several behaviours, chosen by type.

Compile-time (static / overloading) — the compiler picks the method from the reference type and the argument types. Decided before the program runs.

Runtime (dynamic / overriding) — the JVM picks the method from the actual object on the heap. Decided while running. Also called dynamic method dispatch.

Real-world framing — a payment gateway

Your checkout code should not care whether the user picked UPI, a card or net banking. It calls pay() on a Payment; the right implementation runs itself:

interface Payment {
    void pay(double amount);
}

class UpiPayment implements Payment {
    public void pay(double a) { System.out.println("UPI PIN -> paid " + a); }
}
class CardPayment implements Payment {
    public void pay(double a) { System.out.println("OTP -> paid " + a); }
}
class WalletPayment implements Payment {
    public void pay(double a) { System.out.println("wallet debit " + a); }
}

// checkout never mentions a single concrete class
class Checkout {
    void complete(Payment method, double amount) {
        method.pay(amount);          // runtime picks the right body
    }
}

new Checkout().complete(new UpiPayment(), 499);
new Checkout().complete(new CardPayment(), 499);

Adding NetBankingPayment tomorrow means writing one new class and changing nothing else. That is the whole point — compare it with the if/else chain it replaces:

// what polymorphism saves you from
if (type.equals("upi"))       { /* ... */ }
else if (type.equals("card"))  { /* ... */ }
else if (type.equals("wallet")){ /* ... */ }
// every new method = edit this file = risk breaking the other three
Trap — fields are NOT polymorphic

Methods dispatch on the object. Fields and static methods dispatch on the reference type. This is a favourite exam question:

class P { String name = "parent";  String who() { return "P"; } }
class C extends P { String name = "child"; String who() { return "C"; } }

P ref = new C();
System.out.println(ref.name);    // "parent"  <- FIELD: reference type wins
System.out.println(ref.who());   // "C"       <- METHOD: object wins

Fields are hidden, not overridden. Never shadow a parent field — there is no good reason to.

Asked

"Is overloading polymorphism?" — yes, compile-time polymorphism, though some purists insist only overriding counts as "true" polymorphism because only it is resolved at runtime. Say both: "overloading is compile-time, overriding is runtime; when people say polymorphism unqualified they usually mean overriding."

10Abstraction

Definition

Abstraction = exposing what a thing does while hiding how it does it. You design against a capability, not an implementation.

Real-world framing — driving

You know a car needs start(), accelerate(), brake(). You do not know or care about spark timing, fuel injection or the battery management system. Learning to drive a petrol car means you can drive an EV: the abstraction is stable even though every implementation detail changed.

In code, the win is that your class depends on an idea rather than a vendor:

// the abstraction: "something that can store a file"
interface FileStore {
    String upload(byte[] data, String name);
    byte[] download(String key);
}

class S3Store    implements FileStore { /* AWS SDK calls */ }
class LocalStore implements FileStore { /* writes to disk  */ }

class ProfileService {
    private final FileStore store;       // depends on the IDEA, not on AWS

    ProfileService(FileStore store) { this.store = store; }

    void setPhoto(byte[] img) { store.upload(img, "profile.png"); }
}

// production
new ProfileService(new S3Store());
// unit test - no network, no AWS account, runs in 2ms
new ProfileService(new LocalStore());

Notice what abstraction actually bought: testability and the freedom to switch cloud providers without touching ProfileService.

"How much abstraction do the two tools give?" — an abstract class gives partial abstraction (it can have concrete methods and state). An interface gave 100% abstraction before Java 8; since default methods arrived, it is also partial. If asked the old-fashioned way, mention that nuance — it shows you know the version history.

11Abstract classes

Definition

An abstract class is a class that cannot be instantiated, declared with abstract. It exists to be extended. It may contain abstract methods (signature, no body) which every concrete subclass must implement.

When it is the right tool

Use an abstract class when subclasses share real code and state, not just a capability. Real case: every payment method needs identical logging, fee calculation and validation — only the actual charge differs.

abstract class BasePayment {
    protected final String txnId;         // shared STATE - an interface cannot do this

    BasePayment() { this.txnId = java.util.UUID.randomUUID().toString(); }

    // the template: fixed skeleton, one hole for the subclass
    public final void process(double amount) {
        validate(amount);                  // shared
        double fee = fee(amount);           // subclass may override
        charge(amount + fee);              // subclass MUST implement
        log(amount, fee);                  // shared
    }

    protected abstract void charge(double total);   // no body: the hole

    protected double fee(double amt) { return 0; }        // sensible default

    private void validate(double a) {
        if (a <= 0) throw new IllegalArgumentException("bad amount");
    }
    private void log(double a, double f) {
        System.out.println(txnId + " amount=" + a + " fee=" + f);
    }
}

class UpiPayment extends BasePayment {
    protected void charge(double total) { System.out.println("UPI debit " + total); }
    // fee() not overridden -> UPI is free
}

class CardPayment extends BasePayment {
    protected void charge(double total) { System.out.println("card charge " + total); }
    protected double fee(double amt)   { return amt * 0.02; }   // 2% MDR
}

That shape — a final method defining the steps, with abstract holes — is the Template Method pattern, and it is the main reason abstract classes exist.

Rules worth memorising
  • An abstract class can have constructors, fields, static methods, and fully concrete methods.
  • An abstract class need not have any abstract method — marking it abstract just to block new is legal and sometimes useful.
  • A class with even one abstract method must be declared abstract.
  • A subclass that does not implement every inherited abstract method must itself be abstract.
  • abstract cannot combine with final (contradiction: extend me / do not extend me), static, or private.
Asked

"Can an abstract class have a constructor? What is the point if you cannot instantiate it?" — Yes. It runs via super() when a subclass object is created, and it initialises the inherited state (txnId above). Your own InstanceFlow.java in section 06 demonstrates it printing.

"Can you create an object of an abstract class?" — not directly, but new AbstractThing() { ... } compiles: that is an anonymous subclass, and the object is of that subclass, not of the abstract class.

12Interfaces

Definition

An interface is a pure contract: a set of method signatures a class promises to provide. It describes a capability ("can be compared", "can be closed") rather than an identity.

interface Notifier {
    int MAX_RETRY = 3;                    // public static final, whether you say it or not

    void send(String to, String msg);      // public abstract

    // default: added in Java 8 so interfaces could grow without
    // breaking the thousands of classes already implementing them
    default void sendWithRetry(String to, String msg) {
        for (int i = 1; i <= MAX_RETRY; i++) {
            try { send(to, msg); return; }
            catch (RuntimeException e) { log(i, e); }
        }
        throw new IllegalStateException("failed after " + MAX_RETRY);
    }

    private void log(int attempt, Exception e) {    // Java 9+, hidden helper
        System.out.println("attempt " + attempt + " failed: " + e.getMessage());
    }

    static Notifier noop() { return (to, msg) -> { }; }   // factory, not inherited
}

class SmsNotifier implements Notifier {
    public void send(String to, String msg) { /* call SMS gateway */ }
}
Do this — a class can implement many interfaces

This is Java's answer to multiple inheritance, and it composes cleanly because interfaces carry no state:

class CloudFile implements Readable, Writable, Closeable, Comparable<CloudFile> { }

Each interface adds one capability. Compare with extends, where you get exactly one shot.

Under the hood — the marker interface

An interface with no members at all is a marker interface — you have these in src/CompleteJava/OOPS/MarkerInterface/. It carries no methods; its whole job is to tag a type so that other code can test it with instanceof.

interface Deletable { }                // no methods - a pure tag

class Dao {
    void delete(Entity e) {
        if (!(e instanceof Deletable))
            throw new UnsupportedOperationException(e.getClass() + " is not deletable");
        // ... proceed
    }
}

JDK examples: Serializable, Cloneable, RandomAccess. Modern code usually prefers annotations for this, because an annotation can carry parameters and does not pollute the type hierarchy — which is exactly what your @important annotation in DiamondProbplem.java is doing.

Asked

"Why were default methods added in Java 8?" — backward compatibility. Java 8 needed to add stream() and forEach() to Collection. Adding an abstract method would have broken every existing implementation on earth overnight. default lets an interface ship a body, so old classes keep compiling.

"Can an interface extend another interface?" — yes, and it can extend several: interface A extends B, C { }. An interface never implements; it always extends.

"Can an interface have a constructor?" — no. There is no state to initialise and it is never instantiated.

14The diamond problem

Definition

The diamond problem is the ambiguity that appears when a class inherits the same method from two different parents. With D inheriting from both B and C, which themselves extend A, a call to d.m1() has two candidate bodies and no rule to pick one.

With classes: simply banned

// class D extends B, C { }     -> COMPILE ERROR, full stop

With interfaces: allowed, but you must disambiguate

Once Java 8 gave interfaces bodies, the diamond became possible again. Java's answer: the compiler refuses to guess and makes you say which one you meant.

interface B { default String m1() { return "B"; } }
interface C { default String m1() { return "C"; } }

class D implements B, C {
    // Without this override: "class D inherits unrelated defaults for m1()"
    @Override
    public String m1() {
        return B.super.m1();       // the ONLY place this syntax is legal
    }
}
The three resolution rules

When the same method comes from several places, Java picks in this order:

  1. Class wins. A method from a superclass beats any interface default.
  2. Most specific interface wins. If B extends A, B's default beats A's.
  3. Otherwise: you decide. Compile error until you override and pick with Interface.super.method().
Asked

"Does Java have the diamond problem?" — the right answer is nuanced: not for classes, because multiple class inheritance is banned. Potentially for interfaces since Java 8's default methods — but it is resolved at compile time by forcing an explicit override, so it never becomes a runtime surprise. Also note there is no state to duplicate, which is the half of the C++ problem Java avoids entirely.

The overriding rulebook
  • Signature identical; return type same or a subtype (covariant return).
  • Access may widen, never narrow: protected → public is fine, public → private is a compile error.
  • Checked exceptions may be narrowed or dropped, never broadened. Unchecked exceptions are unrestricted.
  • final, static and private methods cannot be overridden. Constructors cannot either.
  • Always write @Override — it turns a silent typo into a compile error.
class Parent {
    protected Object fetch() throws Exception { return null; }
}

class Child extends Parent {
    @Override
    public String fetch() throws java.io.IOException {   // all three legal:
        return "data";                                   // String IS-A Object  (covariant)
    }                                                  // public widens protected
}                                                      // IOException narrows Exception
Trap — static methods are hidden, not overridden 
class P { static String who() { return "P"; } }
class C extends P { static String who() { return "C"; } }

P ref = new C();
System.out.println(ref.who());   // "P"  <- reference type, NOT the object

This is method hiding. There is no dynamic dispatch for statics, so polymorphism does not apply. Adding @Override to C.who() would fail to compile — a useful way to prove it to yourself.

Trap — overload resolution surprises 
void f(Object o) { System.out.println("Object"); }
void f(String s) { System.out.println("String"); }

f(null);          // "String"  - the MOST SPECIFIC match wins

And the classic: the compiler prefers widening over boxing, and boxing over varargs.

void g(long x)    { System.out.println("long"); }
void g(Integer x) { System.out.println("Integer"); }

g(5);             // "long"  - widening int->long beats boxing int->Integer

16Composition (HAS-A) — and why to prefer it

Definition

Composition = a class holds a reference to another object and delegates work to it. A HAS-A relationship. A Car HAS-A Engine; a Car IS-A Vehicle.

Aggregation is the loose flavour (the part survives the whole — a Team HAS Players who exist without the team). Composition proper is the strict flavour (the part dies with the whole — an Order and its OrderLines).

The same job done both ways

Say you need a queue that also counts everything ever added — a real requirement for metrics.

// ---------- inheritance: fragile ----------
class CountingQueue<E> extends ArrayDeque<E> {
    private int added;

    @Override public boolean add(E e)                  { added++; return super.add(e); }
    @Override public boolean addAll(Collection<? extends E> c) {
        added += c.size(); return super.addAll(c);
    }
    public int getAdded() { return added; }
}
// BUG: if ArrayDeque.addAll() internally calls add(), every element is
// counted TWICE. Your correctness depends on the parent's private
// implementation details, which can change in any JDK release.
// Also: push(), offer(), offerLast() all bypass your counter entirely.

// ---------- composition: solid ----------
class CountingQueue<E> {
    private final Deque<E> inner = new ArrayDeque<>();   // HAS-A
    private int added;

    public void add(E e)      { added++; inner.add(e); }     // you control every door
    public E    poll()        { return inner.poll(); }
    public int  size()        { return inner.size(); }
    public int  getAdded()    { return added; }
}
// Cannot be broken by a JDK change. Exposes exactly the 4 methods you
// meant to expose. Can swap ArrayDeque for LinkedList in one line.
Do this — "favour composition over inheritance"

The most quoted rule in OOP (Joshua Bloch, Effective Java). Reach for extends only when all of these hold:

  • There is a genuine IS-A relationship, not just convenient code sharing.
  • The child is fully substitutable for the parent (section 20, LSP).
  • The parent was designed for extension — documented, with stable hooks.

Otherwise compose. Composition is testable (inject a fake), swappable at runtime, and does not leak the parent's API to your callers.

Asked

"Difference between IS-A and HAS-A, with an example?" — Car extends Vehicle is IS-A: a car can be used anywhere a vehicle is expected. Car holding an Engine field is HAS-A: a car is not an engine and cannot be used as one. Test it out loud — "a car is an engine" is nonsense, so it must be HAS-A.

17equals, hashCode, toString

Every class inherits these from Object, and the inherited versions are almost always wrong for your domain. Getting equals/hashCode wrong is the single most common cause of "my object vanished from the HashMap".

MethodDefault behaviour in ObjectWhat you usually want
toString()ClassName@1a2b3c — the hex hashReadable field dump for logs
equals(Object)this == other — identity onlyCompare the fields that define identity
hashCode()Derived from the memory addressDerived from the same fields as equals

Why it matters — the disappearing key

class Employee {
    private final int id;
    private final String name;
    Employee(int id, String name) { this.id = id; this.name = name; }
    // no equals, no hashCode
}

Map<Employee, String> roles = new HashMap<>();
roles.put(new Employee(1, "Subhranshu"), "Developer");

System.out.println(roles.get(new Employee(1, "Subhranshu")));   // null !

The two objects are identical in content but different in memory, so their default hash codes differ, so HashMap looks in a different bucket and finds nothing. The entry is still in the map and is now unreachable forever.

Do this — the correct implementation 
@Override
public boolean equals(Object o) {
    if (this == o) return true;                  // fast path
    if (o == null || getClass() != o.getClass()) return false;
    Employee e = (Employee) o;
    return id == e.id && Objects.equals(name, e.name);
}

@Override
public int hashCode() {
    return Objects.hash(id, name);          // SAME fields as equals
}

@Override
public String toString() {
    return "Employee{id=" + id + ", name='" + name + "'}";
}
The contract — learn these five words

equals must be: reflexive (a.equals(a)), symmetric (a.equals(b) == b.equals(a)), transitive, consistent (same answer every call), and a.equals(null) must be false.

And the link that actually bites:

  • If a.equals(b) then a.hashCode() == b.hashCode() — mandatory.
  • Equal hash codes do not imply equality — that is just a collision, and is perfectly legal.
Trap

Overriding equals but not hashCode is the classic bug — your object works with == and equals but breaks in every hash-based collection. Override both or neither.

Wrong signature. public boolean equals(Employee e) is an overload, not an override. Object.equals is still there and still doing identity comparison, and collections will call that one. Write @Override and the compiler catches it.

Mutable fields in hashCode. Put an object in a HashSet, then mutate a field that feeds its hash, and it is lost — it now hashes to a bucket it is not in. Prefer immutable identity fields.

Under the hood — record does all of this for you

Since Java 16, a record generates a correct equals, hashCode, toString, private final fields and an all-args constructor:

record Employee(int id, String name) { }   // that is the whole class

Records are implicitly final and immutable. Use them for plain data carriers — DTOs, map keys, return tuples. Mention this in interviews; it signals you follow modern Java.

Trap — final does not mean immutable 
final List<String> list = new ArrayList<>();
list.add("hello");        // LEGAL - the object is mutable
// list = new ArrayList<>();  // illegal - the reference is final

final freezes the arrow, not the box. This distinction is asked constantly.

Building a genuinely immutable class

Five requirements — miss any one and it leaks:

public final class Money {                       // 1. final class: no subclass
    private final String currency;                // 2. private final fields
    private final List<String> tags;

    public Money(String currency, List<String> tags) {
        this.currency = currency;
        this.tags = List.copyOf(tags);             // 3. defensive copy IN
    }

    public String getCurrency() { return currency; }

    public List<String> getTags() {
        return tags;                              // 4. already unmodifiable; else copy OUT
    }
                                                   // 5. NO setters at all
    // "changing" it returns a new object
    public Money withCurrency(String c) { return new Money(c, tags); }
}
Why bother
  • Automatically thread-safe — no state changes, so no race is possible. No locks needed.
  • Safe as a map key — its hash can never change (section 17).
  • Free to share and cache — no defensive copying by callers.
  • Easier to reason about: the value you were handed is the value you keep.

This is exactly why String is immutable, and why String is safe to use as a HashMap key everywhere.

Asked

"Why is String immutable in Java?" — four reasons, give them in order: (1) the String Constant Pool can only share one object between many references if nobody can change it; (2) security — a file path or SQL string validated and then mutated would defeat the check; (3) its hashcode is cached, which makes it a fast, reliable map key; (4) thread safety for free.

Do this

Start every field private and every class package-private. Widen only when something outside genuinely needs it. The narrowest thing that works is always the right default — you can always loosen later, but you can never tighten a public API without breaking callers.

Trap — protected is subtler than it looks

From a different package, a subclass can only touch a protected member through a reference of its own type (or a subtype), not through the parent's:

// package b;  class Child extends a.Parent {
void test(a.Parent p, Child c) {
    c.protectedField = 1;   // OK   - own type
    p.protectedField = 1;   // COMPILE ERROR - parent reference, other package
}

Also: a class can only be public or package-private. private class Foo at top level is illegal (nested classes are a different story).

Asked

"Can we reduce visibility when overriding?" — no. Overriding may only widen access. Narrowing would break substitutability: a caller holding a parent reference expects the method to be callable.

20SOLID principles

Five design rules that turn "I know the syntax" into "I can design a class". Interviewers for 2–5 year roles ask for these with an example, so learn one concrete example each.

S — Single Responsibility

A class should have one reason to change. The classic violation bundles unrelated jobs:

// BAD: three reasons to change - business rules, DB schema, email template
class Employee {
    void calculatePay()  { }
    void saveToDatabase(){ }
    void sendPayslipMail(){ }
}

// GOOD
class Employee          { /* data + rules only */ }
class PayCalculator     { double calculate(Employee e) { return 0; } }
class EmployeeRepository{ void save(Employee e) { } }
class PayslipMailer     { void send(Employee e) { } }

O — Open/Closed

Open for extension, closed for modification. You should add behaviour by adding code, not by editing working code. Section 09's payment example is exactly this: a new payment method never touches Checkout.

L — Liskov Substitution

Anywhere a parent works, a child must work without the caller noticing. The famous violation:

class Rectangle {
    protected int w, h;
    void setWidth(int w)  { this.w = w; }
    void setHeight(int h) { this.h = h; }
    int area() { return w * h; }
}

class Square extends Rectangle {          // "a square IS-A rectangle"... in maths
    void setWidth(int w)  { this.w = this.h = w; }
    void setHeight(int h) { this.w = this.h = h; }
}

void test(Rectangle r) {
    r.setWidth(5); r.setHeight(4);
    assert r.area() == 20;      // passes for Rectangle, FAILS (16) for Square
}

The lesson: IS-A in English is not IS-A in code. Substitutability is about behaviour, not vocabulary.

I — Interface Segregation

No client should be forced to depend on methods it does not use. Many small interfaces beat one fat one:

// BAD: a scanner is forced to implement fax() and print()
interface Machine { void print(); void scan(); void fax(); }

// GOOD
interface Printer { void print(); }
interface Scanner { void scan(); }
interface Fax     { void fax(); }
class SimpleScanner implements Scanner { public void scan() { } }

D — Dependency Inversion

Depend on abstractions, not concretions. High-level policy should not import low-level detail:

// BAD: OrderService is welded to MySQL forever
class OrderService {
    private final MySqlOrderRepo repo = new MySqlOrderRepo();
}

// GOOD: depends on an interface, gets the implementation from outside
class OrderService {
    private final OrderRepo repo;
    OrderService(OrderRepo repo) { this.repo = repo; }   // constructor injection
}

This is literally what Spring's @Autowired automates — a good thing to say out loud, since it connects OOP theory to the framework you will actually use.

Asked

"Which SOLID principle do you use most?" — a good honest answer is S and D: single responsibility keeps classes small enough to test, and dependency inversion is what makes unit testing possible at all (you inject a fake repository instead of hitting a real database). Tie it to testing and it sounds like experience rather than recital.

21Patterns you must know

Singleton — exactly one instance

Real use: a configuration holder, a logger, a connection pool. Your SingletonClass.java uses the synchronized method version:

// your version - correct, but locks on EVERY call, even after creation
class Test {
    private static Test test;
    private Test() { }
    public synchronized static Test getInstance() {
        return test == null ? test = new Test() : test;
    }
}
Do this — the two versions worth memorising

1. Static holder (best for most cases). Lazy, thread-safe, zero synchronization — it leans on the JVM's guarantee that <clinit> runs once (section 05):

class Config {
    private Config() { }
    private static class Holder {                 // loaded only on first use
        static final Config INSTANCE = new Config();
    }
    public static Config getInstance() { return Holder.INSTANCE; }
}

2. Enum singleton (Bloch's recommendation). Immune to reflection and serialization attacks, which the others are not:

enum Config {
    INSTANCE;
    public void load() { }
}
Trap — the broken double-checked lock

Without volatile, another thread can see a partially constructed object, because the assignment can be reordered before the constructor finishes:

private static volatile Config instance;      // volatile is MANDATORY

public static Config getInstance() {
    if (instance == null) {                     // 1st check: no lock, fast
        synchronized (Config.class) {
            if (instance == null)                // 2nd check: under lock
                instance = new Config();
        }
    }
    return instance;
}

Drop the volatile and this is a real, famous bug. See section 09 of your MultiThreading notes for why.

Factory — hide which class you get

class PaymentFactory {
    static Payment of(String type) {
        return switch (type) {
            case "upi"    -> new UpiPayment();
            case "card"   -> new CardPayment();
            case "wallet" -> new WalletPayment();
            default       -> throw new IllegalArgumentException(type);
        };
    }
}
// caller says WHAT it wants, never HOW to build it
Payment p = PaymentFactory.of("upi");

Builder — many optional fields, readably

The cure for a constructor with eight parameters you can never remember the order of:

Pizza p = new Pizza.Builder("medium")
        .cheese(true)
        .olives(true)
        .jalapeno(false)
        .build();

Strategy — swap an algorithm at runtime

interface SortStrategy { void sort(int[] a); }

class Sorter {
    private SortStrategy strategy;                        // HAS-A
    void setStrategy(SortStrategy s) { strategy = s; }     // change mid-flight
    void sort(int[] a) { strategy.sort(a); }
}
// small array -> insertion sort; huge array -> quicksort. Same caller.

Note that Strategy is just composition + polymorphism. Most patterns are; that is why sections 09 and 16 matter more than memorising pattern names.

22Traps & gotchas

The ten that actually appear in interviews
  1. Fields are not polymorphic. ref.name uses the reference type; ref.method() uses the object. (§09)
  2. Static methods are hidden, not overridden. No dynamic dispatch. (§15)
  3. Calling an overridable method from a constructor sees uninitialised child fields. (§06)
  4. final ≠ immutable. A final reference to an ArrayList is still mutable. (§18)
  5. equals without hashCode breaks every hash collection. (§17)
  6. Writing any constructor removes the free no-arg one. (§02)
  7. void Car() is a method, not a constructor. It never runs on new. (§02)
  8. Overload resolution prefers widening over boxing, and f(null) picks the most specific type. (§15)
  9. Static fields read before assignment give the default value, not an error. (§05)
  10. Returning a mutable field hands away control of your own state. (§07)
Asked — predict the output

A compact question that tests four things at once:

class A {
    static { System.out.print("1 "); }
    { System.out.print("2 "); }
    A() { System.out.print("3 "); m(); }
    void m() { System.out.print("A.m "); }
}
class B extends A {
    static { System.out.print("4 "); }
    private String s = "set";
    { System.out.print("5 "); }
    B() { System.out.print("6 "); }
    @Override void m() { System.out.print("B.m(s=" + s + ") "); }
}
// new B();

Answer: 1 4 2 3 B.m(s=null) 5 6

Read it as: parent static, child static (once, parent first) → parent instance block, parent constructor → the constructor calls m(), which dispatches to B's override while s is still null → then child instance block, then child constructor. Trap 3 in one line of output.

23Question bank

Answer these out loud before reading the answer. If you cannot say it in two sentences, you do not know it yet.

What are the four pillars of OOP?

Encapsulation (bind and hide data), Inheritance (reuse via IS-A), Polymorphism (one name, many behaviours), Abstraction (expose what, hide how). Some add "message passing" as a fifth.

Difference between encapsulation and abstraction?

Encapsulation hides data using private plus rule-enforcing methods — an implementation concern. Abstraction hides implementation using interfaces and abstract classes — a design concern.

Is Java purely object-oriented?

No. It has 8 primitives that are not objects, plus static members that belong to a class rather than an instance.

Why no multiple inheritance of classes?

The diamond problem: duplicated state and ambiguous method resolution. Interfaces are permitted because they carry no instance state; since Java 8 the method ambiguity is possible but must be resolved explicitly with Interface.super.method().

Abstract class vs interface — when do you pick which?

Interface for a capability shared by unrelated types; abstract class when related types share real code and state. Professionally, often both: interface for the contract, abstract class for a skeleton implementation (List / AbstractList / ArrayList).

Can an abstract class have a constructor?

Yes. It runs through super() when a subclass is instantiated, initialising inherited state. It just cannot be called with new directly.

Can an abstract class have zero abstract methods?

Yes — perfectly legal, and a valid way to prevent instantiation while still providing shared behaviour.

Overloading vs overriding in one line each?

Overloading: same name, different parameters, same class, resolved at compile time. Overriding: same signature, subclass, resolved at runtime by the actual object.

Can we override a static method?

No. Redeclaring it in a subclass is method hiding; resolution uses the reference type, so P ref = new C(); ref.who(); calls P's version. Adding @Override would not compile.

Can we override a private or final method?

No. A private method is not visible to the subclass (redeclaring it creates an unrelated new method), and final explicitly forbids it.

Can a constructor be private? Why would you?

Yes — for Singletons, static utility classes, and static factory methods like Integer.valueOf() or a Builder.

What is covariant return type?

An override may return a subtype of the parent's return type. Object fetch() can be overridden as String fetch(). Allowed since Java 5.

Rules about exceptions when overriding?

Checked: may throw the same, a subclass of it, or fewer — never a broader checked exception. Unchecked: no restriction at all.

Difference between == and equals()?

== compares references (same object?) for objects and values for primitives. equals() compares content — but only if the class overrides it; Object.equals just does ==.

What breaks if I override equals but not hashCode?

Hash-based collections. Two equal objects can produce different hash codes, land in different buckets, and the entry becomes unreachable — map.get(equalKey) returns null.

Can two unequal objects have the same hashCode?

Yes — that is a legal collision. The contract only runs one way: equal objects must have equal hash codes.

Why is String immutable?

String pool sharing, security (a validated path cannot be mutated afterwards), cached hashcode for fast map keys, and free thread safety.

Does final make an object immutable?

No. It prevents reassignment of the reference. final List can still be added to. Immutability requires no setters, private final fields, defensive copies and ideally a final class.

Why must main be static?

So the JVM can invoke it without first creating an object — otherwise you would need an instance of the class before the code that creates instances has run.

Order of execution: static blocks, instance blocks, constructors?

Parent static → child static (once per class, on load), then per object: parent instance block → parent constructor → child instance block → child constructor.

What is a marker interface? Give JDK examples.

An interface with no members, used purely to tag a type for instanceof checks. Serializable, Cloneable, RandomAccess. Annotations are the modern alternative.

Why were default methods added in Java 8?

Backward compatibility — to add stream() and forEach() to Collection without breaking every existing implementation.

Can an interface have a static method? Is it inherited?

Yes since Java 8, and no — interface static methods are not inherited by implementing classes. Call them as MyInterface.method().

IS-A vs HAS-A?

IS-A is inheritance (Car extends Vehicle) — the child is substitutable for the parent. HAS-A is composition (Car holds an Engine) — delegation, not substitution.

Why favour composition over inheritance?

extends is the tightest coupling in Java: the child depends on the parent's internals, inherits its whole API, and breaks when the parent changes. Composition exposes only what you choose, is swappable at runtime, and is testable with fakes.

What is the Liskov Substitution Principle, with a violation?

A subtype must be usable anywhere the supertype is, without surprising the caller. Square extends Rectangle violates it: setting width then height gives an unexpected area.

What is dynamic method dispatch?

The JVM choosing an overridden method's body at runtime based on the actual object, not the reference type. The mechanism behind runtime polymorphism.

What does instanceof do, and what is pattern matching?

instanceof tests whether an object is of a given type. Since Java 16 it also binds a variable: if (o instanceof String s) { s.length(); } — no separate cast needed.

Upcasting vs downcasting?

Upcasting (child → parent) is implicit and always safe. Downcasting (parent → child) needs an explicit cast and can throw ClassCastException — guard it with instanceof.

Can you instantiate an abstract class?

Not directly, but new Abstract() { ... } works — that creates an anonymous subclass, and the object belongs to that subclass.

What is a record and when would you use it?

A Java 16+ immutable data carrier that auto-generates the constructor, accessors, equals, hashCode and toString. Use for DTOs, map keys and return tuples. Implicitly final.

Difference between aggregation and composition?

Both are HAS-A. Aggregation is weak — the part outlives the whole (Team and Player). Composition is strong — the part dies with the whole (Order and OrderLine).

What happens if a subclass does not implement all abstract methods?

The subclass must itself be declared abstract, otherwise it is a compile error.

Can an interface extend a class?

No. An interface can only extend other interfaces (one or many). A class implements interfaces and extends at most one class.

Why is the double-checked locking Singleton broken without volatile?

Without volatile, instruction reordering lets the reference become visible before the constructor has finished, so another thread can obtain a partially constructed object.

What is the best way to write a Singleton?

An enum with a single constant — thread-safe, serialization-safe and reflection-proof. Otherwise the static holder idiom, which is lazy and lock-free.

What is method chaining and how does it work?

Each method returns this (or a builder), so calls can be strung together: obj.a().b().c(). The basis of the Builder pattern and of StringBuilder.

Can we declare a class static?

Only a nested class. A static nested class needs no outer instance; a non-static inner class holds an implicit reference to its outer object (a common memory-leak source).

What is the object class hierarchy root, and what do you get free?

java.lang.Object. Every object gets toString, equals, hashCode, getClass, clone, finalize, wait, notify, notifyAll.

Shallow copy vs deep copy?

Shallow copies the fields, so reference fields still point at the same nested objects (what Object.clone() does). Deep copy recursively copies the nested objects too, giving full independence.

25Last-night cheat sheet

One-liners

  • Class blueprint · object heap instance · reference stack variable holding an address.
  • Encapsulation hides data · abstraction hides implementation.
  • Overloading = compile time, parameters differ · overriding = runtime, signature identical.
  • Methods dispatch on the object · fields and statics dispatch on the reference type.
  • Static flow once per class, parent first · instance flow every new, parent first.
  • Interface = CAN-DO capability · abstract class = IS-A with shared state.
  • final freezes the arrow, not the box.
  • equals without hashCode = objects lost in hash collections.
  • extends is the tightest coupling in Java — default to composition.

Say this if you blank out

Asked — "tell me about OOP"

"OOP models a program as objects that own their state and expose behaviour. The point is containment — a bug in one class can only damage what that class owns. The four pillars are encapsulation, inheritance, polymorphism and abstraction, and in practice the two I lean on most are polymorphism, to add behaviour without editing working code, and composition over inheritance, to keep classes loosely coupled and testable."

That answer is short, correct, and mentions design judgement rather than definitions — which is what a 2–5 year interview is actually probing.
