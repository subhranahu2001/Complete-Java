00Why threads exist

A program that does one thing at a time wastes the CPU every time it waits — for a disk read, a database, an HTTP call. Threads let the CPU do something else during that wait.

Definition

Process — an independent program in execution. It owns its own memory space (heap, code, data). Two processes cannot touch each other's memory directly; they talk through IPC (sockets, pipes, files).

Thread — the smallest unit the CPU schedules. A thread lives inside a process and shares the process's heap, static area and open files with all sibling threads, but has its own stack.

PointProcessThread
MemorySeparate address spaceShares heap, own stack
Creation costHeavy (MBs, OS fork)Light (~1 MB stack)
Context switchExpensive (TLB / page table flush)Cheap (same address space)
CommunicationIPC — slow, explicitShared variables — fast
Crash blast radiusOne process dies, others liveUncaught error can kill the JVM

Concurrency vs Parallelism

Concurrency = dealing with many tasks at once (they make progress by interleaving — possible on 1 core). Parallelism = doing many tasks at the same instant (needs ≥ 2 cores).

Concurrency is a structure, parallelism is an execution. Every parallel program is concurrent; not every concurrent program is parallel.

Asked

"Does multithreading always make the program faster?" — No. For I/O-bound work yes, hugely (threads wait, not the CPU). For CPU-bound work, more threads than cores only adds context-switch overhead. A single-core CPU-bound task gets slower with 10 threads.

Rule of thumb for pool size: CPU-bound → N cores + 1. I/O-bound → N × (1 + waitTime/serviceTime).

01What memory a thread gets

This is the question people fumble. The JVM runtime data areas split into two groups: shared by all threads and private per thread.

Under the hood
  • The Thread object is just an ordinary object on the heap. The actual OS thread and its stack are created only when you call start().
  • Stack size is fixed at thread creation: -Xss512k. Deep recursion → StackOverflowError (per thread). Too many threads → OutOfMemoryError: unable to create new native thread.
  • Local primitives live on the stack. Local reference variables live on the stack, but the object they point to lives on the shared heap.
  • Escape analysis: if the JIT proves an object never escapes a method, it can scalar-replace it and keep it on the stack. That is an optimisation, not a rule you can rely on.
Asked

"Are local variables thread-safe?" — Yes, each thread has its own stack, so each gets its own copy. But if a local reference points to a shared object, the object is still unsafe. Thread-safety belongs to the object, not the variable.

02Birth of a thread: new → start() → scheduler → run()

Trace exactly what happens when you write two lines of code. This sequence is the answer to "how is a thread registered with the thread scheduler?"

The same thing in code terms

// 1. object created on the heap. No OS thread yet. state = NEW
Thread t = new Thread(() -> System.out.println("hi"), "worker-1");

System.out.println(t.getState());   // NEW

// 2. start() does three things and returns IMMEDIATELY:
//      a) checks threadStatus != 0 -> else IllegalThreadStateException
//      b) adds the thread to its ThreadGroup
//      c) calls the native start0() -> OS creates the thread + stack
//         and puts it in the scheduler's ready queue
t.start();
System.out.println(t.getState());   // RUNNABLE (ready OR running - Java cannot tell)

t.join();                           // caller waits for t to die
System.out.println(t.getState());   // TERMINATED
Under the hood — Thread.start() source, simplified 
public synchronized void start() {
    if (threadStatus != 0)
        throw new IllegalThreadStateException();  // already started
    group.add(this);
    start0();                                    // NATIVE: real thread is born here
}

public void run() {
    if (target != null) target.run();            // target = the Runnable you passed
}

That target field is the whole reason both "extend Thread" and "implement Runnable" work: overriding run() replaces the method, passing a Runnable fills the field.

Trap

start() vs run() is the single most common trick question. t.run() compiles, runs, prints — and creates zero threads. The output appears on main. Only start() reaches the native code that creates an OS thread.

start() twice → IllegalThreadStateException, even after the thread finished. A Thread object is single-use. A Runnable object is reusable.

03The thread scheduler

Definition

The thread scheduler is part of the OS, not the JVM. Java threads are mapped 1:1 onto native OS threads (on HotSpot). The JVM hands your thread to the OS; the OS decides who runs, when, and for how long.

  • Preemptive — a higher-priority ready thread can take the CPU from a lower-priority running one.
  • Time slicing (round robin) — each thread gets a quantum; when it expires the thread goes back to the ready queue.
  • A thread also leaves the CPU voluntarily by sleep(), wait(), blocking I/O, or lock contention.
Trap — scheduling is not guaranteed

Thread scheduling is platform dependent. Never write logic that depends on the order threads run in, or on a sleep() being long enough. That is the root cause of "works on my machine" concurrency bugs.

  • setPriority(1..10) is only a hint; many OSes largely ignore it. Never build correctness on priority.
  • Thread.yield() is a hint to give up the current slice. The scheduler may ignore it and reschedule the same thread.
  • Output interleaving differs on every run. That is normal, not a bug in your code.
Asked

"Is RUNNABLE the same as running?" — No. Java's RUNNABLE merges two OS states: ready in the queue and actually executing on a core. The JVM cannot distinguish them, so there is no RUNNING enum constant. A thread blocked in native I/O also shows as RUNNABLE.

04Every way to create a thread

Asked — answer it this way

"There are only two real mechanisms: extend Thread and override run(), or pass a Runnable target to a Thread. Everything else — lambda, Callable, executor, CompletableFuture, ForkJoin, virtual threads — is a convenience layer built on those two." That answer scores far higher than reciting five items.

1 — extend Thread

class Worker extends Thread {
    Worker(String name) { super(name); }
    @Override public void run() {
        System.out.println(getName() + " running");
    }
}
new Worker("w-1").start();

Downside: Java has single inheritance — your class can now never extend anything else, and you have fused "what to do" with "who runs it".

2 — implement Runnable preferred

class Task implements Runnable {
    @Override public void run() {
        System.out.println(Thread.currentThread().getName() + " running");
    }
}
Runnable task = new Task();
new Thread(task, "w-1").start();
new Thread(task, "w-2").start();   // same task, two workers

Why better: class stays free to extend something; task is separated from worker; the same object can go to a Thread, an executor, or CompletableFuture.

Limit: run() returns void and cannot throw a checked exception → no result, no error propagation. That is exactly why Callable exists.

3 — anonymous class / lambda

// anonymous Thread subclass (mechanism 1)
new Thread() { public void run() { System.out.println("a"); } }.start();

// anonymous Runnable (mechanism 2)
new Thread(new Runnable() { public void run() { System.out.println("b"); } }).start();

// lambda - Runnable is a @FunctionalInterface
new Thread(() -> System.out.println("c"), "lambda-thread").start();

// method reference
new Thread(MyClass::work).start();

4 — Callable + FutureTask returns a value

Callable<Integer> job = () -> {          // V call() throws Exception
    int s = 0;
    for (int i = 1; i <= 100; i++) s += i;
    return s;
};

FutureTask<Integer> ft = new FutureTask<>(job);
new Thread(ft).start();                 // FutureTask IS-A Runnable
System.out.println(ft.get());           // BLOCKS until the result is ready
Why FutureTask works

FutureTask<V> implements RunnableFuture<V> and RunnableFuture<V> extends Runnable, Future<V>. So one object is both the thing a Thread can run and the handle you call get() on. It is the bridge between the Runnable-only Thread constructor and the result-bearing Callable.

5 — ExecutorService use this in production

ExecutorService pool = Executors.newFixedThreadPool(4);

pool.execute(() -> work());                    // fire and forget
Future<String> f = pool.submit(() -> "done");  // with a result
System.out.println(f.get());

pool.shutdown();                               // MANDATORY
if (!pool.awaitTermination(5, TimeUnit.SECONDS)) pool.shutdownNow();

Why: threads are reused, work is queued, concurrency is bounded, and you get naming, monitoring and lifecycle for free. new Thread() per request is how you get OutOfMemoryError: unable to create new native thread.

6 — ThreadFactory (controls how pool threads are built)

ThreadFactory factory = r -> {
    Thread t = new Thread(r, "payment-" + counter.getAndIncrement());
    t.setDaemon(false);
    t.setUncaughtExceptionHandler((th, ex) -> log.error(th.getName(), ex));
    return t;
};
ExecutorService pool = Executors.newFixedThreadPool(4, factory);

Named threads make thread dumps and production logs readable. Always do this in real code.

7 — CompletableFuture, ForkJoinPool, Timer

CompletableFuture.supplyAsync(() -> fetch())   // runs on ForkJoinPool.commonPool()
        .thenApply(String::toUpperCase)
        .thenAccept(System.out::println);

ForkJoinPool.commonPool().invoke(new MyRecursiveTask(arr, 0, arr.length));

new Timer(true).schedule(new TimerTask(){ public void run(){ ping(); } }, 1000);
// Timer is legacy: single thread, one thrown exception kills all future tasks.
// Use ScheduledExecutorService instead.

Asked — sleep() vs wait()
  • sleep() is static, on Thread; wait() is an instance method on Object.
  • sleep() does NOT release the lock. wait() releases the monitor so another thread can enter and eventually notify.
  • sleep() can be called anywhere; wait() must be called inside synchronized on the same object, else IllegalMonitorStateException.
  • sleep() wakes on time; wait() wakes on notify() (or timeout, or a spurious wakeup).

06Thread class API worth knowing

join() — wait for another thread to die

Thread t = new Thread(job);
t.start();
t.join();            // CALLER blocks until t is TERMINATED
t.join(500);        // or until 500 ms pass, whichever is first
// internally: while (isAlive()) wait(0);  -- that is why it needs no notify

Use it for: "start N threads, then continue only after all finish" — loop start() over all of them first, then loop join(). Starting and joining in the same loop makes the program fully sequential — a classic interview trap.

Daemon threads

Thread t = new Thread(job);
t.setDaemon(true);    // MUST be called before start(), else IllegalThreadStateException
t.start();
  • The JVM exits when the last non-daemon (user) thread finishes. Daemon threads are then killed abruptly — finally blocks may not run.
  • Good for background housekeeping: GC, JIT compiler, monitoring, heartbeat. Never for work that must complete (writing a file, flushing a DB).
  • Daemon status is inherited from the creating thread. main is a user thread; executor threads are user threads by default.

Stopping a thread — interruption

stop(), suspend(), resume() are deprecated and unsafe: stop() kills a thread mid-update leaving objects in a broken state and releases all its locks; suspend() holds the lock while suspended → deadlock. The only safe way is cooperative interruption.

// interruption is a FLAG, not a kill switch. The task must cooperate.
while (!Thread.currentThread().isInterrupted()) {
    try {
        doChunkOfWork();
        Thread.sleep(100);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();   // RESTORE the flag
        break;                               // then exit cleanly
    }
}
Trap — why "restore the flag"?

When sleep()/wait()/join() throw InterruptedException, the JVM clears the interrupt flag. If you catch it and do nothing, the interruption is silently swallowed and outer code (an executor's shutdownNow(), for example) never learns it should stop. Either rethrow, or call Thread.currentThread().interrupt().

isInterrupted() — instance method, does not clear the flag. Thread.interrupted() — static, clears the flag. Knowing that difference is a standard question.

07Race conditions — the three real problems

Every concurrency bug is one of three things. Naming all three is what separates a memorised answer from an understood one.

The three problems
  1. Atomicity — an operation that looks like one step is many. count++ is read → add → write; two threads can both read 5 and both write 6. One increment is lost.
  2. Visibility — a thread caches a field in a CPU register / core cache. Another thread's write may never become visible. Loops on a non-volatile boolean running can spin forever.
  3. Ordering — the compiler, JIT and CPU are allowed to reorder instructions as long as the result is unchanged for a single thread. Another thread can observe the reordering.
class Counter {
    private int count = 0;
    public void increment() { count++; }   // NOT atomic: 3 bytecodes
}
// 1000 threads x 1000 increments  →  expected 1_000_000
//                                    actual   997_431 (varies every run)
Under the hood — why count++ loses updates 
getfield  count     // T1 reads 5        T2 reads 5
iconst_1
iadd                // T1 computes 6     T2 computes 6
putfield  count     // T1 writes 6       T2 writes 6  ← one increment vanished

A critical section is any code that touches shared mutable state. It must be executed by one thread at a time, and its effects must be made visible to the next thread. synchronized and Lock give you both; volatile gives only visibility + ordering.

Do this

The cheapest fix is to have no shared mutable state at all:

  • Make it immutable — final fields, no setters. Immutable objects are automatically thread-safe.
  • Make it local — stack-confined data needs no synchronization.
  • Give each thread its own copy — ThreadLocal.
  • Only if none of those work: synchronize, or use an atomic / concurrent class.

08synchronized & the monitor lock

Definition

Every Java object has an invisible monitor (intrinsic lock) in its header. synchronized acquires that monitor on entry and releases it on exit — including when an exception is thrown. It provides mutual exclusion (atomicity) and a happens-before edge (visibility).

The four forms

// 1. synchronized instance method  → locks on 'this'
public synchronized void inc() { count++; }

// 2. synchronized block on this    → same lock, smaller critical section
public void inc() {
    doExpensiveUnsharedWork();          // not locked - good
    synchronized (this) { count++; }
}

// 3. synchronized static method    → locks on Counter.class (ONE per class)
public static synchronized void incStatic() { staticCount++; }

// 4. block on a private lock object → BEST: nobody outside can grab your lock
private final Object lock = new Object();
public void inc() { synchronized (lock) { count++; } }
Trap — instance lock vs class lock

A synchronized instance method and a synchronized static method of the same class use two different locks (this vs Counter.class), so two threads can run them at the same time. If both touch the same static field, you still have a race.

Similarly, two different instances each have their own monitor — synchronized instance methods do not protect static state.

Reentrancy

public synchronized void outer() { inner(); }   // acquires lock, hold count = 1
public synchronized void inner() { ... }        // same thread re-enters, count = 2
// released only when the count drops back to 0

Java locks are reentrant — a thread that already holds a lock can acquire it again. Without this, any call from one synchronized method to another would self-deadlock.

Trap — never lock on these
  • String literals — interned and shared across the whole JVM; unrelated code can lock the same object.
  • Boxed primitives (Integer, Long) — the cache from −128 to 127 makes them shared too.
  • A non-final field — reassigning it mid-flight means two threads lock different objects.
  • The object you expose publicly — any caller can lock it and stall you.

Always: private final Object lock = new Object();

Asked

"Can two threads run two different synchronized methods of the same object simultaneously?" — No. Both need the same monitor (this). One instance method + one static method → yes, different locks.

"Is the lock released if the method throws?" — Yes, monitorexit runs on the exception path too. With a manual Lock, you must write finally { lock.unlock(); } yourself.

"Can a constructor be synchronized?" — No. Only one thread can construct an object anyway.

09volatile & the Java Memory Model

Definition

volatile guarantees visibility and ordering, not atomicity.

  • Every read comes from main memory; every write goes straight to main memory. No caching in registers / core cache.
  • A memory barrier is inserted: the compiler and CPU may not reorder across it.
  • It creates a happens-before edge: everything a thread did before writing a volatile is visible to any thread that later reads it.
class Worker implements Runnable {
    private volatile boolean running = true;   // remove 'volatile' → may loop forever

    public void run() { while (running) { work(); } }
    public void stop()  { running = false; }         // seen immediately by the worker
}
Trap — volatile does NOT make count++ safe 
volatile int count;
count++;    // still read-modify-write → still loses updates

Use volatile only for a flag or a reference that is written by one thread and read by many. For counters use AtomicInteger; for compound state use a lock.

happens-before — the rules to name

  1. Program order — within one thread, statements happen in order.
  2. Monitor — unlock happens-before every later lock of the same monitor.
  3. Volatile — a write happens-before every later read of that field.
  4. Thread start — everything before t.start() is visible inside t.
  5. Thread join — everything t did is visible after t.join() returns.
  6. Final fields — correctly constructed final fields are visible without synchronization.
  7. Transitivity — if A hb B and B hb C, then A hb C.
Asked — double-checked locking 
class Singleton {
    private static volatile Singleton instance;   // volatile is MANDATORY

    static Singleton get() {
        if (instance == null) {                    // 1st check, no lock
            synchronized (Singleton.class) {
                if (instance == null)              // 2nd check, with lock
                    instance = new Singleton();
            }
        }
        return instance;
    }
}

Why volatile? new Singleton() is three steps: allocate, run the constructor, assign the reference. The JIT may reorder 2 and 3. Another thread could then see a non-null reference to a half-constructed object. volatile forbids that reordering.

Better answer: use a static final holder class (lazy + safe by classloading) or an enum singleton (also serialization- and reflection-safe).

10Inter-thread communication: wait / notify

These three methods live on Object, not Thread — because the lock they coordinate on belongs to an object.

MethodEffect
wait()Release the monitor, go to WAITING, join this object's wait set
notify()Wake one arbitrary waiting thread (you cannot choose which)
notifyAll()Wake all waiting threads; they then compete for the lock
Do this — the canonical pattern 
synchronized (lock) {
    while (!conditionHolds()) {    // WHILE, never IF
        lock.wait();
    }
    consumeTheState();
    lock.notifyAll();
}

Why while and not if? Two reasons: spurious wakeups are permitted by the JVM spec, and with notifyAll() several threads wake but only one wins the lock — by the time the others get in, the condition may be false again. Using if is a guaranteed follow-up question.

Producer – Consumer (bounded buffer)

class Buffer {
    private final Queue<Integer> q = new LinkedList<>();
    private final int CAPACITY = 5;

    public synchronized void produce(int item) throws InterruptedException {
        while (q.size() == CAPACITY) wait();      // buffer full → wait
        q.add(item);
        System.out.println("produced " + item);
        notifyAll();                              // wake consumers
    }

    public synchronized int consume() throws InterruptedException {
        while (q.isEmpty()) wait();               // buffer empty → wait
        int item = q.poll();
        System.out.println("consumed " + item);
        notifyAll();                              // wake producers
        return item;
    }
}
Trap
  • Calling wait()/notify() outside synchronized → IllegalMonitorStateException at runtime (compiles fine).
  • notify() with mixed producers and consumers can wake the wrong kind of thread → everyone waits forever. Use notifyAll(), or use two Condition objects (see next section).
  • wait() releases only the monitor of that object. Any other lock the thread holds is still held — a deadlock source.
In real code, don't write this at all 
BlockingQueue<Integer> q = new ArrayBlockingQueue<>(5);
q.put(item);      // blocks when full
int item = q.take();   // blocks when empty

BlockingQueue is the wait/notify pattern already written and tested. Know the manual version for the interview; ship the library version.

11The Lock API — java.util.concurrent.locks

synchronized is rigid: you cannot try, time out, interrupt, or unlock in a different scope. ReentrantLock gives all of that back.

Lock lock = new ReentrantLock();

lock.lock();
try {
    criticalSection();
} finally {
    lock.unlock();      // MANDATORY - a missed unlock deadlocks the whole app
}
Trap

Never put lock() inside the try. If lock() itself throws, the finally would call unlock() on a lock you never acquired → IllegalMonitorStateException, masking the real error. Lock first, then try.

What ReentrantLock adds

// 1. tryLock - never block; take the alternative path instead
if (lock.tryLock()) {
    try { work(); } finally { lock.unlock(); }
} else {
    System.out.println("busy, skipping");
}

// 2. tryLock with timeout - the standard deadlock-avoidance tool
if (lock.tryLock(500, TimeUnit.MILLISECONDS)) { ... }

// 3. interruptible - a waiting thread can be cancelled
lock.lockInterruptibly();

// 4. fairness - longest waiter goes first (slower, but no starvation)
Lock fair = new ReentrantLock(true);

ReadWriteLock — many readers, one writer

ReadWriteLock rw = new ReentrantReadWriteLock();

rw.readLock().lock();     // MANY threads may hold this at once
try { return map.get(k); } finally { rw.readLock().unlock(); }

rw.writeLock().lock();    // EXCLUSIVE - blocks all readers and writers
try { map.put(k, v); } finally { rw.writeLock().unlock(); }

Use when reads vastly outnumber writes (caches, config, lookup tables). If writes are frequent, the extra bookkeeping makes it slower than a plain lock.

StampedLock (Java 8) goes further with optimistic reads — read without locking, then validate(stamp) to confirm no writer interfered. Fastest for read-heavy code, but it is not reentrant.

Condition — typed wait sets

Lock lock = new ReentrantLock();
Condition notFull  = lock.newCondition();
Condition notEmpty = lock.newCondition();

// producer
lock.lock();
try {
    while (q.size() == CAP) notFull.await();   // == wait()
    q.add(item);
    notEmpty.signal();                          // == notify(), but ONLY consumers
} finally { lock.unlock(); }

Advantage over wait/notify: one lock can have many condition queues, so you signal exactly the right group instead of waking everyone.

12Atomics & CAS — lock-free

Definition — Compare-And-Swap

CAS(memoryLocation, expectedValue, newValue) is a single CPU instruction (lock cmpxchg on x86). It writes newValue only if the current value still equals expectedValue; otherwise it fails and the caller retries. No lock, no blocking, no context switch.

AtomicInteger count = new AtomicInteger(0);

count.incrementAndGet();          // atomic ++count
count.getAndIncrement();          // atomic count++
count.addAndGet(5);
count.compareAndSet(10, 20);     // only if it is exactly 10 right now
count.updateAndGet(x -> x * 2);   // retries the lambda until CAS succeeds

// the retry loop inside incrementAndGet, conceptually:
// do { old = get(); next = old + 1; } while (!compareAndSet(old, next));

The family

  • AtomicInteger, AtomicLong, AtomicBoolean, AtomicReference<T>
  • AtomicIntegerArray — per-element atomicity
  • LongAdder / LongAccumulator (Java 8) — under heavy contention, far faster than AtomicLong: each thread bumps its own cell, sum() adds them up. Use for counters/metrics where you read rarely.
  • AtomicStampedReference — value + version stamp, to defeat the ABA problem.
Asked — the ABA problem

Thread 1 reads A. Thread 2 changes it to B and back to A. Thread 1's CAS succeeds because the value still looks like A — but the world changed in between (a node was recycled, a stack was popped and pushed). Fix: attach a version counter that only ever increases → AtomicStampedReference.

Trap

CAS is not free. Under very high contention the retry loop spins and burns CPU. Lock-free beats locking for short operations with low-to-moderate contention; for long critical sections a real lock is better because the thread sleeps instead of spinning.

13Deadlock, livelock, starvation

Deadlock

// Thread 1                          Thread 2
synchronized (lockA) {              synchronized (lockB) {
    synchronized (lockB) { ... }        synchronized (lockA) { ... }
}                                    }
// T1 holds A waits for B; T2 holds B waits for A. Both wait forever.
Coffman conditions — all four must hold
  1. Mutual exclusion — a resource is held exclusively.
  2. Hold and wait — a thread holds one lock while requesting another.
  3. No preemption — a lock cannot be forcibly taken away.
  4. Circular wait — a cycle of threads each waiting on the next.

Break any one of them and deadlock is impossible.

Prevention — in priority order
  1. Global lock ordering — every thread acquires locks in the same fixed order (e.g. by System.identityHashCode or account id). Kills circular wait. This is the answer interviewers want first.
  2. tryLock(timeout) — back off and retry, releasing what you hold. Kills hold and wait.
  3. Shrink the critical section — never call unknown / external code while holding a lock.
  4. Use one lock, or a higher-level construct (ConcurrentHashMap, BlockingQueue) instead of hand-rolled locking.
// Global ordering applied to a bank transfer
void transfer(Account from, Account to, long amt) {
    Account first  = from.id < to.id ? from : to;
    Account second = from.id < to.id ? to   : from;
    synchronized (first) {
        synchronized (second) { from.debit(amt); to.credit(amt); }
    }
}

The other two

  • Livelock — threads are not blocked, they keep responding to each other and making no progress (two people stepping aside in a corridor). Typical cause: naive retry-on-conflict with no randomised backoff.
  • Starvation — a thread never gets the resource because others keep winning it. Causes: unfair locks, thread priority abuse, one thread holding a lock for too long. Fix with a fair lock.
Asked — how do you detect a deadlock in production?
  • jstack <pid> or jcmd <pid> Thread.print — the JVM prints "Found one Java-level deadlock" with both stacks.
  • VisualVM / JMC / JConsole — detect-deadlock button.
  • Programmatically: ThreadMXBean.findDeadlockedThreads().
  • In a thread dump, look for many threads in BLOCKED on - waiting to lock <0x...>.

Trap
  • Pool threads are non-daemon: forget shutdown() and your JVM never exits.
  • submit() swallows exceptions into the Future. If you never call get(), the error disappears silently. execute() lets it reach the uncaught-exception handler. This is a favourite question.
  • shutdownNow() only interrupts. A task that ignores the interrupt flag keeps running.

15Future & CompletableFuture

Future — and its limits

Future<Integer> f = pool.submit(() -> compute());

f.isDone();  f.isCancelled();
f.cancel(true);                     // true = interrupt if already running
int v = f.get();                     // BLOCKS forever if the task hangs
int v2 = f.get(2, TimeUnit.SECONDS);  // always prefer this

Limits of Future: get() blocks, you cannot chain steps, cannot combine two futures, and cannot register a callback. Every one of those is fixed by CompletableFuture.

Note: a checked exception from the task comes back wrapped — ExecutionException, with the real error in e.getCause().

CompletableFuture — async pipelines

CompletableFuture.supplyAsync(() -> fetchUser(id))       // produces a value
    .thenApply(User::getEmail)                           // transform (sync)
    .thenCompose(mail -> lookupPrefsAsync(mail))         // flatMap - avoids CF<CF<T>>
    .thenCombine(loadSettingsAsync(), Prefs::merge)      // join TWO futures
    .thenAccept(System.out::println)                     // consume, returns CF<Void>
    .exceptionally(ex -> { log.error(ex); return null; })
    .join();                                             // like get() but unchecked

Asked

thenApply vs thenCompose? thenApply with a function returning a future gives you CompletableFuture<CompletableFuture<T>>. thenCompose flattens it — it is flatMap. Same distinction as map vs flatMap in Streams.

Which pool runs it? The …Async variants without an executor use ForkJoinPool.commonPool(), which is sized cores − 1 and shared with parallel streams. Never do blocking I/O there — you will starve the whole JVM. Pass your own executor: supplyAsync(task, myPool).

Non-Async variants (thenApply vs thenApplyAsync) may run on the thread that completed the previous stage — or on the caller thread if it is already done.

Asked — CountDownLatch vs CyclicBarrier
  • Latch: a waiter thread waits; other threads count down. Count only goes down, cannot be reset.
  • Barrier: the same threads that wait are the ones that arrive. Auto-resets for the next round, and can run a barrier action.
  • If one thread at a barrier is interrupted, all the others get BrokenBarrierException.

Semaphore vs Lock: a binary semaphore (new Semaphore(1)) looks like a lock but is not reentrant and has no owner — any thread can release() a permit it never acquired. Use it for rate limiting / resource pools, not for mutual exclusion.

18ThreadLocal

A variable where every thread gets its own independent copy. No sharing → no synchronization needed.

private static final ThreadLocal<SimpleDateFormat> FMT =
        ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

String today = FMT.get().format(new Date());   // SDF is not thread-safe; this is
  • Storage lives in the Thread object itself (Thread.threadLocals, a ThreadLocalMap), keyed by the ThreadLocal instance.
  • Classic uses: per-request user / trace id (MDC logging), the current DB transaction or connection, non-thread-safe formatters.
  • InheritableThreadLocal passes the value to child threads at creation time.
Trap — the memory leak

In a thread pool the thread is reused forever, so a value you set is never garbage collected and leaks into the next unrelated task. The ThreadLocalMap key is a weak reference but the value is strong.

Always remove() in a finally block:

try { CONTEXT.set(userId); handle(request); }
finally { CONTEXT.remove(); }

Also note: with virtual threads, per-thread caching loses its point (there may be millions of threads). Java 21 offers ScopedValue as the modern replacement.

19ForkJoin & parallel streams

For divide-and-conquer CPU-bound work. The pool uses work stealing: each worker has its own double-ended queue; an idle worker steals a task from the tail of a busy worker's deque, so load balances itself.

class SumTask extends RecursiveTask<Long> {
    private static final int THRESHOLD = 1000;
    private final int[] arr; private final int lo, hi;

    protected Long compute() {
        if (hi - lo <= THRESHOLD) {              // small enough → do it directly
            long s = 0;
            for (int i = lo; i < hi; i++) s += arr[i];
            return s;
        }
        int mid = (lo + hi) >>> 1;
        SumTask left  = new SumTask(arr, lo, mid);
        SumTask right = new SumTask(arr, mid, hi);
        left.fork();                              // run async in the pool
        return right.compute() + left.join();      // compute one here, join the other
    }
}
long total = ForkJoinPool.commonPool().invoke(new SumTask(arr, 0, arr.length));
  • RecursiveTask<V> returns a value; RecursiveAction returns void.
  • Idiom: left.fork(); right.compute(); left.join(); — forking both and joining both wastes a thread.
  • A threshold is essential: splitting down to single elements costs more than the work itself.
Trap — parallel streams

list.parallelStream() runs on the shared ForkJoinPool.commonPool() — sized cores − 1 and used by the entire JVM. One blocking I/O call inside a parallel stream can stall every other parallel stream and CompletableFuture in the application.

Use parallel streams only when: the data set is large, the operation is CPU-bound and stateless, the source splits well (array, ArrayList — not LinkedList), and you have measured a gain.

21Interview question bank

Click a question to reveal the answer. Cover the answer and say it out loud first — recall beats recognition.

Difference between start() and run()?

start() creates a new OS thread, registers it with the scheduler, and the JVM calls run() on that new stack. run() called directly is an ordinary method call on the current thread — no new thread is created, and nothing runs concurrently.

Can we call start() twice on the same thread?

No — IllegalThreadStateException, because threadStatus is no longer 0. This holds even after the thread has terminated. A Thread object is single-use; a Runnable is reusable.

Runnable vs Callable?
  • run() returns void; call() returns V.
  • run() cannot throw checked exceptions; call() can.
  • Runnable works with Thread and executors; Callable only with executors (or wrapped in FutureTask).
  • Callable arrived in Java 5 with the executor framework.
sleep() vs wait()?

sleep() — static, on Thread, keeps all locks, wakes on time, callable anywhere. wait() — instance method on Object, releases the monitor, wakes on notify()/timeout/spurious wakeup, and must be inside synchronized on the same object or you get IllegalMonitorStateException.

Why are wait/notify on Object and not Thread?

Because they operate on the monitor, and every object has a monitor — not every wait is about a thread. Threads wait on the condition of an object (a queue being non-empty), so the wait set logically belongs to that object.

Why must wait() be in a while loop?

Spurious wakeups are allowed by the spec, and with notifyAll() many threads wake but only one wins the lock — by the time the others acquire it the condition may be false again. while re-checks; if proceeds on a stale assumption.

notify() vs notifyAll()?

notify() wakes one arbitrary waiter — you cannot pick which. With mixed waiter types (producers and consumers on the same monitor) it can wake the wrong one and stall everything. notifyAll() is safe but causes a thundering herd. The precise alternative is multiple Condition objects on a ReentrantLock.

volatile vs synchronized?

volatile gives visibility + ordering on one field, never blocks, and does not give atomicity. synchronized gives mutual exclusion plus visibility and ordering over a block of code. volatile count++ is still broken.

What is the Java Memory Model?

The JMM defines when a write by one thread becomes visible to another, and which reorderings the compiler/CPU may perform. Its core relation is happens-before: unlock→lock, volatile write→read, start()→thread body, thread body→join(), final-field freeze, and transitivity.

Is HashMap thread-safe? What breaks?

No. Concurrent puts can lose entries, corrupt the table, and in Java 7 could create a circular linked list during resize causing a 100% CPU infinite loop in get(). Java 8 avoids the cycle but data is still lost. Use ConcurrentHashMap.

ConcurrentHashMap vs Hashtable vs synchronizedMap?

Hashtable and Collections.synchronizedMap lock the whole map — one writer, and readers block too. ConcurrentHashMap locks only the bin being written (CAS if it is empty), reads never lock, and iterators are weakly consistent instead of fail-fast.

Why does ConcurrentHashMap forbid null?

get(k) == null would be ambiguous: absent, or present-but-null? In a single-threaded HashMap you disambiguate with containsKey; concurrently the map can change between the two calls, so the ambiguity is unfixable. The API bans null instead.

Explain the ThreadPoolExecutor admission order.

1. If running threads < corePoolSize → create a new thread. 2. Else offer to the work queue. 3. Only if the queue is full → create threads up to maximumPoolSize. 4. If that also fails → RejectedExecutionHandler. Key insight: with an unbounded queue, step 3 never happens and maximumPoolSize is meaningless.

Why avoid Executors.newFixedThreadPool in production?

It uses an unbounded LinkedBlockingQueue: under overload the queue grows until OutOfMemoryError, with no back-pressure. newCachedThreadPool has the opposite problem — unbounded thread creation. Build ThreadPoolExecutor yourself with a bounded queue and CallerRunsPolicy.

How do you size a thread pool?

CPU-bound: N_cores + 1. I/O-bound: N_cores × targetUtilisation × (1 + waitTime/serviceTime). In practice: measure, don't guess — and never let the pool be unbounded.

submit() vs execute()?

execute(Runnable) returns void; an exception reaches the thread's UncaughtExceptionHandler. submit() returns a Future and captures the exception inside it — if nobody calls get(), the failure is silently swallowed. Common source of "the task just stopped working".

shutdown() vs shutdownNow()?

shutdown() — graceful: no new tasks, existing queue drains. shutdownNow() — interrupts running tasks and returns the tasks still queued. Neither blocks; use awaitTermination for that. shutdownNow() only requests cancellation — a task ignoring interrupts keeps going.

How do you stop a thread safely?

Cooperatively. Either a volatile boolean flag checked in the loop, or interrupt() plus isInterrupted() checks and catching InterruptedException. Never stop() — it kills the thread mid-update and releases its locks, leaving objects corrupted.

What happens if you swallow InterruptedException?

The JVM clears the interrupt flag when it throws, so swallowing it destroys the signal: enclosing code and shutdownNow() never learn that cancellation was requested. Either rethrow it, or restore with Thread.currentThread().interrupt().

Daemon vs user thread?

The JVM exits when the last user thread ends, killing daemons abruptly — their finally blocks may never run. setDaemon(true) must be called before start(). Use daemons only for background housekeeping, never for work that must complete.

What is a deadlock and how do you prevent it?

Two or more threads each hold a lock the other needs — circular wait. Prevent by breaking one Coffman condition: global lock ordering (best), tryLock with timeout and backoff, shrinking critical sections, or using a single lock / higher-level concurrent structure.

Deadlock vs livelock vs starvation?

Deadlock — blocked forever, zero CPU. Livelock — running, responding to each other, zero progress. Starvation — a thread makes no progress because others always win the resource; fix with a fair lock.

What is reentrancy?

A thread already holding a lock can acquire it again; the JVM keeps a hold count and only releases at zero. Without it, one synchronized method calling another on the same object would deadlock with itself. Both synchronized and ReentrantLock are reentrant; a Semaphore(1) is not.

synchronized vs ReentrantLock — when do you pick the lock?

When you need tryLock, a timeout, interruptible acquisition, fairness, multiple condition queues, or to acquire and release in different scopes. Otherwise prefer synchronized: shorter, impossible to forget the unlock, and JIT-optimised (biased/lightweight locking).

What is CAS? Where is it used?

Compare-And-Swap: an atomic CPU instruction that writes only if the value still matches the expected one, else fails and the caller retries. It is the basis of Atomic* classes, ConcurrentHashMap's empty-bin insert, and the AQS queue behind ReentrantLock. Weakness: the ABA problem and CPU spinning under high contention.

What is AQS?

AbstractQueuedSynchronizer — a framework holding an int state plus a FIFO queue of parked threads. ReentrantLock, Semaphore, CountDownLatch and ReentrantReadWriteLock are all thin subclasses that just define what state means.

CountDownLatch vs CyclicBarrier?

Latch: one-shot, count only goes down, waiters and counters are different threads. Barrier: reusable, the arriving threads are the waiting threads, supports a barrier action, and resets automatically after each round.

How do you make a class thread-safe?

In order of preference: make it immutable (final fields, no setters); confine state to a thread or the stack; use atomic/concurrent classes; and only then synchronize — guarding all access to the state, reads included, with the same lock.

Why is double-checked locking broken without volatile?

new Singleton() = allocate, construct, assign. The JIT may reorder the assign before the construct, so another thread can see a non-null reference to a partially constructed object. volatile inserts the barrier that forbids that reordering.

Best way to write a singleton for concurrency?

Enum singleton — thread-safe by classloading, plus serialization- and reflection-proof. Or the static holder idiom: an inner class whose static final field initialises on first use, using the JVM's class-initialisation lock. Both beat double-checked locking.

What is ThreadLocal and its risk?

Per-thread storage held in the Thread object itself — no sharing, no locks. In a pool the thread is reused, so a value never removed leaks memory and bleeds into the next task. Always remove() in finally.

What is false sharing?

Two independent variables land on the same 64-byte CPU cache line. One core writing its variable invalidates the line for the other core, so both keep re-fetching from memory — big slowdown with no logical contention. Mitigations: padding, or @Contended. It is why LongAdder spreads counters across cells.

What does Thread.yield() actually do?

Hints to the scheduler that the current thread will give up its remaining slice. It is only a hint — the scheduler may immediately reschedule the same thread, and behaviour varies by OS. Never rely on it for correctness.

Explain the fork/join idiom.

left.fork(); right.compute(); left.join(); — hand one half to the pool, do the other half on the current thread, then join. Work-stealing deques keep workers busy. A size threshold is essential or the splitting costs more than the work.

Which pool does a parallel stream use?

ForkJoinPool.commonPool(), sized cores − 1 and shared JVM-wide. Blocking inside a parallel stream starves every other parallel stream and default CompletableFuture. Pass your own pool where you can, or don't go parallel.

thenApply vs thenCompose?

thenApply is map; if the function returns a future you get CF<CF<T>>. thenCompose is flatMap and flattens it. Use compose when the next step is itself asynchronous.

How does ConcurrentHashMap work in Java 8?

No segments. An empty bin is filled with a CAS; a non-empty bin is locked with synchronized on its first node. Bins longer than 8 become red-black trees. Reads are lock-free via volatile Node fields. size() uses a LongAdder-style counter array.

How would you find a deadlock in a running JVM?

jstack <pid> or jcmd <pid> Thread.print — the JVM explicitly reports "Found one Java-level deadlock" with both stack traces. VisualVM/JMC have a detect button, and ThreadMXBean.findDeadlockedThreads() does it in code.

Are local variables thread-safe?

The variable itself, yes — each thread has its own stack frame. But a local reference to a shared object gives no protection: thread safety is a property of the object, not the variable.

Is a static variable shared between threads?

Yes — static fields live in the class metadata area, one copy per class per classloader, visible to every thread. Static mutable state is the most common hidden race in real code.

What is a virtual thread and when do you use it?

A JVM-scheduled thread with a heap-allocated growable stack, multiplexed onto carrier threads. Blocking I/O unmounts it instead of parking an OS thread, so millions can run. Use for I/O-heavy concurrency; never pool them; avoid synchronized around blocking calls (it pins the carrier).

What happens if an exception escapes run()?

The thread terminates. The exception goes to the thread's UncaughtExceptionHandler, then the ThreadGroup's, then the default one — which prints the stack trace. Other threads are unaffected, and main does not see it.

Can two threads read the same object at the same time?

Yes, if nobody writes. Concurrent reads of immutable or effectively-final data need no synchronization. The moment one thread writes, all accesses — reads included — must be synchronized or the field made volatile.

What is a race condition vs a data race?

A data race is the low-level fact: two threads access the same location, at least one writes, with no happens-before between them — undefined behaviour per the JMM. A race condition is the higher-level bug: correctness depends on timing (e.g. check-then-act). You can have a race condition with no data race, and vice versa.

How do you share data between two threads safely?

Best: hand it off through a BlockingQueue — no shared mutable state at all. Otherwise: make the object immutable, use an atomic/concurrent class, or guard every access with the same lock. If it is a one-way flag, volatile is enough.

22Must-do coding programs

Write each one from scratch, run it, then write it a second way. These cover almost every coding round.

Tier 1 — asked constantly

  1. Print even and odd numbers alternately with two threads — do it three ways: wait/notify, ReentrantLock + Condition, and Semaphore.
  2. Producer–Consumer with a bounded buffer — hand-written wait/notify version, then the BlockingQueue version.
  3. Print 1 to N in sequence with 3 threads (T1 prints 1, T2 prints 2, T3 prints 3, T1 prints 4…).
  4. Thread-safe singleton — double-checked locking, static holder, enum.
  5. Demonstrate a race condition on count++, then fix it three ways: synchronized, AtomicInteger, ReentrantLock.

Tier 2 — senior-leaning

  1. Create a deadlock deliberately, prove it with jstack, then fix it with lock ordering.
  2. Bank account transfer that is safe under concurrent transfers in both directions.
  3. Implement your own BlockingQueue using wait/notify (put, take, bounded).
  4. Dining philosophers without deadlock.
  5. Custom thread pool — N worker threads consuming from a shared queue, with shutdown.
  6. Rate limiter — token bucket with a Semaphore + ScheduledExecutorService refill.

Tier 3 — framework level

  1. Parallel sum / merge sort with RecursiveTask and a threshold.
  2. Call 3 APIs in parallel and merge with CompletableFuture.allOf + timeouts + exceptionally.
  3. ExecutorService with CountDownLatch — start N workers, wait for all, aggregate results.
  4. Thread-safe LRU cache — LinkedHashMap + lock, or ConcurrentHashMap + eviction.
How to present any concurrency program
  1. Name the shared mutable state out loud.
  2. Say which invariant must hold.
  3. Name the mechanism you chose and why (lock / atomic / queue / immutability).
  4. Mention how it terminates — shutdown, interruption, poison pill.

Interviewers score that reasoning far higher than a fast keyboard.

23Last-night cheat sheet

Say these exactly right

  • start() creates a thread; run() does not.
  • sleep() keeps the lock; wait() releases it.
  • wait()/notify() must be inside synchronized, always in a while loop.
  • volatile = visibility + ordering, never atomicity.
  • Pool order: core → queue → max → reject.
  • Unbounded queue makes maximumPoolSize meaningless.
  • submit() hides exceptions in the Future; execute() does not.
  • Lock ordering is the primary deadlock cure.
  • Java RUNNABLE ≠ running — it also means "ready".
  • ConcurrentHashMap allows no nulls; reads never lock.
  • Always ThreadLocal.remove() in a pool.
  • Prefer immutability over synchronization.

Never say these

  • "volatile makes count++ thread-safe"
  • "synchronized static and synchronized instance methods use the same lock"
  • "wait() can be called anywhere"
  • "setPriority guarantees execution order"
  • "more threads always means faster"
  • "stop() is how you stop a thread"
