00Why collections exist

An array is a fixed block of memory with a length fixed at birth. Real programs do not know how many things they will hold, and they need more than "the element at index 4" — they need lookup by key, ordering, uniqueness, first-in-first-out. The Collection Framework is the standard answer to all of that.

What an array cannot do

ArrayCollection
Fixed size — new int[10] is 10 foreverGrows and shrinks on demand
Holds primitives and objectsObjects only — primitives are autoboxed
Only length, index read/writeadd / remove / contains / sort / iterate
No uniqueness, no key lookup, no ordering policySet, Map, Queue give you each of those
Covariant — Object[] o = new String[1] compiles, then throws at runtimeInvariant — the same mistake is a compile error
Definition

Collection Framework — a unified architecture of interfaces (the contracts: List, Set, Map, Queue), implementations (ArrayList, HashMap, …) and algorithms (the static methods on Collections and Arrays).

The whole point of splitting interface from implementation: you write List<String> names = new ArrayList<>(); and can swap in LinkedList tomorrow without touching a single line that uses names. That is programming to an interface, and it is the one-line answer when an interviewer asks why the framework is designed this way.

Asked — "Collection vs Collections?"

Collection (no s) is the root interface — java.util.Collection<E>, the thing List and Set extend.

Collections (with s) is a final utility class of static helper methods — Collections.sort(), unmodifiableList(), emptyList(). Same relation as Array vs Arrays.

Trap — autoboxing is not free

List<Integer> does not store ints. Every element is a heap-allocated Integer object plus a reference — roughly 16–20 bytes instead of 4. A million-element int[] is 4 MB; a million-element List<Integer> is closer to 20 MB.

Java caches Integer values from −128 to 127, which is why a == b is accidentally true for small numbers and false for large ones. Always compare boxed values with .equals().

01The hierarchy map

Learn this shape once and half the framework answers itself. There are two separate trees — and the most common beginner mistake is thinking there is one.

The four contracts
  • List — ordered by index, duplicates allowed. "A row of numbered slots."
  • Set — no duplicates, usually no index. "A bag of distinct things."
  • Queue / Deque — ordered for processing: FIFO, LIFO, or by priority.
  • Map — key → value pairs, unique keys. Not a Collection at all.
Asked — "Why is Map not a Collection?"

Because a Collection is a container of single elements — its whole contract is built around add(E e) and Iterator<E>. A Map holds pairs; add(entry) would not fit, and iterator() would have no sensible single answer.

Instead a Map exposes three collection views: keySet(), values(), entrySet(). Say "it is not a collection of elements, it is a collection of mappings" and follow with the three views — that is the full-marks answer.

The two other root interfaces

  • Iterable<E> — the real root. It promises exactly one thing: iterator(). That is what makes the for-each loop work (section 03).
  • Collection<E> — adds the common verbs: add, remove, contains, size, isEmpty, clear, stream(), plus the bulk addAll/removeAll/retainAll.
Under the hood — the AbstractX classes

Between the interface and the real class sits a skeleton: AbstractCollection → AbstractList → ArrayList. The skeleton implements everything it can in terms of a couple of primitives (get(i) and size() for a list), so writing your own list means overriding two methods, not twenty. This is the Template Method pattern, and "why does ArrayList extend AbstractList?" has exactly that answer.

Trap — optional operations

Every mutating method on the interfaces is documented as optional. Arrays.asList(...), List.of(...) and Collections.unmodifiableList(...) all satisfy List yet throw UnsupportedOperationException from add(). The type tells you the shape, not whether you may write to it.

02Generics & type erasure

Generics are the reason a collection is type-safe. They are also almost entirely a compile-time device — understanding what survives into the bytecode explains every strange rule.

Life before generics

List raw = new ArrayList();          // raw type - holds Object
raw.add("hello");
raw.add(42);                            // compiles fine. the bug is planted here
String s = (String) raw.get(1);        // ClassCastException at RUNTIME

With generics the same mistake is caught at the keyboard: List<String> simply will not accept 42. Generics move failures from runtime to compile time and remove the casts.

Definition — type erasure

The compiler checks your types, then throws them away. List<String> and List<Integer> are both plain List in the class file; the compiler silently inserts the casts you no longer write. Erasure replaces <T> with Object, or with the first bound if there is one (<T extends Number> erases to Number).

Why do it this way? Backward compatibility — Java 5 code had to keep running on collections compiled before generics existed.

Trap — everything erasure forbids
  • new T() — illegal, the type is gone at runtime. Pass a Class<T> or a Supplier<T> instead.
  • new T[10] — illegal. Create Object[] and cast, the way ArrayList itself does.
  • if (list instanceof List<String>) — illegal; only List<?> is checkable.
  • Two overloads f(List<String>) and f(List<Integer>) — same erasure, will not compile.
  • A generic class cannot extend Throwable — catch blocks need real runtime types.
  • Static members cannot use the type parameter of the class — there is one static field for all parameterisations.

Wildcards — and why you need them

Collections are invariant: List<String> is not a subtype of List<Object>, even though String is a subtype of Object. If it were, this would compile — and corrupt the list:

List<Object> objs = names;    // imagine this were allowed
objs.add(42);                 // an Integer now sits inside a List<String>

Wildcards give back the flexibility without the hole.

FormMeansYou may readYou may write
List<?>list of some unknown typeObjectnothing but null
List<? extends Number>Number or any subtype — a producerNumbernothing but null
List<? super Integer>Integer or any supertype — a consumerObject onlyInteger and subtypes
Asked — PECS

Producer Extends, Consumer Super. If the parameter produces values for you to read, use ? extends T. If it consumes values you hand it, use ? super T. If it does both, use a plain T.

The signature in the JDK itself is the perfect example — quote it:

public static <T> void copy(List<? super T> dest, List<? extends T> src)

src produces (extends), dest consumes (super). Same idea in Collections.addAll, Stream.map(Function<? super T, ? extends R>) and Comparator.comparing.

Under the hood — heap pollution & @SafeVarargs

Because erasure hides the real parameter, a List<String> reference can end up pointing at a list holding an Integer. The JVM calls that heap pollution, and it is why generic varargs (T... args, really a T[]) raise an "unchecked" warning. If your method only reads the array and never stores it, mark it @SafeVarargs.

03Iterable, Iterator, fail-fast

Every collection is walkable because it implements Iterable. The for-each loop is pure syntax sugar — the compiler rewrites it:

// you write
for (String s : list) { use(s); }

// the compiler emits
for (Iterator<String> it = list.iterator(); it.hasNext(); ) {
    String s = it.next();
    use(s);
}

That rewrite explains why you cannot call list.remove(s) inside a for-each: the loop holds an iterator that does not know you did it.

Iterator<E>What it does
hasNext()Is there another element? Does not move.
next()Returns the next element and advances. NoSuchElementException if exhausted.
remove()The only safe way to delete while iterating. Removes what next() just returned.
forEachRemaining(c)Java 8 — consume the rest.

ListIterator — the List-only upgrade

  • Walks both ways: hasPrevious(), previous().
  • Knows where it is: nextIndex(), previousIndex().
  • Can modify: set(e) replaces, add(e) inserts at the cursor.
Definition — fail-fast vs fail-safe

Fail-fast — the iterator throws ConcurrentModificationException the moment it notices the collection was structurally changed behind its back. ArrayList, HashMap, HashSet, LinkedList: all fail-fast.

Fail-safe (more correctly weakly consistent) — the iterator works on a snapshot or tolerates concurrent change, and never throws. CopyOnWriteArrayList, ConcurrentHashMap, ConcurrentSkipListMap.

Structural modification = adding or removing. Calling set(i, v) on a list or put on an existing key is not structural and never trips the check.

Under the hood — how modCount works

Every AbstractList and HashMap keeps an int field modCount, bumped on each add/remove. When you ask for an iterator it copies that value into expectedModCount. Every next() runs:

final void checkForComodification() {
    if (modCount != expectedModCount)
        throw new ConcurrentModificationException();
}

it.remove() is safe precisely because it re-syncs expectedModCount = modCount after removing.

It is best-effort, not a guarantee. The docs say so explicitly — never write code whose correctness depends on CME being thrown.

Trap — the removal that looks like it works 
List<String> l = new ArrayList<>(List.of("a", "b", "c"));
for (String s : l) if (s.equals("a")) l.remove(s);   // CME

// but with two elements, removing the FIRST of them:
List<String> t = new ArrayList<>(List.of("a", "b"));
for (String s : t) if (s.equals("a")) t.remove(s);   // NO exception!

Why? After removing, size is 1 and cursor is 1, so hasNext() returns false and the loop exits before next() can check modCount. The last element is silently skipped. This is a favourite trick question.

The three correct ways to remove:

Iterator<String> it = l.iterator();
while (it.hasNext()) if (it.next().equals("a")) it.remove();

l.removeIf(s -> s.equals("a"));                 // Java 8, clearest

List<String> kept = l.stream().filter(...).toList();  // build a new list
Asked — "Iterator vs Enumeration?"

Enumeration is the Java 1.0 original (hasMoreElements/nextElement), used by Vector and Hashtable. It has no remove and is not fail-fast. Iterator replaced it in Java 1.2 with shorter names, removal, and the modCount check. Use Enumeration only when a legacy API hands you one.

04equals & hashCode contract

This is the single most important section in the whole file. HashMap, HashSet, LinkedHashMap, ConcurrentHashMap, distinct(), contains() — all of them are only as correct as your equals and hashCode.

The contract
  1. If a.equals(b) is true, then a.hashCode() == b.hashCode() must be true.
  2. If hash codes are equal, equals may still be false — that is a legal collision.
  3. hashCode() must return the same value every time, as long as the fields used in equals do not change.
  4. equals must be reflexive (a.equals(a)), symmetric, transitive, consistent, and a.equals(null) must be false.

Rule 1 is the one that breaks code. Rule 2 is the one people get wrong in interviews.

Why a hash collection needs both

Lookup is a two-step process, and each step uses a different method:

  1. hashCode() decides which bucket to look in — this is the O(1) part.
  2. equals() decides which entry inside that bucket is the one — this is the correctness part.

Break step 1 and the right entry is never found because you looked in the wrong bucket. Break step 2 and you find the bucket but reject the entry.

Trap — override equals but not hashCode 
class Point {
    int x, y;
    // equals overridden, hashCode NOT overridden
    public boolean equals(Object o) { /* compares x and y */ }
}

Set<Point> set = new HashSet<>();
set.add(new Point(1,2));
set.contains(new Point(1,2));   // false !
set.add(new Point(1,2));        // size is now 2, in a SET

The inherited Object.hashCode() is identity-based, so the two equal points land in different buckets and never meet. Always override the pair together.

Trap — the mutable key 
Map<Point,String> m = new HashMap<>();
Point p = new Point(1,2);
m.put(p, "origin-ish");
p.x = 99;                       // the key mutated AFTER insertion
m.get(p);                       // null - it hashes to a different bucket now
m.containsKey(p);               // false. the entry is stranded, a memory leak

The entry is still in the map and still counted by size(), but it is unreachable forever. Use immutable keys — String, Integer, enum, a record, or a class whose equals fields are all final. This is the strongest single argument for records as map keys.

Writing them correctly

public final class Employee {
    private final String id;
    private final String name;

    @Override public boolean equals(Object o) {
        if (this == o) return true;                 // cheap fast path
        if (!(o instanceof Employee e)) return false;  // null-safe, Java 16 pattern
        return id.equals(e.id) && name.equals(e.name);
    }

    @Override public int hashCode() {
        return Objects.hash(id, name);                // same fields, same order
    }
}

Java 16 records do all of this for you — a record Employee(String id, String name) {} generates a correct equals, hashCode and toString over all components. For a value-like map key, prefer a record.

Under the hood — Objects.hash vs the 31 trick

Objects.hash(a, b) is Arrays.hashCode on a varargs array, so it allocates. The classic hand-written form avoids that:

int h = 17;
h = 31 * h + id.hashCode();
h = 31 * h + name.hashCode();

Why 31? It is odd and prime, it spreads bits well, and the JIT turns 31 * h into (h << 5) - h — a shift and a subtract. String.hashCode() uses exactly this: s[0]*31^(n-1) + s[1]*31^(n-2) + ..., cached in a field after the first call.

Asked — rapid fire
  • Can two unequal objects share a hash code? Yes — a collision, perfectly legal and unavoidable (there are more objects than ints).
  • Can two equal objects have different hash codes? No — that breaks the contract and silently breaks every hash collection.
  • What if hashCode always returns 1? Still correct, but every key lands in one bucket — the map degenerates to a list, O(n) lookup (O(log n) from Java 8 once the bin is treeified).
  • Does HashSet call hashCode or equals first? hashCode, to find the bucket; equals only against entries already in that bucket.
  • Which is cheaper? hashCode — which is exactly why it runs first as a filter.

05Comparable vs Comparator

Two different jobs. Comparable defines the one natural order a class is born with. Comparator defines any number of external orders imposed from outside.

Comparable<T>Comparator<T>
Packagejava.langjava.util
Methodint compareTo(T o)int compare(T a, T b)
LivesInside the classOutside — a separate object or lambda
How manyExactly oneAs many as you like
Needs source accessYesNo
Used byTreeMap, TreeSet, Collections.sort(list)sort(list, cmp), new TreeSet<>(cmp)

The return value is what people forget: negative if a comes first, zero if equal in ordering, positive if a comes after.

// natural order - the class owns it
class Employee implements Comparable<Employee> {
    public int compareTo(Employee o) { return Integer.compare(id, o.id); }
}
Collections.sort(list);                      // uses compareTo

// external orders - as many as you need
list.sort(Comparator.comparing(Employee::getName));
list.sort(Comparator.comparingDouble(Employee::getSalary).reversed());

// multi-key: salary desc, then name asc, nulls last
list.sort(Comparator.comparingDouble(Employee::getSalary).reversed()
                    .thenComparing(Employee::getName,
                                   Comparator.nullsLast(Comparator.naturalOrder())));
Trap — subtraction as a comparator 
return a.value - b.value;       // overflows and returns the WRONG sign
return Integer.compare(a.value, b.value);   // always correct

With a.value = Integer.MAX_VALUE and b.value = -1 the subtraction overflows to a negative number, so the comparator says "a comes first" when it does not. On a large list this can throw IllegalArgumentException: Comparison method violates its general contract! from TimSort.

Trap — TreeSet uses compareTo, not equals

A sorted collection decides duplicates by compareTo(...) == 0 — it never calls equals. If your comparator only looks at, say, salary, then two different employees on the same salary are "duplicates" and the second one is silently dropped.

That is why the docs say the natural ordering should be consistent with equals. BigDecimal is the famous violator: new BigDecimal("1.0") and new BigDecimal("1.00") are compareTo-equal but not equals-equal, so a HashSet keeps both and a TreeSet keeps one.

Asked — which one, and why

Use Comparable when there is one obvious order that belongs to the type itself (id, date, natural number order). Use Comparator when the order is a view the caller chooses, when you need several, or when you cannot modify the class (a third-party or JDK type). In modern code, Comparator wins most of the time because it is a one-line lambda.

Under the hood — which sort algorithm runs

Collections.sort / List.sort delegate to Arrays.sort on the backing array, which uses TimSort for objects: a stable, adaptive merge sort that finds existing runs, O(n log n) worst case and O(n) on nearly sorted data. Primitive arrays use dual-pivot quicksort instead — faster, not stable, but stability is meaningless for primitives. "Object sort is stable, primitive sort is not" is a good line to have ready.

06List & ArrayList internals

A List is an ordered sequence with integer indices and duplicates allowed. ArrayList is the default choice in almost every program you will write — and the class interviewers ask about most.

The List contract adds index operations

get(i)  set(i,e)  add(i,e)  remove(i)  indexOf(o)  lastIndexOf(o)
subList(from,to)  listIterator()  sort(cmp)  replaceAll(fn)
Under the hood — the three fields 
transient Object[] elementData;   // the backing array
private int size;                  // how many slots are USED
protected transient int modCount; // structural changes, for fail-fast

capacity is elementData.length; size is how much of it is filled. They are different numbers and size() returns the second one — there is no public way to read capacity.

elementData is transient and writeObject is custom, so serialization writes only the used elements rather than a half-empty array.

Growth — the number to memorise

new ArrayList<>()            // capacity 0 - a shared empty array, lazily grown
first add()                   // jumps to 10 (DEFAULT_CAPACITY)
full?                         // newCapacity = oldCapacity + (oldCapacity >> 1)
                              // i.e. 1.5x : 10 -> 15 -> 22 -> 33 -> 49 -> 73 ...

Growing is not cheap: it allocates a new array and calls System.arraycopy (an intrinsic, but still O(n)), then leaves the old array for the GC.

Do this

If you know roughly how many elements are coming, pre-size it: new ArrayList<>(10_000). Filling a list of a million elements from capacity 0 costs about 30 reallocations and copies well over a million references; pre-sizing costs one allocation.

Definition — amortised O(1)

add(e) at the end is usually one array write — O(1). Occasionally it triggers a 1.5x resize — O(n). Because resizes get rarer as the list grows (geometric growth), the average cost per add over n adds is constant. That is what "amortised O(1)" means, and it is exactly the phrase to use.

Complexity — know the why, not just the letter

Trap — removing from the front in a loop

while (!list.isEmpty()) list.remove(0); is O(n²) — every removal shifts the whole remaining array. On 100k elements that is billions of copies. Iterate backwards, use removeIf, or use an ArrayDeque if you need front removal.

Also: list.remove(1) removes index 1, while list.remove(Integer.valueOf(1)) removes the object 1. On a List<Integer> that difference has bitten everybody once.

Trap — subList is a view, not a copy 
List<String> part = list.subList(2, 5);
part.clear();          // removes those 3 elements FROM list too
list.add("x");
part.get(0);           // ConcurrentModificationException

The sublist is backed by the original and shares its modCount. Structurally modifying the parent invalidates the view. If you want an independent copy: new ArrayList<>(list.subList(2, 5)).

Asked — "How does ArrayList grow?"

Full answer in one breath: "It wraps an Object array. Default capacity is 10, created lazily on the first add. When full it computes oldCapacity + (oldCapacity >> 1), that is 1.5x, allocates a new array, System.arraycopy's the contents over and drops the old one. So add at the end is amortised O(1), but insert or remove in the middle is O(n) because of the shift."

07LinkedList internals

A doubly linked list. It implements both List and Deque, so it is simultaneously a list, a queue and a stack.

private static class Node<E> {
    E item;
    Node<E> next;
    Node<E> prev;
}
transient Node<E> first;   // head
transient Node<E> last;    // tail  -> both ends are O(1)
Under the hood — the optimisation in get(i)

node(int index) checks which half the index falls in and walks from the nearer end:

if (index < (size >> 1)) { walk forward from first; }
else                    { walk backward from last; }

It is still O(n) — at best n/2 pointer hops. This is why indexing a LinkedList in a loop is the classic accidental O(n²).

Asked — "When would you actually use LinkedList?"

The honest, senior answer: almost never as a List. Even for middle insertion, ArrayList usually wins because System.arraycopy is a vectorised intrinsic while a linked walk is a chain of cache misses. Each node also costs ~40 bytes of overhead for one reference of payload.

It is defensible when you need Deque behaviour (both ends) — and even then ArrayDeque is faster. Saying "I default to ArrayList, and reach for ArrayDeque rather than LinkedList when I need a queue" reads as experience.

Trap — the accidental quadratic 
for (int i = 0; i < linked.size(); i++) use(linked.get(i));   // O(n^2)
for (String s : linked) use(s);                              // O(n) - iterator

08Vector, Stack, legacy

The Java 1.0 collections, retrofitted into the framework in 1.2. You need to recognise them, explain why they are obsolete, and never choose them.

Vector

  • An ArrayList where every method is synchronized.
  • Grows by 100% (doubles), not 1.5x — or by capacityIncrement if you passed one. "Vector doubles, ArrayList grows by half" is a stock question.
  • Has legacy method names alongside the modern ones: addElement, elementAt, removeElement, elements().
Trap — "Vector is thread-safe" is only half true

Each method is atomic. A sequence of methods is not:

if (!v.contains(x)) v.add(x);   // two atomic calls, still a race

Between the two calls another thread can add x. Compound actions need external synchronization regardless. Iteration has the same problem — you must lock around the whole loop. For real concurrency use CopyOnWriteArrayList or ConcurrentHashMap, which offer atomic compound operations.

Stack

Stack extends Vector — and that is its fatal design flaw. Because it inherits everything, you can do this:

Stack<Integer> s = new Stack<>();
s.push(1); s.push(2);
s.add(0, 99);       // insert at the BOTTOM of a stack. nonsense, but legal
s.get(0);            // random access into a stack

It also iterates bottom-to-top, the opposite of pop order — a genuine surprise in real code.

Do this instead 
Deque<Integer> stack = new ArrayDeque<>();
stack.push(1);   // addFirst
stack.pop();      // removeFirst
stack.peek();     // peekFirst

The Javadoc of Stack itself recommends Deque. It is faster (no synchronization), it iterates in pop order, and it cannot be used as a list by accident.

The rest of the legacy corner

  • Hashtable — synchronized map, no nulls at all. Replaced by ConcurrentHashMap (section 19).
  • Properties extends Hashtable<Object,Object> — config files, load()/store(). Still used, still awkwardly typed.
  • Enumeration — the pre-Iterator walker (section 03).
  • Dictionary — the abstract parent of Hashtable. Obsolete; nothing should extend it.

09CopyOnWriteArrayList

The concurrent List. Its strategy is in the name: every mutation copies the entire backing array.

public boolean add(E e) {
    synchronized (lock) {
        Object[] es = getArray();
        Object[] newEs = Arrays.copyOf(es, es.length + 1);  // full copy
        newEs[es.length] = e;
        setArray(newEs);                 // one volatile write - publishes it
        return true;
    }
}
  • The array field is volatile, so readers never lock and never block — they just read the current array reference.
  • Writers take a lock and swap in a fresh array. Writes are O(n), every single time.
  • An iterator captures the array reference at creation, so it iterates a snapshot: it never throws ConcurrentModificationException and never sees later changes.
  • iterator().remove() throws UnsupportedOperationException — you cannot mutate a snapshot.
Do this — the one right use case

Read-mostly, write-rarely, shared across threads. The canonical example is a listener/observer list: registered once at startup, then iterated on every event.

CopyOnWriteArraySet is the same idea for sets (backed by a COW list, so contains is O(n) — fine for a handful of listeners, terrible for thousands).

Trap

Write-heavy use is catastrophic: adding n elements one at a time is O(n²) copies, and each copy briefly doubles the memory for that array. If writes are frequent, use Collections.synchronizedList with explicit locking, or restructure around ConcurrentHashMap.

Also remember the snapshot is shallow — the array is copied, the elements are not. A mutable element mutated by another thread is still visible through the "snapshot".

Under the hood — HashSet is a HashMap in a costume 
private transient HashMap<E,Object> map;
private static final Object PRESENT = new Object();   // one shared dummy value

public boolean add(E e)      { return map.put(e, PRESENT) == null; }
public boolean contains(Object o) { return map.containsKey(o); }
public boolean remove(Object o)   { return map.remove(o) == PRESENT; }
public int size()            { return map.size(); }

Your elements are the map keys; every value is the same singleton PRESENT object. That single fact answers a whole family of questions:

  • Why is HashSet unordered? Because HashMap keys are bucket-ordered.
  • Why does add return boolean? Because put returns the previous value — null means it was absent, so the add really happened.
  • Why does it need equals/hashCode? Because uniqueness is key uniqueness in the map.
  • Why exactly one null? Because HashMap allows exactly one null key.
  • Everything in section 15 about HashMap applies unchanged.

The bulk operations are set algebra

a.addAll(b);      // union          a = a U b
a.retainAll(b);   // intersection   a = a n b
a.removeAll(b);   // difference     a = a - b
a.containsAll(b); // subset test    b subset of a ?

These are on Collection, so they work on lists too — but on a list they are O(n·m) because contains is linear. Converting to a HashSet first turns an O(n·m) job into O(n+m). That trick alone has fixed many slow loops.

Trap — removeAll can be surprisingly slow, or surprisingly fast

list.removeAll(otherList) is O(n·m). list.removeAll(otherSet) is O(n). The JDK picks its strategy from the size of the two collections, not their types, so the same call can flip behaviour as data grows. Pass a Set when you mean a membership test.

Asked — "How does HashSet guarantee uniqueness?"

"It delegates to a HashMap and stores the element as the key with a constant dummy value. Adding calls put, and put returns the previous value; if that is non-null the element was already there, so add returns false and nothing is inserted. Uniqueness is therefore decided by hashCode to find the bucket and equals to compare inside it."

11LinkedHashSet

LinkedHashSet extends HashSet and is backed by a LinkedHashMap. It keeps the O(1) operations of a hash set and adds a doubly linked list through all entries so iteration follows insertion order.

Set<String> h = new HashSet<>(List.of("banana", "apple", "cherry"));
// [banana, cherry, apple]  - an artefact of hashing, do not rely on it

Set<String> l = new LinkedHashSet<>(List.of("banana", "apple", "cherry"));
// [banana, apple, cherry]  - guaranteed
  • Re-inserting an existing element does not move it — the original position is kept.
  • Costs a little more memory (two extra references per entry) and slightly slower writes.
  • Iteration is actually faster than HashSet: it walks the linked list instead of scanning empty buckets.
Do this — deduplicate while preserving order 
List<String> unique = new ArrayList<>(new LinkedHashSet<>(withDuplicates));

// stream equivalent
List<String> u = withDuplicates.stream().distinct().toList();

This is the single most common real use of LinkedHashSet, and a frequent one-liner question.

Asked

"HashSet vs LinkedHashSet vs TreeSet — pick one." Need speed and do not care about order → HashSet. Need the order you inserted → LinkedHashSet. Need sorted order, or range queries like headSet/tailSet/first/last → TreeSet, and accept O(log n).

12TreeSet & NavigableSet

A sorted set, backed by a TreeMap, which is a red-black tree — a self-balancing binary search tree. Every operation is O(log n) because the tree height is kept at O(log n).

Under the hood — red-black rules

A binary search tree degenerates into a linked list if you insert sorted data. Red-black rules prevent that by repainting and rotating after each insert:

  1. Every node is red or black; the root is black.
  2. A red node cannot have a red child (no two reds in a row).
  3. Every path from a node down to a null leaf contains the same number of black nodes.

Together these force the longest path to be at most twice the shortest, which bounds the height at 2·log(n+1) — hence guaranteed O(log n) insert, delete and search. You do not need to code rotations; you do need to be able to say why the tree stays balanced.

  • "Give me the 5 nearest values to x" — floor / ceiling walking outwards.
  • Leaderboards and rank queries kept sorted as data arrives.
  • Interval / booking overlap checks — floor(start) tells you the interval that could overlap.
  • Any time you would otherwise re-sort a list after every insertion.

13EnumSet & the bit vector

A specialised Set for enum constants, and one of the most elegant classes in the JDK. If your elements are enum values, this is always the right choice.

enum Day { MON, TUE, WED, THU, FRI, SAT, SUN }

EnumSet<Day> weekend = EnumSet.of(Day.SAT, Day.SUN);
EnumSet<Day> week    = EnumSet.complementOf(weekend);   // MON..FRI
EnumSet<Day> all     = EnumSet.allOf(Day.class);
EnumSet<Day> none    = EnumSet.noneOf(Day.class);       // the empty start
EnumSet<Day> mid     = EnumSet.range(Day.TUE, Day.THU); // TUE, WED, THU
Under the hood — a set that is one long

EnumSet is abstract with two package-private implementations chosen by noneOf:

  • RegularEnumSet — up to 64 constants: the entire set is one long, bit i meaning "ordinal i is present".
  • JumboEnumSet — more than 64: a long[].

So add, remove and contains are single bitwise instructions, containsAll is one AND, addAll is one OR, and the whole set fits in a machine word. Iteration comes out in ordinal (declaration) order for free. It is dramatically faster and smaller than HashSet<Day> — no hashing, no buckets, no boxing.

Do this — replace int bit flags

Old C-style code writes int flags = READ | WRITE;. EnumSet gives the same performance with type safety, readable toString(), and no chance of mixing flags from two unrelated groups. Effective Java Item 36 is exactly this: "use EnumSet instead of bit fields".

The map counterpart is EnumMap (section 18) — an array indexed by ordinal.

Trap

There is no public constructor — only the static factories. EnumSet.of() with no arguments does not exist; use noneOf(X.class), which is also the only form that can build an empty set (it needs the Class to know the universe of constants).

It is not thread-safe. Wrap with Collections.synchronizedSet if shared across threads.

15HashMap internals

The most asked class in Java interviews. Know the fields, the six steps of a put, the resize, and the treeify threshold — and you can answer anything they follow up with.

The fields and the constants

transient Node<K,V>[] table;      // the bucket array - always a power of 2
transient int size;               // number of key-value mappings

final float loadFactor;           // 0.75 by default

Under the hood — the Node 
static class Node<K,V> implements Map.Entry<K,V> {
    final int hash;    // cached! never recomputed
    final K key;
    V value;
    Node<K,V> next;    // singly linked chain within one bucket
}

The hash is cached in the node, which is why a lookup can reject a candidate with one int comparison before ever calling equals.

Step 1 — the hash spread

static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
Why XOR the top 16 bits down?

The bucket index is hash & (n - 1), which with a table of 16 keeps only the lowest 4 bits. Two keys differing only in their high bits would collide every time. XOR-ing the upper half into the lower half mixes high-bit entropy down where the mask can see it — one cheap instruction instead of a full re-hash. This is called spreading or perturbation.

Note null hashes to 0, so the null key always lives in bucket 0. That is the whole "how does HashMap store null?" answer.

Step 2 — the bucket index, and why capacity is a power of 2

index = (n - 1) & hash        // NOT hash % n

When n is a power of two, n-1 is all ones in binary (16-1 = 0b1111), so the AND keeps exactly the low bits — identical to a modulo, but a single machine instruction instead of a division. If you pass new HashMap<>(13), the constructor silently rounds up to 16 via tableSizeFor. "Why must capacity be a power of two?" is asked constantly — the answer is: so that & (n-1) can replace %, and so that resizing can split a bin cleanly (below).

Step 3 — what put actually does

  1. Compute the spread hash; if the table is null, resize() creates it (lazy init — new HashMap<>() allocates no array).
  2. Find the bucket. If it is empty, drop a new Node there. Done.
  3. If occupied, compare with the first node: hash == h && (k == key || key.equals(k)). The == short-circuit makes interned Strings and boxed small Integers very fast.
  4. If it is a TreeNode, delegate to the red-black tree put.
  5. Otherwise walk the chain. Match → overwrite the value and return the old one. End of chain → append; if the chain is now ≥ 8, call treeifyBin.
  6. if (++size > threshold) resize();
Under the hood — resize, and the clever bit

Resize doubles the capacity and the threshold, allocates a new table and redistributes every node. The elegant part, added in Java 8:

When capacity doubles from n to 2n, an existing key can only stay at index i or move to i + n — nothing else is possible, because only one extra bit of the hash is now in play. So the JDK tests that single bit:

if ((e.hash & oldCap) == 0)  -> stays at index i   (lo list)
else                        -> moves to i + oldCap (hi list)

No re-hashing, no modulo — each bin is split into two lists in preserved relative order, which is also what fixed the Java 7 reversal bug. Resize is still O(n) and allocates a whole new table, so it is the thing you pre-size to avoid.

Definition — load factor 0.75

threshold = capacity * loadFactor. With 16 buckets the map resizes when the 13th entry is added. 0.75 is the documented time/space compromise: lower means more empty buckets wasted but fewer collisions; higher means denser tables, longer chains, slower lookups. The Javadoc notes it offers a good tradeoff under the assumption that hash codes are roughly uniform (formally, bucket occupancy follows a Poisson distribution).

Sizing formula: to hold n entries without any resize, ask for n / 0.75 + 1. For 1000 entries, new HashMap<>(1334). Java 19 added HashMap.newHashMap(n) which does that arithmetic for you.

Step 4 — treeification

  • A bin whose chain reaches 8 nodes becomes a red-black tree, turning that bin from O(n) to O(log n).
  • Unless the table is smaller than MIN_TREEIFY_CAPACITY = 64 — then it resizes instead, because in a small table long chains mean "too few buckets", not "bad hash".
  • If a tree shrinks to 6 nodes (during resize or removal) it untreeifies back to a list. The gap between 8 and 6 is hysteresis, so a bin hovering at the boundary does not flip back and forth.
  • Tree nodes take about twice the space of plain nodes, which is why 8 is set high enough that a decent hash function should essentially never reach it.
Asked — "Why 8 and 6?"

Because with a well-distributed hash, the chance of a bin reaching 8 entries is about 1 in 10 million (the Poisson calculation is in the HashMap source comments). So treeification is a defence against hostile or terrible hash codes, not an ordinary code path. The real motivation was a denial-of-service class of attack: an attacker sends thousands of keys that collide, and a pre-Java-8 HashMap degrades to O(n) per lookup.

Trap — the famous Java 7 infinite loop

Two threads resizing a Java 7 HashMap at the same time could link node A → B and B → A, producing a cycle. A later get() on that bucket would spin forever at 100% CPU — a real production outage that many teams have hit.

Java 8 removed the reversal so the cycle cannot form, but HashMap is still not thread-safe: concurrent puts still lose entries and corrupt size. The fix is ConcurrentHashMap, never "it is fine on Java 8".

Asked — the full "how does HashMap work?" answer

"It is an array of buckets whose length is a power of two. On put it takes the key hashCode, spreads it by XOR-ing the top 16 bits down, and masks with (n-1) to get the bucket index. If the bucket is empty it stores a Node. If not, it walks the chain comparing cached hash first and then equals; a match overwrites the value, otherwise it appends. A chain of 8 in a table of at least 64 becomes a red-black tree. When size exceeds capacity times the 0.75 load factor it doubles the table and splits each bin into a lo and hi list using one extra hash bit. get does the same index computation and comparison. Average O(1), worst case O(log n) since Java 8."

16LinkedHashMap & LRU

LinkedHashMap extends HashMap and threads a doubly linked list through every entry, so iteration has a defined order. Its entry adds two fields:

static class Entry<K,V> extends HashMap.Node<K,V> {
    Entry<K,V> before, after;    // the cross-bucket linked list
}
final boolean accessOrder;      // false = insertion order, true = access order

The two orders

new LinkedHashMap<>()                       // insertion order
new LinkedHashMap<>(16, 0.75f, true)        // ACCESS order - the LRU switch

In access order, every get and put moves that entry to the end of the list. The head is therefore always the least recently used entry — which is the whole basis of an LRU cache.

Do this — an LRU cache in 6 lines 
class LRUCache<K,V> extends LinkedHashMap<K,V> {
    private final int capacity;

    LRUCache(int capacity) {
        super(capacity, 0.75f, true);        // accessOrder = true
        this.capacity = capacity;
    }

    @Override protected boolean removeEldestEntry(Map.Entry<K,V> eldest) {
        return size() > capacity;               // true -> evict the head
    }
}

removeEldestEntry is a hook called by HashMap.put after every insertion; returning true evicts the oldest entry. You do not remove anything yourself — you just answer the question. This is the classic "write an LRU cache" answer, and being able to produce it from memory is worth the five minutes it takes to learn.

The alternative implementation interviewers sometimes want instead: a HashMap<K,Node> plus a hand-written doubly linked list, so you control O(1) unlink and move-to-front yourself. Be ready to write that too — see section 30.

Trap
  • In access order, a plain get() is a structural modification for iteration purposes — iterating while calling get throws ConcurrentModificationException.
  • It is not thread-safe. A shared LRU cache needs Collections.synchronizedMap plus external locking, or a purpose-built cache (Caffeine, Guava).
  • containsKey does not count as an access; only get, getOrDefault, put, merge and compute reorder.

17TreeMap & NavigableMap

A sorted map built on a red-black tree (the same structure described in section 12 — TreeSet is literally a TreeMap with dummy values). Keys are kept in natural order, or in the order of a comparator you pass to the constructor.

NavigableMap<Integer,String> m = new TreeMap<>();
m.put(10, "ten"); m.put(20, "twenty"); m.put(30, "thirty");

m.firstKey();                  // 10
m.floorEntry(25);             // 20=twenty   (greatest key <= 25)
m.ceilingKey(25);             // 30          (smallest key >= 25)
m.headMap(20, true);          // {10=ten, 20=twenty}  - a live VIEW
m.subMap(10, true, 25, false); // {10=ten, 20=twenty}
m.descendingMap();             // reverse-order view
m.pollFirstEntry();            // remove and return the smallest

// a comparator changes the whole ordering
Map<String,Integer> ci = new TreeMap<>(String.CASE_INSENSITIVE_ORDER);
Do this — where TreeMap earns its O(log n)
  • Range queries — "all events between two timestamps" is one subMap, no scanning.
  • Tiered lookup — price bands, tax slabs, grade boundaries: floorEntry(value) finds the band in one call.
  • Nearest neighbour on a single dimension — floorKey and ceilingKey together.
  • Any report that must come out in sorted key order without a final sort.
Trap
  • No null keys — put(null, v) throws NPE because insertion must compare. Null values are fine.
  • Keys must be mutually comparable, or you get a ClassCastException on insert.
  • A comparator inconsistent with equals makes the map behave "wrongly" by Map contract — two keys that compare equal are one key here.
  • All the head/tail/sub views are live and bounded: inserting a key outside the view range through the view throws IllegalArgumentException.
Asked — "HashMap vs TreeMap vs LinkedHashMap"

One line each: HashMap — fastest, no order, O(1). LinkedHashMap — HashMap plus a linked list for insertion or access order, still O(1), slightly more memory. TreeMap — red-black tree, sorted keys and range queries, O(log n), no nulls. Choose on whether you need ordering, and which ordering.

18The specialist maps

Five maps you will rarely reach for, but must be able to explain — each exists to solve exactly one problem.

EnumMap — keys are enum constants

EnumMap<Day,String> schedule = new EnumMap<>(Day.class);
  • Internally just a plain array indexed by ordinal() — no hashing, no collisions, no Node objects.
  • Iterates in enum declaration order. Faster and far smaller than HashMap<Day,V>.
  • Needs the Class object in the constructor, because it must size the array to the number of constants.
  • If your key is an enum, use it — there is no downside.

WeakHashMap — entries that vanish

  • Keys are held by weak references. If nothing else in the program refers to a key, the GC may collect it and the entry disappears from the map on its own.
  • Dead entries are cleared lazily, when a later operation drains the internal ReferenceQueue — so size() can shrink between two calls with no code in between.
  • Used for caches and for metadata attached to objects you do not own.
  • The classic mistake: the value is a strong reference. If a value refers back to its key, the entry never dies — a leak in a leak-prevention class.

IdentityHashMap — == instead of equals

  • Compares keys with == reference identity, and uses System.identityHashCode. It deliberately violates the Map contract, and the Javadoc says so.
  • Two equal-but-distinct Strings are two different keys here.
  • Real uses: serialization and deep-copy graph walking ("have I already visited this exact object?"), and topology-preserving transforms.
  • Implementation curiosity: it uses linear probing in a single array where keys and values alternate — not chaining.

Hashtable & Properties — legacy

  • Hashtable: every method synchronized on the whole object, no null key and no null value, initial capacity 11, grows to 2n+1, index by % not by masking. Superseded entirely by ConcurrentHashMap.
  • Properties extends Hashtable<Object,Object> — still the standard for .properties config files, with load(InputStream), store() and a defaults chain. Use getProperty, not get, or you skip the defaults lookup.
Asked — "HashMap vs Hashtable"

HashMap is unsynchronized, allows one null key and many null values, is fail-fast, and was designed in 1.2. Hashtable is fully synchronized on a single lock, allows no nulls, uses Enumeration, and is from 1.0. Never answer "use Hashtable for thread safety" — the correct modern answer is ConcurrentHashMap, because one global lock serialises every reader as well as every writer.

19ConcurrentHashMap

The default map for shared mutable state across threads. Its Java 8 rewrite is a favourite senior-level question — and the answer is not "segments" any more.

Under the hood — the Java 8 put
  1. Compute the spread hash and find the bin.
  2. Bin empty? casTabAt — a single compare-and-swap installs the node. No lock at all in the common case.
  3. Bin occupied? synchronized (firstNode) and walk or treewalk it. Only that one bin is blocked; every other bin stays fully available.
  4. Bin header hash MOVED? A resize is in progress — this thread calls helpTransfer and joins the resize instead of waiting. Resizing is cooperative and multi-threaded.

Node.val and Node.next are volatile, which is why reads never lock and still see correct, published data.

Trap — why null is banned

Neither keys nor values may be null. On a single-threaded HashMap, get(k) == null is ambiguous ("absent" or "mapped to null") and you resolve it with containsKey. In a concurrent map that follow-up call is a race — the answer can change between the two calls, and there is no way to ask both questions atomically. Doug Lea removed the ambiguity instead of the race.

Do this — atomic compound operations 
// BROKEN - two operations, a race between them
if (!map.containsKey(k)) map.put(k, v);

// CORRECT - one atomic operation
map.putIfAbsent(k, v);
map.computeIfAbsent(k, key -> expensiveLoad(key));   // computed once, per key
map.merge(word, 1, Integer::sum);                  // atomic counter
map.compute(k, (key, old) -> old == null ? 1 : old + 1);

Keep the lambda short and side-effect free — it runs while holding that bin lock. Never call another map operation, take another lock, or do I/O inside it.

  • Iterators are weakly consistent: they never throw CME, reflect some state at or after creation, and each key appears once.
  • size() is an estimate under concurrent writes — for a live counter use mappingCount(), which returns a long.
  • ConcurrentHashMap.newKeySet() gives you the concurrent Set the framework otherwise lacks.
  • Bulk parallel operations exist: forEach, search, reduce, each with a parallelism threshold.

ConcurrentSkipListMap — the concurrent TreeMap

  • A skip list: a linked list with randomised express lanes above it, giving O(log n) expected search with no rebalancing and no global lock — which is exactly why a red-black tree could not be made lock-free easily.
  • Implements ConcurrentNavigableMap, so you get floorKey, subMap, headMap and friends, concurrently.
  • ConcurrentSkipListSet is its Set form. Use when you need sorted + concurrent; otherwise ConcurrentHashMap is faster.
Asked — "ConcurrentHashMap vs Collections.synchronizedMap"

synchronizedMap is a wrapper that puts one lock around every method, so two threads can never read at the same time, and you still must lock manually around iteration. ConcurrentHashMap locks per bin, never locks readers at all, provides atomic compound methods, and its iterators never throw CME. The only thing the wrapper gives you is the ability to make an existing arbitrary map thread-safe.

Under the hood — ArrayDeque is a circular buffer 
transient Object[] elements;   // one slot is always left empty
transient int head;            // index of the first element
transient int tail;            // index where the next tail element goes

Both ends move by wrapping the index rather than shifting elements, so both ends are true O(1) and nothing is ever copied except on a grow.

Two different implementations — know which one you are describing:

  • Java 8: the array length was always a power of two and wrapping was head = (head - 1) & (elements.length - 1) — the same masking trick HashMap uses. Growth doubled. This is the version nearly every tutorial and blog still describes.
  • Java 9+ (the Java 11 rewrite, still current in 21): the power-of-two requirement was dropped. Wrapping is now explicit — inc() / dec() helpers that compare against the length — the default array is new Object[16 + 1], and grow() adds oldCapacity + 2 below 64 and 1.5x above it. The extra slot is what keeps head == tail unambiguously meaning "empty".

Either way it is never full in the user-visible sense — it grows — so offer always returns true.

Do this 
Deque<Integer> stack = new ArrayDeque<>();   // instead of Stack
Queue<Integer> queue = new ArrayDeque<>();   // instead of LinkedList

ArrayDeque beats LinkedList as a queue (contiguous memory, no per-node object, better cache behaviour) and beats Stack as a stack (no synchronization, correct iteration order). It is the default queue in modern Java.

Trap
  • No null elements — null is the sentinel that poll and peek return for "empty", so storing one would be ambiguous. LinkedList as a Deque does allow null, which is a genuine behavioural difference.
  • Not thread-safe. The concurrent versions are ConcurrentLinkedDeque (unbounded, non-blocking) and LinkedBlockingDeque.
  • No index access — get(i) does not exist on a Deque. If you need it, you wanted a List.

21PriorityQueue & the heap

A queue where poll() returns the smallest element (by natural order or comparator), not the oldest. Backed by a binary min-heap stored in a plain array.

Under the hood — a tree with no pointers

The heap is a complete binary tree flattened into an array, so the shape needs no node objects at all:

parent of i  = (i - 1) / 2
left  of i   = 2*i + 1
right of i   = 2*i + 2

The only invariant is every parent ≤ its children. That is weaker than sorted, which is why the heap is cheap to maintain:

  • offer → place at the end, then siftUp while smaller than its parent. O(log n).
  • poll → take index 0, move the last element to the root, then siftDown. O(log n).
  • peek → array[0]. O(1).
  • remove(Object) / contains → linear scan first. O(n).
  • Building from an existing collection uses heapify — O(n), not O(n log n).
Trap — only the head is ordered 
PriorityQueue<Integer> pq = new PriorityQueue<>(List.of(5, 1, 3));
System.out.println(pq);          // [1, 5, 3]  - heap order, NOT sorted
for (Integer i : pq) ...          // iterates in heap order, not priority order
while (!pq.isEmpty()) pq.poll();  // 1, 3, 5 - THIS is the sorted way

Printing a PriorityQueue does not show sorted output, and neither does a for-each. The ordering guarantee applies to peek/poll only. This is one of the most common surprises in coding rounds.

Also: it is unbounded (it grows), it allows no nulls, and it is not stable — equal-priority elements come out in no defined order. If you need FIFO among equals, add a sequence number to the comparator.

Do this — the top-K pattern 
// K largest elements: keep a MIN-heap of size k
PriorityQueue<Integer> heap = new PriorityQueue<>();    // min-heap
for (int x : data) {
    heap.offer(x);
    if (heap.size() > k) heap.poll();     // evict the smallest
}
// O(n log k) time, O(k) space - beats sorting the whole array

// max-heap: just reverse the comparator
new PriorityQueue<>(Comparator.reverseOrder());
new PriorityQueue<>(Comparator.comparingInt(Task::priority).reversed());

Counter-intuitive but important: K largest uses a min-heap, K smallest uses a max-heap. The heap holds the winners so far, and its head is the weakest one — the next candidate to evict.

Concurrent variants: PriorityBlockingQueue (unbounded, blocking take) and DelayQueue (a priority queue ordered by expiry time, covered next).

26Streams & Collectors

A Stream is not a collection. It is a one-shot pipeline over a source: it stores nothing, it does not modify the source, and once consumed it is dead.

Definition — the three parts of a pipeline
  1. Source — collection.stream(), Arrays.stream(a), Stream.of(...), IntStream.range(0, n).
  2. Intermediate operations — filter, map, sorted, distinct, limit, skip, peek, flatMap. These are lazy: they return a new stream and do nothing until a terminal operation arrives.
  3. Terminal operation — collect, forEach, reduce, count, anyMatch, findFirst, toList. This triggers the whole pipeline, exactly once.

Laziness matters: list.stream().filter(expensive).findFirst() stops at the first match rather than filtering everything. Short-circuiting operations (findFirst, anyMatch, limit) make infinite streams usable.

The nine mistakes that show up in real code

  1. Mutating a key after insertion — the entry becomes unreachable (section 04).
  2. equals without hashCode — duplicates in a Set, failed lookups in a Map.
  3. remove(int) vs remove(Object) on a List<Integer> — index or value, silently different.
  4. Removing inside a for-each — CME, or worse, a silently skipped element.
  5. Not pre-sizing a collection you know the size of — repeated resize and copy.
  6. list.contains() inside a loop — O(n²). Use a HashSet.
  7. Indexing a LinkedList in a for loop — O(n²).
  8. Returning an internal collection from a getter — callers mutate your state. Return List.copyOf.
  9. Using HashMap across threads — lost updates and corruption; use ConcurrentHashMap.

29Interview question bank

Click a question to reveal the answer. Cover the answer and say it out loud first — recall beats recognition.

Difference between Collection and Collections?

Collection is the root interface of the framework (List, Set and Queue extend it). Collections is a final utility class of static methods — sort, reverse, shuffle, unmodifiableList, synchronizedList. Same relationship as Array and Arrays.

Why is Map not part of the Collection hierarchy?

Because Collection is defined around single elements — add(E) and Iterator<E>. A Map holds key-value pairs, so neither method has a sensible meaning. Instead it exposes three collection views: keySet(), values() and entrySet().

ArrayList vs LinkedList — and which do you actually use?
  • ArrayList: dynamic array, O(1) get, O(n) middle insert/remove, contiguous memory, excellent cache locality.
  • LinkedList: doubly linked nodes, O(n) get, O(1) at the ends, ~40 bytes overhead per element.
  • In practice ArrayList almost always wins, even for middle insertion, because System.arraycopy is a vectorised intrinsic and pointer-chasing thrashes the cache. For queue/stack behaviour use ArrayDeque, not LinkedList.
How does ArrayList grow?

Default capacity 10, created lazily on the first add (the no-arg constructor allocates nothing). When full: newCapacity = old + (old >> 1), i.e. 1.5x. It allocates a new array, System.arraycopys across, and discards the old one. Hence amortised O(1) for add-at-end. Vector doubles instead.

How does HashMap work internally?

An array of buckets, length always a power of two. put spreads the hash (h ^ (h >>> 16)), indexes with (n-1) & hash, and either drops a Node in an empty bucket or walks the chain comparing cached hash then equals. A chain of 8 in a table of at least 64 becomes a red-black tree. When size > capacity * 0.75 the table doubles and each bin splits into a lo/hi list using one extra hash bit. Average O(1), worst case O(log n).

Why must HashMap capacity be a power of two?

So the index can be computed as hash & (n-1) — a single AND instruction — instead of the much slower hash % n. It also makes resizing cheap: doubling adds exactly one significant bit, so each entry either stays at index i or moves to i + oldCapacity, decided by testing (hash & oldCap) == 0. Passing a non-power-of-two to the constructor just rounds up.

Why does HashMap XOR the high bits into the low bits?

Because the index mask only keeps the low bits of the hash. Keys whose hash codes differ only in the upper half would all collide. XOR-ing h >>> 16 into h mixes that high entropy down into the bits the mask actually reads — one cheap operation that dramatically reduces collisions for poorly distributed hash codes.

What is the load factor and why 0.75?

threshold = capacity * loadFactor — the size at which the table doubles. 0.75 is a documented time/space compromise: lower wastes buckets, higher lengthens chains and slows lookups. Under a roughly uniform hash the bucket occupancy follows a Poisson distribution, and 0.75 keeps collisions rare while keeping the table reasonably full.

What happens when two keys have the same hash code?

They land in the same bucket — a collision, which is legal. HashMap chains them in a linked list, comparing cached hash and then equals on lookup. If the chain reaches 8 nodes and the table is at least 64 buckets, the bin is converted to a red-black tree, so worst-case lookup is O(log n) rather than O(n).

What if hashCode() always returns the same constant?

The map still works correctly — the contract is not violated — but every key lands in one bucket. Lookup degrades to O(n), or O(log n) once that bin treeifies. It turns a hash map into a list with extra steps.

Why 8 for treeify and 6 for untreeify?

With a decent hash, the probability of a bin reaching 8 entries is about one in ten million, so treeification is a defence against hostile or broken hash codes rather than a normal path. The gap between 8 and 6 is hysteresis — without it a bin sitting on the boundary would convert back and forth on every add/remove. Tree nodes also cost roughly twice the memory of plain nodes.

Can HashMap store null? What about Hashtable and ConcurrentHashMap?

HashMap: one null key (hashed to 0, so always bucket 0) and any number of null values. Hashtable: no null key or value. ConcurrentHashMap: no nulls either — because get(k) == null would be ambiguous between "absent" and "mapped to null", and resolving it with containsKey is a race in a concurrent map.

What breaks if you override equals but not hashCode?

Equal objects get different hash codes, so they land in different buckets. set.contains(equalObject) returns false, a HashSet accepts visible "duplicates", and map.get(equalKey) returns null. The lookup never gets as far as calling equals, because it looked in the wrong bucket.

What happens if you mutate a key after putting it in a HashMap?

Its hash changes, so it now belongs in a different bucket — but it physically sits in the old one. get and containsKey return nothing, yet size() still counts it and iteration still yields it. The entry is stranded permanently: a correctness bug and a leak. Use immutable keys — String, Integer, enum, or a record.

HashMap vs Hashtable vs ConcurrentHashMap?
  • HashMap — unsynchronized, one null key, fail-fast iterators, Java 1.2.
  • Hashtable — every method synchronized on the whole object, no nulls, Enumeration, Java 1.0. Obsolete.
  • ConcurrentHashMap — per-bin locking (CAS on empty bins), lock-free reads, no nulls, weakly consistent iterators, atomic compound methods. The correct modern choice.
How does ConcurrentHashMap achieve thread safety in Java 8?

Segments are gone. It uses one table like HashMap, and on put: CAS to install a node into an empty bin (no lock at all), or synchronized on the first node of an occupied bin, so only that one bin blocks. Reads never lock because Node.val and next are volatile. A thread that meets a bin marked MOVED joins the in-progress resize via helpTransfer instead of waiting.

Why is ConcurrentHashMap.size() described as an estimate?

Counting is striped across baseCount plus a CounterCell[] to avoid a single contended counter. Summing them is not atomic with respect to concurrent writes, so the result is a snapshot that may already be stale. mappingCount() returns the same thing as a long and is preferred for large maps.

HashSet vs TreeSet vs LinkedHashSet?

HashSet: no order, O(1), backed by HashMap, one null. LinkedHashSet: insertion order, O(1), backed by LinkedHashMap, slightly more memory, faster iteration. TreeSet: sorted, O(log n), backed by TreeMap, no nulls, and it decides duplicates with compareTo rather than equals.

How does HashSet guarantee uniqueness?

It wraps a HashMap<E,Object> and stores each element as a key with a shared dummy value called PRESENT. add returns map.put(e, PRESENT) == null — a non-null previous value means the element was already there. So uniqueness is key uniqueness: hashCode picks the bucket, equals compares within it.

Comparable vs Comparator?

Comparable is in java.lang, has compareTo(T), lives inside the class, and gives one natural order. Comparator is in java.util, has compare(T,T), lives outside, and you can have as many as you like — including for classes you cannot modify. Comparable for the intrinsic order; Comparator for everything else.

Why should a comparator never return a - b?

Integer subtraction overflows. With a = Integer.MAX_VALUE and b = -1 the result wraps negative, so the comparator claims a < b. On a large list TimSort detects the inconsistency and throws IllegalArgumentException: Comparison method violates its general contract!. Use Integer.compare(a, b).

Fail-fast vs fail-safe iterators?

Fail-fast (ArrayList, HashMap, HashSet) compare modCount with expectedModCount on every next() and throw ConcurrentModificationException on a structural change. Fail-safe, properly weakly consistent (CopyOnWriteArrayList, ConcurrentHashMap), iterate a snapshot or tolerate change and never throw. Fail-fast is explicitly best-effort — never write logic that depends on the exception.

How do you remove elements while iterating?

Iterator.remove(), collection.removeIf(predicate), or build a new collection with a stream filter. Never collection.remove(x) inside a for-each — and note that removing the second-to-last element does not throw, it silently skips the last one, which is worse.

What is a structural modification?

Anything that changes the size — add or remove. list.set(i, v) and map.put(existingKey, v) are not structural and do not bump modCount. Exception: in an access-ordered LinkedHashMap, a plain get() is structural because it reorders the linked list.

Vector vs ArrayList?

Vector synchronizes every method and grows by 100% (doubling); ArrayList is unsynchronized and grows by 50%. Vector also carries legacy methods and Enumeration. Vector is not the answer to thread safety — compound actions like check-then-act still race, and iteration still needs external locking.

Why is Stack considered obsolete?

Stack extends Vector, so it inherits get(i) and add(i, e) — you can insert at the bottom of a "stack". It is synchronized whether you want it or not, and it iterates bottom-to-top, the opposite of pop order. Its own Javadoc recommends Deque/ArrayDeque instead.

Why is ArrayDeque preferred over LinkedList for queues?

ArrayDeque is a circular buffer: no per-element Node object, contiguous memory, far better cache behaviour, and true O(1) at both ends via index wrapping instead of shifting. LinkedList allocates ~40 bytes per element and scatters them across the heap. The one behavioural difference to remember: ArrayDeque rejects nulls, LinkedList allows them. If you add the internals, be version-specific — Java 8 used a power-of-two array with & (len-1) masking and doubled on growth; Java 9+ dropped that, wraps with explicit inc/dec checks, and grows by oldCapacity + 2 below 64 and 1.5x above.

How does PriorityQueue work, and why does printing it look unsorted?

It is a binary min-heap in an array: parent = (i-1)/2, children at 2i+1 and 2i+2. The only invariant is parent ≤ children, which is weaker than sorted — so toString() and iteration show heap order, not priority order. Only peek and poll honour the ordering. offer/poll are O(log n), peek is O(1), and building from a collection heapifies in O(n).

Find the K largest elements — which heap?

A min-heap of size k. Offer each element, and when the size exceeds k, poll — that removes the smallest, so the heap always holds the k largest seen so far. O(n log k) time and O(k) space, better than sorting the whole input. (K smallest uses a max-heap, symmetrically.)

How do you write an LRU cache?

Extend LinkedHashMap, call super(capacity, 0.75f, true) for access order, and override removeEldestEntry to return size() > capacity. Access order moves every touched entry to the tail, so the head is always the least recently used, and the JDK evicts it for you. The from-scratch variant is a HashMap plus a hand-written doubly linked list for O(1) unlink and move-to-front.

What does LinkedHashMap add over HashMap?

A doubly linked list threaded through all entries (before/after on each Entry), giving predictable iteration order — insertion order by default, or access order with the three-arg constructor. Operations stay O(1); iteration is actually faster than HashMap because it walks the list instead of scanning empty buckets. The cost is two extra references per entry.

How does TreeMap stay balanced?

It is a red-black tree. The rules — root black, no red node with a red child, and every root-to-leaf path containing the same number of black nodes — force the longest path to be at most twice the shortest. That bounds the height at O(log n), so get/put/remove are guaranteed O(log n). Rebalancing is done by recolouring and rotations after each insert or delete.

Why does TreeSet drop elements that are not equal?

Sorted collections decide duplicates with compareTo(x) == 0, never equals. If your comparator only inspects one field, two distinct objects agreeing on it are "the same element" and the second is silently rejected. This is why the docs say the ordering should be consistent with equals — BigDecimal is the famous counter-example.

What is EnumSet and why is it so fast?

A Set specialised for enum constants. With 64 or fewer constants the entire set is a single long, one bit per ordinal (RegularEnumSet); beyond that it is a long[] (JumboEnumSet). So contains/add/remove are single bitwise ops, containsAll is one AND, addAll one OR. It replaces C-style int bit flags with type safety and no performance loss.

What is WeakHashMap for?

Its keys are weak references, so an entry disappears automatically once nothing else in the program refers to its key. Useful for caches and for attaching metadata to objects you do not own. The trap: values are strong references, so if a value points back at its key the entry can never be collected.

Difference between Collections.unmodifiableList and List.copyOf?

unmodifiableList returns a read-only view — writes through the original reference are still visible through it. List.copyOf makes an independent immutable copy that nothing can change. Both are shallow: the elements themselves remain mutable.

What is wrong with Arrays.asList?

Three things. It is fixed size (a view over the array — set works and writes through, add/remove throw). Given an int[] it produces a List<int[]> of size 1, not a list of ints. And it permits nulls, unlike List.of. For a real list: new ArrayList<>(Arrays.asList(...)).

List.of vs Arrays.asList vs new ArrayList?

List.of — fully immutable, no nulls, independent, cheapest. Arrays.asList — fixed size, set allowed, backed by the array, nulls allowed. new ArrayList<>() — fully mutable and growable. Note also that Set.of/Map.of throw on duplicate entries and randomise iteration order per JVM run.

What are sequenced collections?

Java 21, JEP 431. Three interfaces — SequencedCollection, SequencedSet, SequencedMap — giving a uniform getFirst, getLast, addFirst, addLast, removeFirst, removeLast and a reversed() view. Retrofitted onto List, Deque, SortedSet, LinkedHashSet, LinkedHashMap and SortedMap. Before this, getting the last element of a LinkedHashSet required a full traversal.

Best way to iterate a Map, and why?

entrySet() (or forEach). Iterating keySet() and calling get(k) performs a second hash lookup per entry — roughly double the work for the same result.

What do computeIfAbsent and merge give you?

They collapse check-then-act into one call: map.computeIfAbsent(k, x -> new ArrayList<>()).add(v) builds a multi-map, and map.merge(word, 1, Integer::sum) counts occurrences. On a ConcurrentHashMap they are atomic, which the old get-check-put sequence never was. Keep the lambda short and side-effect free — it runs while holding the bin lock, and modifying the same map inside it is forbidden.

Is Collections.synchronizedMap enough for thread safety?

Only per method. Compound actions (check-then-act) still race, and you must manually synchronized around any iteration — the Javadoc requires it. It also serialises readers against each other. ConcurrentHashMap locks per bin, never blocks readers, and offers atomic compound operations.

When is CopyOnWriteArrayList the right choice?

Read-mostly, write-rarely, shared across threads — the classic case is a listener list. Reads are lock-free (the array field is volatile) and iterators work on an immutable snapshot, so they never throw CME. Every write copies the whole array, so writes are O(n) and write-heavy use is quadratic and memory-hungry.

When is a parallel stream actually faster?

When the dataset is large, the per-element work is CPU-bound and non-trivial, the source splits evenly (arrays and ArrayList yes; LinkedList and most Maps no), and the operation is stateless and associative. It uses the shared common ForkJoinPool, so one bad parallel stream degrades the whole JVM — and never use it for blocking I/O. Measure with JMH rather than assuming.

How do you make a collection thread-safe? List every option.
  • A purpose-built concurrent class — ConcurrentHashMap, CopyOnWriteArrayList, ConcurrentLinkedQueue, ConcurrentSkipListMap, ConcurrentHashMap.newKeySet(). Preferred.
  • Collections.synchronizedX(...) — one lock per method, manual locking for iteration and compound actions.
  • Your own synchronized blocks or a ReentrantLock around the access pattern.
  • Immutability — List.copyOf, Map.of. Nothing to synchronize if nothing changes; this is the strongest option when it fits.
  • Confinement — never share it; give each thread its own.
Is Iterator an interface or a class? And what design pattern is it?

An interface, and the Iterator pattern — it decouples traversal from the underlying structure, so the same for-each loop works over an array-backed list and a linked one. The AbstractList/AbstractMap skeletons are the Template Method pattern, and Collections.unmodifiableList/synchronizedList are Decorators.

How would you sort a Map by its values? 
map.entrySet().stream()
   .sorted(Map.Entry.comparingByValue(Comparator.reverseOrder()))
   .collect(Collectors.toMap(Map.Entry::getKey, Map.Entry::getValue,
                             (a, b) -> a, LinkedHashMap::new));

The LinkedHashMap::new supplier is the part people forget — without it the result collects into a HashMap and the sort order you just computed is thrown away.

What is the initial capacity you should pass for n entries?

n / 0.75 + 1, so that the 0.75 load factor never triggers a resize. For 1000 entries that is 1334 (rounded up to 2048 internally). Since Java 19 there is HashMap.newHashMap(n) which does the arithmetic for you. Passing n directly is the common mistake — it still resizes at 0.75n.

30Must-do coding programs

Write each one from scratch, run it, then write it a second way. These cover almost every collections coding round.

Tier 1 — asked constantly

  1. Count word frequency in a sentence — three ways: getOrDefault, merge, and Collectors.groupingBy(w -> w, counting()).
  2. Find the first non-repeating character in a String — a LinkedHashMap<Character,Integer> in one pass, then scan for the first count of 1.
  3. Remove duplicates from a list preserving order — new ArrayList<>(new LinkedHashSet<>(list)), and again with stream().distinct().
  4. Sort a Map by value, descending, collecting into a LinkedHashMap so the order survives.
  5. Find duplicates in an array — a HashSet and the return value of add().
  6. Reverse a list / a map (swap keys and values, handling duplicate values).
  7. Find the second largest element without sorting — one pass, or a TreeSet.
  8. Intersection, union and difference of two lists using retainAll, addAll, removeAll — and explain why converting to a Set first changes it from O(n·m) to O(n+m).

Tier 2 — the implementation round

  1. Implement your own ArrayList — backing array, size vs capacity, 1.5x growth, System.arraycopy for insert and remove, and a fail-fast iterator with modCount.
  2. Implement your own HashMap — bucket array, hash() spread, (n-1) & hash indexing, chaining, resize-and-rehash at 0.75. Getting this right is the single best use of an afternoon.
  3. LRU cache — first with LinkedHashMap + removeEldestEntry, then from scratch with a HashMap plus a hand-written doubly linked list for O(1) get and put.
  4. LFU cache — the harder follow-up: a frequency map plus a map of frequency to a LinkedHashSet.
  5. Implement a Stack and a Queue from an array and from a linked list, with proper empty/full handling.
  6. Custom object in a HashSet — demonstrate the duplicate bug with no hashCode, then fix it; then mutate a key and show the entry becoming unreachable.

Tier 3 — pattern recognition

  1. Two Sum with a HashMap in one pass — the canonical "hash map as a lookup" problem.
  2. Group anagrams — groupingBy on the sorted characters of each word.
  3. Top K frequent elements — frequency map plus a size-k min-heap. Explain why a min-heap gives the k largest.
  4. Sliding window maximum with an ArrayDeque holding indices — the classic monotonic deque.
  5. Balanced parentheses with a Deque as a stack.
  6. Merge K sorted lists with a PriorityQueue of list heads.
  7. Producer–consumer with a bounded BlockingQueue and a poison pill for shutdown.
  8. Thread-safe counter map — ConcurrentHashMap + merge, and show why containsKey-then-put loses updates under load.
How to present any collections program
  1. Name the access pattern first: lookup by key, membership test, ordered scan, both-ends processing.
  2. Name the collection that matches it and the one property that decided it.
  3. State the complexity of your solution, time and space, before you are asked.
  4. Mention the edge cases out loud: empty input, one element, all duplicates, nulls.
  5. If a custom object is a key, say "this needs equals and hashCode" without being prompted.

Point 5 is the one that separates candidates. Interviewers score that reasoning far higher than a fast keyboard.

31Last-night cheat sheet

The numbers

  • ArrayList: default 10, grows 1.5x. Vector: 10, grows 2x.
  • HashMap: capacity 16, load factor 0.75, treeify at 8, untreeify at 6, min table for treeify 64.
  • Hashtable: capacity 11, grows to 2n+1.
  • HashMap capacity is always a power of two. ArrayDeque was too until Java 9 — it is not any more (default 16 + 1, grows by +2 below 64, 1.5x above).
  • To hold n entries without a resize, size the map at n / 0.75 + 1.

Say these exactly right

  • Collection is the interface; Collections is the utility class.
  • Map is not a Collection — it exposes keySet, values, entrySet.
  • Index is (n-1) & hash, not hash % n — that is why capacity is a power of two.
  • hashCode picks the bucket; equals picks the entry.
  • Equal objects must have equal hash codes; equal hash codes need not mean equal objects.
  • HashSet is a HashMap with a dummy PRESENT value.
  • TreeSet decides duplicates with compareTo, never equals.
  • HashMap: one null key. Hashtable and ConcurrentHashMap: no nulls.
  • Fail-fast is best-effort, not a guarantee.
  • Java 8 ConcurrentHashMap locks per bin, not per segment.
  • Access-ordered LinkedHashMap + removeEldestEntry = LRU.
  • K largest uses a min-heap of size k.
  • PriorityQueue is ordered at the head only — printing it is not sorted.
  • Arrays.asList is fixed size; List.of is immutable; unmodifiableList is a live view.
  • Object sort is stable (TimSort); primitive sort is not (dual-pivot quicksort).
  • Java 21 gave every ordered collection getFirst, getLast and reversed().

Never say these

  • "HashMap is O(1) always" — average O(1), worst case O(log n) since Java 8.
  • "Use Vector or Hashtable for thread safety" — one global lock; use the concurrent classes.
  • "Vector is thread-safe so my code is safe" — compound actions still race.
  • "LinkedList is faster for insertion" — only if you are already positioned there.
  • "ConcurrentHashMap uses 16 segments" — that was Java 7.
  • "HashSet keeps insertion order" — that is LinkedHashSet.
  • "unmodifiableList makes an immutable copy" — it makes a view.
  • "parallelStream is always faster" — it is often slower, and it shares one JVM-wide pool.
  • "I only need equals, not hashCode" — for anything going into a hash collection, never.
