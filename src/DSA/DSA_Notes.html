00Big-O & complexity

Big-O answers one question: as the input grows, how does the work grow? It ignores the machine, the language and the constants, and keeps only the shape of the curve. Every interview solution ends with "and the complexity is…", so this is chapter zero.

Core concept

O(f(n)) is an upper bound on growth: for large enough n, the running time is at most a constant times f(n). Two rules do almost all the work:

  • Drop constants — O(2n) is O(n). Two passes over an array is still linear.
  • Keep the dominant term — O(n² + n log n + 100) is O(n²).

Ω is a lower bound, Θ is a tight bound. Interviewers say "Big-O" but almost always mean Θ of the worst case.

Pattern cue — read the constraints backwards

A judge does roughly 108 simple operations per second. The constraint tells you the intended complexity before you read the problem:

  • n ≤ 12 → O(n!)  ·  n ≤ 25 → O(2n)  ·  n ≤ 500 → O(n³)
  • n ≤ 5 000 → O(n²)  ·  n ≤ 105–106 → O(n) or O(n log n)
  • n ≤ 109 or more → O(log n) or O(1) — binary search or maths.

Counting loops

for (int i = 0; i < n; i++)            // n
    for (int j = i; j < n; j++)        // n + (n-1) + ... + 1 = n(n+1)/2  -> O(n^2)
        work();

for (int i = 1; i < n; i *= 2)         // i doubles -> log n iterations
    work();

for (int i = 0; i < n; i++)            // looks nested, but j never resets:
    while (j < n && ok(j)) j++;        // j moves n times IN TOTAL -> O(n)
Under the hood — amortized cost

ArrayList.add is usually O(1) but occasionally O(n) when it resizes. Doubling means n appends cost 1 + 2 + 4 + … + n < 2n copies in total — O(1) amortized per append. Same argument: every element is pushed and popped at most once in a monotonic stack, so the inner while loop is O(n) overall, not O(n²).

Common pitfall
  • Hidden loops: s.substring(), list.contains(), list.remove(0), string += in a loop are each O(n). Inside a loop they make O(n²).
  • Forgetting recursion space: a recursive DFS uses O(depth) stack even if you allocate nothing.
  • Two different inputs need two letters: merging lists of size n and m is O(n + m), not O(n).
  • HashMap is O(1) average; say "average" out loud.
Asked — "What is the space complexity?"

Count extra memory only (not the input): auxiliary arrays/maps + the deepest recursion stack. Say whether the output counts. "O(n) time, O(1) extra space" is the sentence that closes every answer.

01Recursion & call stack

Recursion is a function solving a problem by trusting itself on a smaller version of the same problem. Trees, backtracking, divide & conquer and top-down DP are all this one idea.

Core concept

Every recursive function has exactly three parts:

  1. Base case — the smallest input, answered directly. Without it: StackOverflowError.
  2. Recursive case — call yourself on a strictly smaller input.
  3. Combine — build this level's answer from the smaller answer.

The leap of faith: assume f(n-1) already works. Only write how to go from that to f(n). Do not trace the whole tree in your head.

int fact(int n) {
    if (n <= 1) return 1;          // base case
    return n * fact(n - 1);        // smaller input + combine
}

// fast power: halve the exponent -> O(log n) calls
double pow(double x, long n) {
    if (n == 0) return 1;
    if (n < 0)  return 1 / pow(x, -n);
    double half = pow(x, n / 2);   // compute ONCE, reuse
    return (n % 2 == 0) ? half * half : half * half * x;
}
Under the hood — the call stack

Each call pushes a stack frame (parameters, locals, return address). fact(4) stacks up 4 → 3 → 2 → 1, then unwinds multiplying on the way back. Work before the recursive call happens on the way down; work after it happens on the way back up — that is how you print a list in reverse with no extra memory. Java's default stack handles roughly 10–20k frames; a linked list of 105 nodes recursed naively will overflow.

Pattern cue
  • The structure is defined in terms of itself (tree = node + two trees, list = node + list) → recurse.
  • "All combinations / all paths" → recursion with choices (backtracking, ch. 20).
  • Time ≈ number of calls × work per call. Space ≈ max depth.
  • Same sub-call repeated? Add a memo — that is top-down DP (ch. 22).
Common pitfall
  • Base case that is never reached (n == 0 but you step by 2 from an odd n).
  • Calling pow(x, n/2) * pow(x, n/2) — two calls turn O(log n) back into O(n).
  • Naive fib(n) is O(2n): the same subproblems are recomputed exponentially often.
  • Mutating a shared list and forgetting to undo it when the call returns.
Asked — "Recursion vs iteration?"

Same power. Recursion is clearer for trees and branching; iteration avoids stack overflow and frame overhead. Any recursion can be made iterative with an explicit stack. Java does not do tail-call optimisation.

02Recurrences & Master Theorem

A recursive algorithm's running time is itself a recursive formula — a recurrence. Solving it is how you justify "merge sort is O(n log n)" instead of reciting it.

Core concept — Master Theorem

For T(n) = a·T(n/b) + O(nd) — a subproblems, each of size n/b, plus nd work to split/combine — compare d with logba:

  • d > logba → O(nd) — the root dominates.
  • d = logba → O(nd log n) — every level costs the same.
  • d < logba → O(nlogba) — the leaves dominate.
AlgorithmRecurrencea, b, dResult
Binary searchT(n)=T(n/2)+O(1)1, 2, 0O(log n)
Merge sortT(n)=2T(n/2)+O(n)2, 2, 1O(n log n)
Tree traversalT(n)=2T(n/2)+O(1)2, 2, 0O(n)
Quickselect (avg)T(n)=T(n/2)+O(n)1, 2, 1O(n)
Karatsuba multiplyT(n)=3T(n/2)+O(n)3, 2, 1O(n1.585)
StrassenT(n)=7T(n/2)+O(n²)7, 2, 2O(n2.81)

When the theorem does not apply: the recursion tree

T(n) = 2T(n/2) + n            level   nodes   work per level
            n                   0       1        n
        n/2   n/2               1       2        n
      n/4 n/4 n/4 n/4           2       4        n
        ...                    log n    n        n
                              total = n * (log n + 1)  ->  O(n log n)

Subtract-style recurrences are not Master-Theorem shaped — unroll them:

  • T(n) = T(n-1) + O(1) → O(n)  (factorial, list recursion)
  • T(n) = T(n-1) + O(n) → O(n²)  (quick sort worst case, selection sort)
  • T(n) = 2T(n-1) + O(1) → O(2n)  (Hanoi, subsets)
  • T(n) = T(n-1) + T(n-2) → O(φn) ≈ O(1.618n)  (naive Fibonacci)
Pattern cue

Write the recurrence straight from the code: how many recursive calls (a), on what size (n/b or n−1), plus what loop work outside the calls. Then pick Master Theorem (divide) or unrolling (subtract).

Common pitfall
  • Counting the Arrays.copyOfRange / substring inside the call as O(1). It is O(n) and changes d.
  • Quick sort is O(n log n) only when splits are balanced; sorted input + first-element pivot gives T(n)=T(n-1)+n = O(n²).
  • Memoized recursion is not analysed by recurrence: it is (number of distinct states) × (work per state).
Asked — "Why is merge sort n log n?"

"The array is halved log n times; each level of the recursion tree merges a total of n elements. log n levels × n work = n log n. Formally T(n)=2T(n/2)+n, Master Theorem case 2."

03Integer gotchas

Your algorithm can be perfect and still fail because a number silently wrapped around. These are the bugs that pass the sample test and fail test 47.

Core concept
  • int = 32-bit, range ±2.147×109 (Integer.MAX_VALUE = 231−1). long = 64-bit, ±9.2×1018.
  • Overflow is silent in Java: MAX_VALUE + 1 == MIN_VALUE. No exception.
  • Division truncates toward zero: -7 / 2 == -3; remainder keeps the dividend's sign: -7 % 2 == -1.
int mid = (lo + hi) / 2;              // BUG: lo + hi can overflow
int mid = lo + (hi - lo) / 2;         // correct

long area = (long) w * h;             // cast BEFORE multiplying
long bad  = w * h;                    // int * int overflows first, THEN widens

// reverse an int with overflow check BEFORE the multiply
if (rev > Integer.MAX_VALUE / 10 || rev < Integer.MIN_VALUE / 10) return 0;
rev = rev * 10 + x % 10;

int idx = ((k % n) + n) % n;          // always-non-negative modulo
final int MOD = 1_000_000_007;
long r = (a % MOD) * (b % MOD) % MOD;  // mod after every multiply, in long
Common pitfall
  • Math.abs(Integer.MIN_VALUE) is still negative — there is no +231 in int.
  • Comparator (a, b) -> a - b overflows for large/negative values. Use Integer.compare(a, b).
  • Integer a = 128, b = 128; a == b is false — cache covers only −128..127. Use .equals(). This bites with map.get(x) == map.get(y).
  • 1 << 31 is negative; 1 << 32 is 1 (shift count is mod 32). Use 1L << k.
  • char arithmetic gives int: 'a' + 1 is 98; cast back with (char).
  • Doubles: never ==; compare with an epsilon. 0.1 + 0.2 != 0.3.
Pattern cue

The moment you see sum, product, "answer modulo 109+7", values up to 109, or a prefix sum — declare the accumulator long. It costs nothing and removes the whole class of bug.

Asked — "How do you detect overflow without long?"

Check before the operation: for a * 10 + d, test a > (MAX - d) / 10. Or use Math.addExact / Math.multiplyExact, which throw ArithmeticException.

04Hashing deep dive

Hashing turns "search for it" into "compute where it is". It is the single most common way to delete a nested loop.

Core concept

A hash function maps a key to a bucket index; equal keys must hash equally. Lookup, insert and delete are O(1) average, O(n) worst case when everything collides. In Java: HashMap (key→value), HashSet (membership), and for small fixed alphabets a plain int[26] / int[128] — faster and simpler than any map.

Under the hood — Java's HashMap

Array of buckets (default 16, always a power of two). Index = (h ^ (h >>> 16)) & (n-1). Collisions chain in a linked list; a chain longer than 8 becomes a red-black tree (O(log n) worst case). At load factor 0.75 the table doubles and rehashes. Full detail is in the Collection Framework notes, section 15.

// frequency count - the idiom you will type 100 times
Map<Character, Integer> freq = new HashMap<>();
for (char c : s.toCharArray()) freq.merge(c, 1, Integer::sum);

// group by a computed key
Map<String, List<String>> groups = new HashMap<>();
for (String w : words) {
    char[] a = w.toCharArray(); Arrays.sort(a);
    groups.computeIfAbsent(new String(a), k -> new ArrayList<>()).add(w);
}

// "have I seen the complement?" - Two Sum in one pass
Map<Integer, Integer> seen = new HashMap<>();      // value -> index
for (int i = 0; i < nums.length; i++) {
    Integer j = seen.get(target - nums[i]);
    if (j != null) return new int[]{j, i};
    seen.put(nums[i], i);                           // put AFTER the check
}
Pattern cue
  • "Find a pair / have I seen this before / count occurrences / first duplicate" → map or set.
  • "Group things that are equivalent" → design a canonical key (sorted string, count signature, slope, row pattern).
  • "Subarray with sum k" → prefix sum + map (ch. 08).
  • Need order too? LinkedHashMap (insertion) or TreeMap (sorted, O(log n)).
Common pitfall
  • Using an array as a key: int[] hashes by identity. Use List<Integer>, a String, or Arrays.toString(a).
  • Mutating a key object after inserting it — the entry becomes unreachable.
  • Own class as key without overriding both equals and hashCode.
  • map.get(k) returns null when absent → unboxing NPE. Use getOrDefault.
  • Removing while iterating → ConcurrentModificationException; use the iterator's remove or removeIf.
Asked — "HashMap vs TreeMap vs array?"

HashMap: O(1) average, no order. TreeMap: O(log n), sorted keys plus floorKey/ceilingKey. Array: when keys are a small dense range (letters, digits, 0..n) — no hashing, no boxing, cache friendly.

05String fundamentals

A string problem is an array problem with two extra traps: strings are immutable, and characters are secretly numbers.

Core concept
  • String is immutable — every "change" allocates a new object. Build with StringBuilder.
  • charAt(i) is O(1); substring, concat, equals, indexOf, contains are O(n).
  • A char is a 16-bit number: c - 'a' gives 0..25, c - '0' gives the digit value.
// O(n^2): every += copies the whole string so far
String s = ""; for (String w : words) s += w;

// O(n)
StringBuilder sb = new StringBuilder();
for (String w : words) sb.append(w);
sb.reverse(); sb.setLength(sb.length() - 1); sb.deleteCharAt(0); sb.insert(0, 'x'); // insert/delete at front are O(n)

int[] cnt = new int[26];
for (char c : s.toCharArray()) cnt[c - 'a']++;

Character.isLetterOrDigit(c); Character.toLowerCase(c); Character.isDigit(c);
String.valueOf(chars); s.split("\\s+"); String.join(" ", parts); s.trim(); s.compareTo(t);

Palindromes — expand around the centre

int expand(String s, int l, int r) {              // returns the palindrome length
    while (l >= 0 && r < s.length() && s.charAt(l) == s.charAt(r)) { l--; r++; }
    return r - l - 1;
}
// for each i: expand(s,i,i) odd length, expand(s,i,i+1) even length -> O(n^2), O(1) space
Pattern cue
  • Anagram / permutation / "same letters" → int[26] count.
  • Palindrome → two pointers from the ends, or expand from centres.
  • Substring with a property → sliding window (ch. 10).
  • Many words, prefix queries → trie (ch. 17). Pattern search → KMP / rolling hash (ch. 26).
  • Parsing nested structure (3[a2[c]]) → stack.
Common pitfall
  • s1 == s2 compares references. Always .equals().
  • sb.append(a + b) with two chars appends their numeric sum.
  • s.split(" ") keeps empty strings for repeated spaces; split("\\s+") after trim() does not.
  • Calling substring inside a loop just to compare — compare indices instead.
  • Assuming lowercase a–z: ask. If it may be any ASCII use int[128]; Unicode → map.
Asked — "Why is String immutable?"

Safe sharing in the string pool, safe as a HashMap key (hash is cached), thread-safe without locks, and security (paths, class names cannot change after validation). StringBuilder = mutable, not synchronized; StringBuffer = synchronized, legacy.

06Comparators & ordering

Half of "medium" problems become easy once the data is sorted the right way. The comparator is how you tell Java what "right" means — for sorting, for heaps and for TreeMaps.

Core concept

compare(a, b) returns negative if a comes first, positive if b comes first, zero if tied. Comparable = the class's one natural order (compareTo). Comparator = an external, swappable order. It must be consistent: transitive, and sgn(compare(a,b)) == -sgn(compare(b,a)).

Arrays.sort(intervals, (a, b) -> Integer.compare(a[0], b[0]));       // by start

// multi-key: score desc, then name asc
people.sort(Comparator.comparingInt((Person p) -> p.score).reversed()
                      .thenComparing(p -> p.name));

PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Comparator.reverseOrder());
PriorityQueue<int[]> byDist  = new PriorityQueue<>((a, b) -> Integer.compare(a[1], b[1]));

// Largest Number: order by which concatenation is bigger
Arrays.sort(strs, (x, y) -> (y + x).compareTo(x + y));

// primitives cannot take a comparator: box, or sort asc and read backwards
Integer[] boxed = Arrays.stream(nums).boxed().toArray(Integer[]::new);
Arrays.sort(boxed, Collections.reverseOrder());
Under the hood

Arrays.sort(int[]) is dual-pivot quicksort — not stable, O(n log n) average. Arrays.sort(Object[]) and Collections.sort are TimSort — stable, O(n log n) worst, O(n) on nearly-sorted data. Stability is what makes "sort by name, then sort by score" keep names ordered inside equal scores.

Common pitfall
  • (a, b) -> a - b overflows; (a, b) -> a[0] - b[0] too when values reach ±109. Use Integer.compare.
  • Returning only 1 or -1 and never 0 → "Comparison method violates its general contract!".
  • Changing a field that the heap/TreeMap ordered by, while the object is still inside — the structure is now corrupt. Remove, change, re-insert.
  • TreeSet/TreeMap treat compare == 0 as the same key — two different objects with equal sort keys collapse into one. Add a tiebreaker.
Pattern cue

Ask "if this were sorted by X, would the answer be a single pass?" Intervals → by start (merge) or by end (max non-overlapping). Meetings, deadlines, weights/ratios, custom concatenation — all comparator problems wearing a costume.

Asked — "Comparable vs Comparator?"

Comparable: inside the class, one order, compareTo(o), java.lang. Comparator: outside the class, many orders, compare(a,b), java.util, works on classes you cannot edit.

07Arrays & hashing patterns

The array is contiguous memory with O(1) index access. Nearly every array problem is one of a handful of moves: count, index-as-key, precompute from both sides, or overwrite in place.

Core concept
OperationArray / ArrayList
Read / write index iO(1)
Append at endO(1) amortized
Insert / delete in the middle or frontO(n) — shifting
Search unsorted / sortedO(n) / O(log n)

The brute force is almost always two nested loops. The fix is almost always: remember something in a map/set, or precompute an array so the inner loop becomes a lookup.

// Product of array except self - left pass then right pass, no division
int[] res = new int[n];
res[0] = 1;
for (int i = 1; i < n; i++) res[i] = res[i - 1] * nums[i - 1];   // product of everything LEFT of i
int right = 1;
for (int i = n - 1; i >= 0; i--) { res[i] *= right; right *= nums[i]; }

// Top K frequent - bucket sort by frequency, O(n)
List<Integer>[] bucket = new List[n + 1];            // index = frequency
freq.forEach((num, f) -> {
    if (bucket[f] == null) bucket[f] = new ArrayList<>();
    bucket[f].add(num);
});                                                  // then walk from n down to 1

// Kadane - best subarray ending here
int cur = nums[0], best = nums[0];
for (int i = 1; i < n; i++) { cur = Math.max(nums[i], cur + nums[i]); best = Math.max(best, cur); }
Pattern cue
  • Values are in 1..n → use the array itself as a hash: negate nums[|x|-1], or cyclic-sort x into slot x−1. O(1) space.
  • "Except self" / "to the left and right of i" → prefix array + suffix array.
  • In-place removal / dedupe → slow write pointer, fast read pointer.
  • Rotate by k → reverse all, reverse first k, reverse the rest.
  • Majority element → Boyer–Moore voting: O(n) time, O(1) space.
Common pitfall
  • Off-by-one at the ends: check i-1, i+1, empty array and single element before submitting.
  • Arrays.asList(int[]) gives a List<int[]> with one element.
  • int[] b = a copies the reference. Use a.clone() / Arrays.copyOf.
  • k larger than n in rotation — always k %= n.
Asked — "Can you do it without extra space?"

The follow-up to every map solution. Options: sort first (O(1) space, O(n log n) time), index-as-hash when values are bounded by n, XOR tricks, or Boyer–Moore.

08Prefix sums

Pay O(n) once, then answer any range-sum question in O(1). Combined with a hash map it counts subarrays — even with negative numbers, where sliding window fails.

Core concept

pre[i] = sum of the first i elements, with pre[0] = 0. Then sum(l..r) = pre[r+1] − pre[l]. The extra leading zero removes every special case at the left edge.

long[] pre = new long[n + 1];
for (int i = 0; i < n; i++) pre[i + 1] = pre[i] + nums[i];
long sum = pre[r + 1] - pre[l];                       // inclusive l..r

// Subarray Sum Equals K: count pairs with pre[j] - pre[i] == k
Map<Long, Integer> count = new HashMap<>();
count.put(0L, 1);                                     // the empty prefix - DO NOT forget
long run = 0; int ans = 0;
for (int x : nums) {
    run += x;
    ans += count.getOrDefault(run - k, 0);           // look up BEFORE inserting
    count.merge(run, 1, Integer::sum);
}

// 2-D prefix: inclusion - exclusion
P[r+1][c+1] = g[r][c] + P[r][c+1] + P[r+1][c] - P[r][c];
sum(r1,c1,r2,c2) = P[r2+1][c2+1] - P[r1][c2+1] - P[r2+1][c1] + P[r1][c1];

// Difference array: many range updates, read once
diff[l] += v; diff[r + 1] -= v;                        // O(1) per update; prefix-sum diff at the end
Pattern cue
  • "Sum of a range", many queries → prefix array.
  • "Number of subarrays with sum = k / divisible by k" → running sum + map of counts (key = sum, or sum mod k).
  • "Longest subarray with …" → map of first index each running value appeared.
  • "Equal number of 0s and 1s" → treat 0 as −1; the question becomes sum = 0.
  • "Add v to every element in [l, r]", many times → difference array.
Common pitfall
  • Forgetting count.put(0, 1) (or first.put(0, -1)) — subarrays starting at index 0 vanish.
  • Inserting the running sum before the lookup — with k = 0 you count the empty subarray.
  • Negative remainders: ((run % k) + k) % k.
  • Sliding window instead of prefix+map when numbers can be negative — the window is no longer monotonic.
  • int overflow in the running sum — use long.
Asked — "What if the array is updated between queries?"

Prefix sums need O(n) per update. Use a Fenwick tree (BIT) or segment tree: O(log n) update and O(log n) query.

09Two pointers

Two indices that move with a rule, so that every step throws away candidates you provably do not need. It turns O(n²) pair searches into O(n).

Core concept — three flavours
  • Opposite ends — l = 0, r = n-1, move inward. Needs sorted data or symmetry (pair sum, palindrome, container).
  • Same direction (slow / fast) — fast reads, slow writes. In-place filter, dedupe, partition.
  • Two sequences — one pointer per array. Merge, intersection, subsequence check.
// pair sum on a SORTED array

10Sliding window

A window is a contiguous range [left, right] whose summary you update in O(1) as it slides, instead of recomputing it from scratch. Every element enters once and leaves once → O(n).

Core concept
  • Fixed size k — add the new right element, drop the one that fell off the left.
  • Variable size — expand right every step; while the window is invalid, shrink from left. Longest-type answers are recorded after shrinking; shortest-type answers are recorded inside the shrink loop while the window is still valid.
// LONGEST valid window - Longest Substring Without Repeating Characters
int[] cnt = new int[128];
int left = 0, best = 0;
for (int right = 0; right < s.length(); right++) {
    cnt[s.charAt(right)]++;                               // 1. expand
    while (cnt[s.charAt(right)] > 1)                      // 2. shrink while invalid
        cnt[s.charAt(left++)]--;
    best = Math.max(best, right - left + 1);              // 3. record
}

// SHORTEST valid window - Minimum Size Subarray Sum (positives only)
int sum = 0, min = Integer.MAX_VALUE;
for (int right = 0, l = 0; right < n; right++) {
    sum += a[right];
    while (sum >= target) {                               // valid -> record, then try smaller
        min = Math.min(min, right - l + 1);
        sum -= a[l++];
    }
}

// Minimum Window Substring: need[] counts + "missing" counter
int[] need = new int[128]; for (char c : t.toCharArray()) need[c]++;
int missing = t.length();
// expand: if (need[c]-- > 0) missing--;   shrink while missing == 0: if (++need[leftChar] > 0) missing++;
Pattern cue

"Contiguous subarray / substring" + "longest / shortest / count" + a condition that is monotonic (growing the window can only break it, shrinking can only fix it). "At most K distinct", "no repeats", "sum ≥ target with positives", "contains all characters of t".

Exactly K = atMost(K) − atMost(K−1).

Common pitfall
  • Negative numbers break sum-based windows — use prefix sum + map (ch. 08).
  • if instead of while for the shrink step.
  • Window length is right - left + 1, not right - left.
  • Comparing two 26-count arrays each step is fine (O(26)), but comparing two maps with Integer == is a bug.
  • Subsequence problems are not window problems — a window is contiguous.
Asked — "Why is this O(n) with a nested while?"

Amortized: left only moves forward and at most n times over the entire run. Total pointer moves ≤ 2n.

11Queue & Deque

A queue processes things in arrival order (FIFO). A deque is open at both ends — which makes it a queue, a stack and the engine of the sliding-window-maximum trick.

Core concept

In Java, use ArrayDeque for both: a circular array, O(1) at both ends, no per-node allocation, faster than LinkedList and much faster than the legacy synchronized Stack. It rejects null — use LinkedList only when a BFS must enqueue nulls.

// BFS skeleton - level by level
Deque<TreeNode> q = new ArrayDeque<>();
q.offer(root);
while (!q.isEmpty()) {
    int size = q.size();                       // freeze: exactly this level
    for (int i = 0; i < size; i++) {
        TreeNode n = q.poll();
        if (n.left != null)  q.offer(n.left);
        if (n.right != null) q.offer(n.right);
    }
}

// Sliding Window Maximum - deque of INDICES, values decreasing front -> back
Deque<Integer> dq = new ArrayDeque<>();
for (int i = 0; i < n; i++) {
    if (!dq.isEmpty() && dq.peekFirst() <= i - k) dq.pollFirst();       // fell out of the window
    while (!dq.isEmpty() && a[dq.peekLast()] <= a[i]) dq.pollLast();   // can never be max again
    dq.offerLast(i);
    if (i >= k - 1) res[i - k + 1] = a[dq.peekFirst()];               // front = max
}
Pattern cue
  • "Level by level", "minimum number of steps", "spreads each minute" → BFS with a queue.
  • "Max / min of every window of size k" → monotonic deque.
  • "Last N events / hits in the last 5 minutes" → queue, evict expired from the front.
  • Queue from two stacks: push to in; when out is empty, pour in into out. Amortized O(1).
Common pitfall
  • Reading q.size() in the loop condition while adding to q — store it first.
  • Storing values in the monotonic deque — you cannot tell when they expire. Store indices.
  • Mixing push (front) and offer (back) on the same deque by accident.
  • list.remove(0) on an ArrayList as a "queue" is O(n) per pop.
Asked — "Implement a circular queue"

Fixed array, head, size. Tail index = (head + size) % cap. Dequeue: head = (head + 1) % cap; size--. Keeping size avoids the full-vs-empty ambiguity.

12Stack & monotonic stack

A stack remembers "what am I still waiting to resolve?" — the most recent unfinished thing is resolved first. The monotonic stack turns that into an O(n) answer for every "next greater / smaller element" question.

Core concept

LIFO, O(1) push/pop/peek. Use Deque<T> st = new ArrayDeque<>(). A monotonic stack keeps its contents sorted by popping everything that violates the order before each push. The moment an element is popped is the moment you have found its answer (the element causing the pop is its "next greater/smaller").

    else if (c == '{') st.push('}');
    else if (st.isEmpty() || st.pop() != c) return false;
}
return st.isEmpty();

13Binary search

Binary search is not "find x in a sorted array". It is: given a yes/no question whose answers look like F F F F T T T T, find the boundary in O(log n). The array version is just one instance.

Core concept

Each step discards half of the search space, so n → 1 takes log2n steps (109 → 30 steps). Requirement: a monotonic predicate. Learn one template and never improvise the boundaries.

// TEMPLATE A - exact match
int lo = 0, hi = n - 1;
while (lo <= hi) {
    int mid = lo + (hi - lo) / 2;
    if (a[mid] == target) return mid;
    if (a[mid] < target) lo = mid + 1; else hi = mid - 1;
}
return -1;

// TEMPLATE B - first index where ok(mid) is true  (lower bound)
int lo = 0, hi = n;                       // hi = n means "no such index"
while (lo < hi) {
    int mid = lo + (hi - lo) / 2;
    if (ok(mid)) hi = mid;                // mid might be the answer - keep it
    else lo = mid + 1;                    // mid is definitely not
}
return lo;                                // first a[i] >= target when ok = a[mid] >= target

// BINARY SEARCH ON THE ANSWER - Koko Eating Bananas
int lo = 1, hi = max(piles);
while (lo < hi) {
    int speed = lo + (hi - lo) / 2;
    long hours = 0;
    for (int p : piles) hours += (p + speed - 1) / speed;    // ceil division
    if (hours <= h) hi = speed; else lo = speed + 1;
}
Pattern cue
  • "Sorted" / "rotated sorted" / "O(log n) required".
  • "Minimum capacity / speed / days such that…" or "maximise the minimum…" → binary search on the answer: guess a value, write a greedy O(n) feasible(x).
  • Rotated array: one half of [lo..mid..hi] is always properly sorted — test whether the target lies inside that half.
  • Java built-ins: Arrays.binarySearch returns -(insertionPoint) - 1 when absent; TreeMap.floorKey / ceilingKey.
Common pitfall
  • (lo + hi) / 2 overflows.
  • Infinite loop: with lo = mid you must round mid up: lo + (hi - lo + 1) / 2.
  • Mixing templates: lo <= hi pairs with hi = mid - 1; lo < hi pairs with hi = mid.
  • Rotated array with duplicates: when a[lo] == a[mid] == a[hi] you cannot decide — shrink both ends; worst case O(n).
  • Wrong answer range: hi must be a value that is definitely feasible.
Asked — "First and last position of target?"

Two lower-bound searches: first = lowerBound(target), last = lowerBound(target + 1) - 1. Check first < n && a[first] == target.

void mergeSort(int[] a, int lo, int hi, int[] tmp) {
    if (lo >= hi) return;
    int mid = lo + (hi - lo) / 2;
    mergeSort(a, lo, mid, tmp);
    mergeSort(a, mid + 1, hi, tmp);
    int i = lo, j = mid + 1, k = lo;
    while (i <= mid && j <= hi) tmp[k++] = (a[i] <= a[j]) ? a[i++] : a[j++];   // <= keeps it stable
    while (i <= mid) tmp[k++] = a[i++];
    while (j <= hi)  tmp[k++] = a[j++];
    System.arraycopy(tmp, lo, a, lo, hi - lo + 1);
}

void quickSort(int[] a, int lo, int hi) {
    if (lo >= hi) return;
    int r = lo + rnd.nextInt(hi - lo + 1); swap(a, r, hi);     // random pivot kills the n^2 case
    int p = lo;
    for (int i = lo; i < hi; i++) if (a[i] < a[hi]) swap(a, i, p++);   // Lomuto partition
    swap(a, p, hi);
    quickSort(a, lo, p - 1); quickSort(a, p + 1, hi);
}

Three tools solve nearly everything: the dummy head, slow / fast pointers, and in-place reversal.

// 1. reverse - three pointers
ListNode prev = null, cur = head;
while (cur != null) {
    ListNode next = cur.next;     // save before you break the link
    cur.next = prev;
    prev = cur;
    cur = next;
}
return prev;

// 2. middle + cycle - slow / fast (Floyd)
ListNode slow = head, fast = head;
while (fast != null && fast.next != null) {
    slow = slow.next; fast = fast.next.next;
    if (slow == fast) { /* cycle */ }
}                                  // no cycle: slow is the middle (2nd middle when even)

// 3. dummy head - the head stops being a special case
ListNode dummy = new ListNode(0), tail = dummy;
while (a != null && b != null) {
    if (a.val <= b.val) { tail.next = a; a = a.next; }
    else                { tail.next = b; b = b.next; }
    tail = tail.next;
}
tail.next = (a != null) ? a : b;
return dummy.next;
Under the hood — why Floyd finds the cycle start

Let the tail before the cycle have length a, and the meeting point be b into the cycle of length c. Fast travelled twice as far: 2(a+b) = a+b+kc → a = kc − b. So a pointer from the head and a pointer from the meeting point, both moving one step, meet exactly at the cycle entrance. Find the Duplicate Number is the same algorithm with i → nums[i] as the "next" pointer.

Pattern cue
  • "N-th from the end" → advance fast n steps, then move both.
  • "Palindrome list" / "reorder L0→Ln→L1→Ln-1" → find middle, reverse second half, merge/compare.
  • Head might change (delete, merge, partition) → dummy node.
  • "O(1) get and put with eviction order" → HashMap + doubly linked list (LRU).
Common pitfall
  • Overwriting cur.next before saving it — the rest of the list is gone.
  • fast.next.next without checking fast != null && fast.next != null → NPE.
  • Forgetting to terminate: after splitting or reordering, set the last node's next = null or you create a cycle.
  • Returning head instead of dummy.next when the head was removed.
  • Draw it. Four boxes and arrows on paper beats ten minutes of mental pointer juggling.

16Trees & BSTs

A tree is the most natural recursive structure: a node plus smaller trees. Almost every tree problem is "ask my children, combine, tell my parent".

Core concept
  • Height h: log n when balanced, n when skewed. Recursion space is O(h).
  • DFS orders: pre (node, L, R) · in (L, node, R) · post (L, R, node). BFS = level order with a queue.
  • BST: everything in the left subtree < node < everything in the right subtree. In-order traversal of a BST is sorted. Search/insert/delete are O(h).
// bottom-up (post-order): children report, I combine
int best = 0;
int height(TreeNode n) {                         // Diameter of Binary Tree
    if (n == null) return 0;
    int l = height(n.left), r = height(n.right);
    best = Math.max(best, l + r);                // answer THROUGH me (global)
    return 1 + Math.max(l, r);                  // what I report UP (one branch only)
}

// top-down: parent passes constraints down - Validate BST
boolean valid(TreeNode n, long lo, long hi) {
    if (n == null) return true;
    if (n.val <= lo || n.val >= hi) return false;
    return valid(n.left, lo, n.val) && valid(n.right, n.val, hi);
}                                                // call with Long.MIN_VALUE, Long.MAX_VALUE

// iterative in-order - Kth smallest, BST iterator
Deque<TreeNode> st = new ArrayDeque<>();
TreeNode cur = root;
while (cur != null || !st.isEmpty()) {
    while (cur != null) { st.push(cur); cur = cur.left; }
    cur = st.pop();
    // visit cur
    cur = cur.right;
}

// LCA in a binary tree
TreeNode lca(TreeNode n, TreeNode p, TreeNode q) {
    if (n == null || n == p || n == q) return n;
    TreeNode l = lca(n.left, p, q), r = lca(n.right, p, q);
    if (l != null && r != null) return n;      // p and q split here
    return l != null ? l : r;
}
Pattern cue
  • Height, diameter, balanced, max path sum → post-order, return one value up and update a global.
  • Path from root with constraints, "good nodes", bounds → pre-order, pass state down as parameters.
  • Level order, right side view, zigzag, min depth → BFS with frozen level size.
  • Anything "sorted / k-th / range / predecessor" in a BST → in-order, or use BST property to go one side only (O(h)).
  • Build tree from traversals → preorder gives the root, inorder index splits left/right (use a map for the index).
Common pitfall
  • Validating a BST by checking only left.val < node.val < right.val — wrong. The constraint covers the whole subtree; pass bounds.
  • Using int bounds when node values can be Integer.MIN_VALUE — use long or null.
  • Confusing "value to return to the parent" with "answer to the problem" (diameter, max path sum).
  • Min depth: a node with one child is not a leaf — do not take min(0, x).
  • Skewed tree of 105 nodes → recursion overflow; mention the iterative version.
Asked — "What does a balanced BST give you?"

Guaranteed O(log n) insert/search/delete plus ordered operations (floor, ceiling, range, k-th). Java's TreeMap/TreeSet are red-black trees. A plain BST fed sorted input degenerates into a linked list — O(n).

17Tries

A trie (prefix tree) stores words letter by letter along paths from the root, so words with a common prefix share nodes. Lookup cost depends on the word length, not on how many words are stored.

Core concept

Each node has up to 26 children and an isEnd flag. Insert, search and startsWith are all O(L). Space is O(total characters) in the worst case. A HashSet can answer "is this word present?" but cannot answer "does any word start with this prefix?" without scanning everything.

class Trie {
    private static class Node { Node[] next = new Node[26]; boolean end; }
    private final Node root = new Node();

    public void insert(String w) {
        Node n = root;
        for (char c : w.toCharArray()) {
            int i = c - 'a';
            if (n.next[i] == null) n.next[i] = new Node();
            n = n.next[i];
        }
        n.end = true;
    }
    private Node walk(String s) {
        Node n = root;
        for (char c : s.toCharArray()) { n = n.next[c - 'a']; if (n == null) return null; }
        return n;
    }
    public boolean search(String w)     { Node n = walk(w); return n != null && n.end; }
    public boolean startsWith(String p) { return walk(p) != null; }
}
Pattern cue
  • Autocomplete, "starts with", dictionary of many words, search suggestions.
  • Wildcard . search → DFS over all children at that position.
  • Many words on a board (Word Search II) → walk the trie and the grid together; one DFS serves every word, and dead prefixes are pruned immediately.
  • Maximum XOR of two numbers → binary trie, greedily take the opposite bit from the top.
Common pitfall
  • Forgetting isEnd: after inserting "apple", search("app") must be false while startsWith("app") is true.
  • Assuming lowercase only — otherwise use Map<Character, Node> children.
  • Word Search II: store the whole word at the end node and null it after collecting (dedupe), and prune leaf nodes that are exhausted — otherwise TLE.
Asked — "Trie vs HashMap?"

HashMap: exact match, O(L) to hash, no prefix support. Trie: prefix queries, sorted iteration for free, shared prefixes save space — but pointer-heavy and cache-unfriendly when the words share little.

18Heaps & priority queues

A heap answers one question fast: "what is the smallest (or largest) right now?" — while items keep arriving. It is a partial order: cheaper than sorting when you only ever need the top.

Core concept

A binary heap is a complete binary tree stored in an array; every parent ≤ its children (min-heap). peek O(1), offer / poll O(log n), build from n items O(n), remove(obj) / contains O(n). Java's PriorityQueue is a min-heap by default.

Under the hood — array layout

Node at index i: children at 2i+1 and 2i+2, parent at (i−1)/2. Insert = append then sift up; poll = move last to root then sift down. Iterating a PriorityQueue does not give sorted order — only repeated poll() does.

PriorityQueue<Integer> min = new PriorityQueue<>();
PriorityQueue<Integer> max = new PriorityQueue<>(Comparator.reverseOrder());

// K LARGEST -> MIN-heap of size k (the root is the weakest of the top k)
for (int x : nums) {
    min.offer(x);
    if (min.size() > k) min.poll();
}                                   // min.peek() = k-th largest, O(n log k)

// MEDIAN OF A STREAM - two heaps
PriorityQueue<Integer> lo = new PriorityQueue<>(Comparator.reverseOrder());   // smaller half, max on top
PriorityQueue<Integer> hi = new PriorityQueue<>();                            // larger half, min on top
void add(int x) {
    lo.offer(x);
    hi.offer(lo.poll());                       // keeps every lo <= every hi
    if (hi.size() > lo.size()) lo.offer(hi.poll());
}
double median() { return lo.size() > hi.size() ? lo.peek() : (lo.peek() + hi.peek()) / 2.0; }

// MERGE K SORTED LISTS - heap holds one head per list
PriorityQueue<ListNode> pq = new PriorityQueue<>((a, b) -> Integer.compare(a.val, b.val));
Pattern cue
  • "Top / K-th / K closest / K most frequent" → heap of size k. K largest → min-heap; K smallest → max-heap. (Counter-intuitive — memorise it.)
  • "Merge k sorted…", "smallest range covering k lists" → heap of k fronts.
  • "Running median" → two heaps.
  • "Always process the cheapest / most urgent next" → scheduling, Dijkstra, Prim, Huffman.
Common pitfall
  • Using a max-heap of everything for "k largest": O(n log n) and O(n) space instead of O(n log k) / O(k).
  • (a, b) -> b - a overflow. Use Integer.compare(b, a).
  • pq.remove(x) is O(n). For sliding-window problems use lazy deletion (count what to skip, discard when it surfaces) or a TreeMap.
  • Mutating an element that is inside the heap.
Asked — "Why is building a heap O(n)?"

Heapify sifts down from the last parent to the root. Half the nodes are leaves (0 work), a quarter move ≤ 1 level, an eighth ≤ 2… Σ n·h/2h+1 converges to O(n). n separate inserts would be O(n log n).

19Matrix & grid

A grid is a graph you do not have to build: each cell is a node, and its 4 (or 8) neighbours are its edges. The rest is index discipline.

Core concept

grid[r][c] — row first, then column. rows = grid.length, cols = grid[0].length. Flood fill (DFS/BFS) is O(rows × cols) because each cell is visited once. Cell ↔ id: id = r * cols + c.

static final int[][] DIRS = {{1,0},{-1,0},{0,1},{0,-1}};

// DFS flood fill - Number of Islands
void sink(char[][] g, int r, int c) {
    if (r < 0 || c < 0 || r == g.length || c == g[0].length || g[r][c] != '1') return;
    g[r][c] = '0';                                 // mark visited by overwriting
    for (int[] d : DIRS) sink(g, r + d[0], c + d[1]);
}

// MULTI-SOURCE BFS - Rotting Oranges: every source starts in the queue at time 0
Deque<int[]> q = new ArrayDeque<>();
// enqueue ALL rotten cells, count fresh
int minutes = 0;

    for (int k = q.size(); k > 0; k--) {

            int nr = cur[0] + d[0], nc = cur[1] + d[1];
            if (nr < 0 || nc < 0 || nr == R || nc == C || g[nr][nc] != 1) continue;
            g[nr][nc] = 2; fresh--;                // mark WHEN ENQUEUED, not when polled

20Backtracking

Backtracking is DFS over a tree of decisions: make a choice, explore everything that follows from it, then undo the choice and try the next one. It is brute force, organised — and pruned.

Core concept — choose, explore, un-choose

Define three things and the code writes itself: the state (partial answer so far), the choices available from here, and the goal (when to record). Complexity is the size of the decision tree: subsets O(2n·n), permutations O(n!·n).

// THE TEMPLATE
void bt(int start, List<Integer> path) {
    if (goal(path)) { res.add(new ArrayList<>(path)); return; }    // COPY the path
    for (int i = start; i < n; i++) {
        if (!valid(i)) continue;        // prune
        path.add(nums[i]);               // choose
        bt(i + 1, path);                 // explore
        path.remove(path.size() - 1);    // un-choose
    }
}

Common pitfall
  • res.add(path) without copying — every entry ends up being the same (empty) list.
  • Forgetting the un-choose step, including un-marking a grid cell in Word Search.
  • Permutations with bt(i + 1) or combinations with a loop from 0 — mixing the two families gives duplicates or misses answers.
  • Duplicate skipping with i > 0 instead of i > start removes valid answers.
  • No pruning: sort Combination Sum candidates and break as soon as one exceeds the remainder.
Asked — "Backtracking vs DFS vs DP?"

DFS visits nodes of an existing graph. Backtracking is DFS on an implicit tree of choices with undo. DP applies when sub-states repeat and you need a number, not the list of solutions.

Anything with "things" and "connections" is a graph: courses and prerequisites, cities and roads, words one letter apart. The hard part is recognising it; after that you pick one of about six algorithms.

Core concept

Adjacency list is the default representation: O(V + E) space, neighbours in O(degree). BFS and DFS are both O(V + E). Directed vs undirected, weighted vs unweighted, cyclic vs DAG — those three questions select the algorithm.

22Dynamic programming

DP is recursion that refuses to solve the same subproblem twice. If you can write the brute-force recursion, you are 80% done — the rest is caching.

Core concept

DP applies when a problem has overlapping subproblems (the same call repeats) and optimal substructure (the best answer is built from best answers of smaller inputs). Time = number of states × work per state.

  • Top-down (memoization) — recursion + cache. Easiest to write; only visits reachable states.
  • Bottom-up (tabulation) — fill an array in dependency order. No recursion limit; allows space optimisation.
Do this — the 5-step recipe
  1. State: what do the parameters of the recursion mean? Say it as a sentence: "dp[i] = best answer using the first i items".
  2. Transition: what choices exist at this state? dp[i] = best over choices of (cost + dp[smaller]).
  3. Base case: the smallest states, answered directly.
  4. Order: fill so that everything a state needs is already computed.
  5. Answer: which cell? (dp[n]? max over all cells?) Then optimise space if only the last row/two values are used.
// 1-D: House Robber - take or skip
int prev2 = 0, prev1 = 0;
for (int x : nums) { int cur = Math.max(prev1, prev2 + x); prev2 = prev1; prev1 = cur; }

23Greedy

Greedy makes the choice that looks best right now and never reconsiders. When it is correct it is the simplest and fastest solution there is. When it is not, it is confidently wrong — so you must be able to argue why it works.

Core concept

Greedy is valid when the problem has the greedy-choice property: some locally optimal choice is always part of a globally optimal solution. The usual proof is an exchange argument: take any optimal solution, swap its first choice for the greedy one, show it does not get worse. Typical shape: sort by the right key, then one pass — O(n log n).

// Jump Game - furthest index reachable so far
int reach = 0;
for (int i = 0; i < n; i++) {
    if (i > reach) return false;
    reach = Math.max(reach, i + nums[i]);
}

// Jump Game II - implicit BFS levels
int jumps = 0, end = 0, far = 0;
for (int i = 0; i < n - 1; i++) {
    far = Math.max(far, i + nums[i]);
    if (i == end) { jumps++; end = far; }      // finished this level - must jump
}

// Gas Station - if the tank goes negative, no station in [start..i] can be the start
int total = 0, tank = 0, start = 0;
for (int i = 0; i < n; i++) {
    int d = gas[i] - cost[i];
    total += d; tank += d;
    if (tank < 0) { start = i + 1; tank = 0; }
}
return total < 0 ? -1 : start;
Pattern cue
  • "Maximum number of non-overlapping…" → sort by end, take the earliest finisher.
  • "Minimum number of platforms / rooms / arrows".
  • "Can you reach / finish", jump games, gas station → track a running frontier.
  • Pair the smallest with the smallest (Assign Cookies), biggest with smallest (Boats to Save People).
  • "Always pick the largest available" → greedy + heap.
  • Test before trusting: invent a tiny counter-example. If you find one in two minutes, it is DP.
Common pitfall
  • Sorting by the wrong key: interval scheduling by start time or by length both fail; by end time works.
  • Coin change with arbitrary denominations, 0/1 knapsack — greedy fails; fractional knapsack — greedy works.
  • Candy / ratings problems need two passes (left→right then right→left), not one.
  • No proof, no counter-example search — "it passed the sample" is not an argument.
Asked — "How do you know greedy is correct here?"

"Exchange argument: suppose an optimal solution picks a meeting that ends later than my choice. Swapping in the earlier-ending one leaves at least as much room for the rest, so the solution is still valid and no smaller. By induction greedy is optimal."

24Intervals

An interval problem is a sorting problem in disguise. Sort, then sweep once comparing each interval with the last one you kept.

Core concept

Two intervals [a, b] and [c, d] overlap iff a ≤ d and c ≤ b (use < if touching endpoints do not count). Their intersection is [max(a,c), min(b,d)], their union [min(a,c), max(b,d)]. After sorting by start, an interval can only overlap the most recent merged one — that is why one pass suffices.

// MERGE - sort by start
Arrays.sort(iv, (x, y) -> Integer.compare(x[0], y[0]));
List<int[]> out = new ArrayList<>();
for (int[] cur : iv) {
    if (out.isEmpty() || out.get(out.size() - 1)[1] < cur[0]) out.add(cur);
    else out.get(out.size() - 1)[1] = Math.max(out.get(out.size() - 1)[1], cur[1]);   // MAX, not cur[1]
}

// MAX NON-OVERLAPPING (= min removals) - sort by END
Arrays.sort(iv, (x, y) -> Integer.compare(x[1], y[1]));
int kept = 0; long lastEnd = Long.MIN_VALUE;
for (int[] cur : iv) if (cur[0] >= lastEnd) { kept++; lastEnd = cur[1]; }
// removals = n - kept

// MIN ROOMS - sweep line over separate start and end arrays
Arrays.sort(starts); Arrays.sort(ends);
int rooms = 0, best = 0;
for (int s = 0, e = 0; s < n; ) {
    if (starts[s] < ends[e]) { rooms++; s++; best = Math.max(best, rooms); }
    else { rooms--; e++; }
}
Pattern cue
  • Merge / insert / union → sort by start.
  • Keep the most, remove the fewest, fewest arrows → sort by end.
  • "How many at the same time" (rooms, platforms, max concurrent) → sweep line: +1 at start, −1 at end; or min-heap of end times.
  • Two already-sorted lists (Interval List Intersections) → two pointers; advance the one that ends first.
  • Insert into a sorted list → three phases: entirely before, overlapping (absorb), entirely after. O(n), no sort.
Common pitfall
  • Merging with last[1] = cur[1] — a contained interval [1,10],[2,3] shrinks the result. Use max.
  • Does [1,2],[2,3] overlap? Depends on the problem (meetings: no; merge intervals: yes). Read it twice and pick < vs ≤.
  • Sweep line ties: process ends before starts at the same time if back-to-back is allowed.
  • Comparator subtraction overflow with coordinates near ±231 (Minimum Arrows has exactly this test).
Asked — "Why sort by end for max non-overlapping?"

The interval that finishes first leaves the most room for everything after it. Exchange argument: any optimal set can swap its first interval for the earliest-ending one without creating a conflict.

26Advanced string algorithms

Naive pattern search is O(n·m) because after a mismatch it throws away everything it learned. KMP, rolling hash and Z-algorithm each keep that knowledge and reach O(n + m).

Core concept — KMP and the LPS array

lps[i] = length of the longest proper prefix of p[0..i] that is also a suffix of it. On a mismatch after matching j characters, the text pointer never moves back: just set j = lps[j-1] — those characters are already known to match.

int[] buildLps(String p) {
    int[] lps = new int[p.length()];
    for (int i = 1, len = 0; i < p.length(); ) {
        if (p.charAt(i) == p.charAt(len)) lps[i++] = ++len;
        else if (len > 0) len = lps[len - 1];          // fall back - do NOT advance i
        else lps[i++] = 0;
    }
    return lps;
}

int kmp(String t, String p) {
    if (p.isEmpty()) return 0;
    int[] lps = buildLps(p);
    for (int i = 0, j = 0; i < t.length(); ) {
        if (t.charAt(i) == p.charAt(j)) {
            i++; j++;
            if (j == p.length()) return i - j;          // (for all matches: record, then j = lps[j-1])
        } else if (j > 0) j = lps[j - 1];
        else i++;
    }
    return -1;
}

Asked — "Why is KMP O(n + m)?"

The text index never decreases. j increases at most n times in total, and every fallback strictly decreases it, so there are at most n fallbacks. Amortized linear — the same argument as the sliding window.

27Math & number theory

A small toolkit — gcd, primes, modular arithmetic, fast power, a little combinatorics — that turns "simulate it" into "compute it".

Core concept
  • GCD by Euclid: gcd(a, b) = gcd(b, a % b), O(log min(a,b)). lcm = a / gcd * b (divide first).
  • Primality: trial division only up to √n. Many queries → Sieve of Eratosthenes, O(n log log n).
  • Modular arithmetic: (a+b)%m, (a·b)%m distribute; subtraction needs +m; division needs a modular inverse: am−2 mod m when m is prime (Fermat).
  • Fast exponentiation: O(log n) by squaring.
long gcd(long a, long b) { return b == 0 ? a : gcd(b, a % b); }

boolean isPrime(int n) {
    if (n < 2) return false;
    for (long i = 2; i * i <= n; i++) if (n % i == 0) return false;
    return true;
}

boolean[] composite = new boolean[n + 1];               // sieve
for (int i = 2; (long) i * i <= n; i++)
    if (!composite[i])
        for (int j = i * i; j <= n; j += i) composite[j] = true;   // start at i*i

    long r = 1; b %= m;
    while (e > 0) {
        if ((e & 1) == 1) r = r * b % m;
        b = b * b % m;
        e >>= 1;
    }
    return r;
}

Any multiple of i smaller than i² is i·k with k < i, so it has a smaller factor and was already crossed out in that factor's round. Same reason the outer loop stops at √n.

HashMap traps interviewers watch for
  • map.get(x) == map.get(y) on Integer values — reference comparison; works below 128, fails above. Use .equals or intValue().
  • int[] / any array as a key: arrays use identity hashCode, so {1,2} and {1,2} are different keys. Use List.of(1,2), a record, or encode as a string/long (r * cols + c for grid cells).
  • Mutating a key after insertion — it is now in the wrong bucket and unreachable.
  • Removing from a map while iterating its keySet() / entrySet() — ConcurrentModificationException. Use iterator.remove(), removeIf, or collect keys first.
  • Reading map.get(k) and unboxing to int when the key is missing — NullPointerException. getOrDefault.
  • Prefix-sum overflow: the running sum of an int[] can exceed int; keep it in a long and key the map by Long.

LinkedHashMap — hash speed with an order

Same O(1) as HashMap plus a doubly linked list threading the entries. With accessOrder = true every get/put moves the entry to the tail, so the head is always the least recently used — the whole LRU cache is one override.

class LRUCache extends LinkedHashMap<Integer,Integer> {
    private final int cap;
    LRUCache(int cap) { super(cap, 0.75f, true); this.cap = cap; }    // true = access order
    public int get(int k)         { return getOrDefault(k, -1); }
    public void put(int k, int v) { super.put(k, v); }
    @Override protected boolean removeEldestEntry(Map.Entry<Integer,Integer> e) { return size() > cap; }
}
// First unique character: LinkedHashMap<Character,Integer> counts -> first entry with value 1 is the answer.
Asked — "Now do LRU without LinkedHashMap"

That is what they usually want next. HashMap<K, Node> + a hand-written doubly linked list with dummy head/tail. get: look up, unlink, add to tail. put: if present update and move; else create, add to tail, and if size > cap unlink head.next and remove it from the map. TreeMap & TreeSet — sorted, with "nearest" queries

A red-black tree. Slower than a hash map (O(log n) and pointer-chasing) but it can answer questions a hash map cannot: what is the smallest key ≥ x? the largest ≤ x? everything in [lo, hi]? Reach for it when the problem keeps a sorted collection while inserting — sorting once then binary-searching does not work if elements keep arriving.

TreeMap traps
  • TreeSet dedups by comparator, not equals. Comparator.comparingInt(a -> a[0]) silently drops a second element with the same a[0]. Add a tiebreak (index) to the comparator.
  • floorKey returns null; unboxing it into int throws. Always null-check.
  • Choosing TreeMap when only counting is needed — you pay log n for order you never use. Ask "do I ever call floor/ceiling/first/last?" If not, HashMap.
  • Choosing TreeMap when only the min (or only the max) is needed — that is a PriorityQueue. TreeMap earns its keep when you need both ends or arbitrary removal.

PriorityQueue — "the smallest right now, while things keep arriving"

A binary heap in an array. You get peek O(1), offer/poll O(log n), and nothing else cheap: no index access, no sorted iteration, remove(obj) and contains are O(n). Use it when the problem repeatedly asks for the current extreme — k-th, top-K, merge-k, scheduling, Dijkstra.

Heap vs the alternatives — say this out loud
  • Heap vs sort: sort is O(n log n) and needs everything up front; a size-k heap is O(n log k) and works on a stream. If k ≈ n, just sort.
  • Heap vs quickselect: quickselect finds the k-th in O(n) average but is in-place, offline and worst-case O(n²). Mention it, then write the heap.
  • Heap vs TreeMap: need arbitrary removal or both min and max? TreeMap. Otherwise heap — smaller constant, less memory.
  • Heap vs bucket sort: when the sort key is a bounded count (frequencies ≤ n) buckets give O(n).

ArrayDeque — your stack, your queue, your deque

A resizable circular array. O(1) amortised at both ends, no boxing overhead of a linked list's nodes, no synchronized tax of the legacy Stack. One class, three roles — the role is defined by which methods you call.

int done = 0;

Deque traps
  • ArrayDeque rejects null — offer(null) throws. LinkedList allows it, which is the only reason to ever pick LinkedList as a queue.
  • peek() / poll() return null on empty; pop() / remove() / element() throw. Mixing them up is how "it works on the sample" fails.
  • Iterating an ArrayDeque used as a stack goes top → bottom (head first) — the reverse of java.util.Stack.
  • BFS: marking visited at dequeue time lets the same cell be enqueued many times — correct but blows up to O(V²) on grids.
  • Monotonic stack with < vs <= decides how duplicates are handled — work it out on [2,2,3] before coding.

Subarray Sum Equals K
public int subarraySum(int[] a, int k) {
    Map<Integer,Integer> seen = new HashMap<>();
    seen.put(0, 1);                                // the empty prefix
    int sum = 0, cnt = 0;
    for (int x : a) {
        sum += x;
        cnt += seen.getOrDefault(sum - k, 0);       // every earlier prefix equal to sum-k closes a subarray here
        seen.merge(sum, 1, Integer::sum);
    }
    return cnt;
}

public int longestConsecutive(int[] nums) {
    Set<Integer> s = new HashSet<>();
    for (int x : nums) s.add(x);
    int best = 0;
    for (int x : s) {
        if (s.contains(x - 1)) continue;           // not the start of a run - skip, someone else counts it

LRU Cache (hand-written)
class LRUCache {
    class Node { int k, v; Node prev, next; Node(int k, int v) { this.k = k; this.v = v; } }
    private final int cap; private final Map<Integer,Node> map = new HashMap<>();
    private final Node head = new Node(0,0), tail = new Node(0,0);   // dummies: head.next = LRU, tail.prev = MRU
    LRUCache(int cap) { this.cap = cap; head.next = tail; tail.prev = head; }
    private void unlink(Node n) { n.prev.next = n.next; n.next.prev = n.prev; }
    private void addLast(Node n) { n.prev = tail.prev; n.next = tail; tail.prev.next = n; tail.prev = n; }
    public int get(int k) {
        Node n = map.get(k); if (n == null) return -1;
        unlink(n); addLast(n); return n.v;
    }
    public void put(int k, int v) {
        Node n = map.get(k);
        if (n != null) { n.v = v; unlink(n); addLast(n); return; }
        if (map.size() == cap) { Node lru = head.next; unlink(lru); map.remove(lru.k); }
        n = new Node(k, v); map.put(k, n); addLast(n);
    }
}

public int[] findOrder(int n, int[][] pre) {
    List<List<Integer>> adj = new ArrayList<>(); int[] indeg = new int[n];
    for (int i = 0; i < n; i++) adj.add(new ArrayList<>());
    for (int[] p : pre) { adj.get(p[1]).add(p[0]); indeg[p[0]]++; }     // p[1] -> p[0]
    Deque<Integer> q = new ArrayDeque<>();
    for (int i = 0; i < n; i++) if (indeg[i] == 0) q.offer(i);
    int[] order = new int[n]; int idx = 0;
    while (!q.isEmpty()) {
        int u = q.poll(); order[idx++] = u;
        for (int v : adj.get(u)) if (--indeg[v] == 0) q.offer(v);
    }
    return idx == n ? order : new int[0];        // idx < n means a cycle
}

class MedianFinder {
    private final PriorityQueue<Integer> lo = new PriorityQueue<>(Collections.reverseOrder()); // smaller half, max on top
    private final PriorityQueue<Integer> hi = new PriorityQueue<>();                          // larger half, min on top
    public void addNum(int x) {
        lo.offer(x);
        hi.offer(lo.poll());                              // guarantee max(lo) <= min(hi)
        if (hi.size() > lo.size()) lo.offer(hi.poll());  // lo keeps the extra element
    }

        return lo.size() > hi.size() ? lo.peek() : (lo.peek() + hi.peek()) / 2.0;

Network Delay Time (Dijkstra)
public int networkDelayTime(int[][] times, int n, int k) {
    List<List<int[]>> adj = new ArrayList<>();
    for (int i = 0; i <= n; i++) adj.add(new ArrayList<>());
    for (int[] t : times) adj.get(t[0]).add(new int[]{t[1], t[2]});   // {to, weight}
    int[] dist = new int[n + 1]; Arrays.fill(dist, Integer.MAX_VALUE); dist[k] = 0;
    PriorityQueue<int[]> pq = new PriorityQueue<>((a, b) -> Integer.compare(a[0], b[0]));  // {dist, node}
    pq.offer(new int[]{0, k});
    while (!pq.isEmpty()) {
        int[] cur = pq.poll(); int d = cur[0], u = cur[1];
        if (d > dist[u]) continue;                                  // stale entry
        for (int[] e : adj.get(u)) {
            int nd = d + e[1];
            if (nd < dist[e[0]]) { dist[e[0]] = nd; pq.offer(new int[]{nd, e[0]}); }
        }
    }
    int best = 0;
    for (int i = 1; i <= n; i++) { if (dist[i] == Integer.MAX_VALUE) return -1; best = Math.max(best, dist[i]); }
    return best;
}

Interview questions on this topic

Why HashMap here and not TreeMap? every round

Because the problem never asks for order or a nearest key — only "have I seen it / how many". HashMap gives O(1) average; TreeMap would pay O(log n) per operation for sorting nobody reads. The moment the problem says "smallest ≥", "range", "in sorted order while inserting", flip to TreeMap.

Why ArrayDeque instead of Stack or LinkedList? every round

Stack extends Vector: every method is synchronized, and it exposes index-based access that breaks the LIFO abstraction. LinkedList allocates a node per element and chases pointers. ArrayDeque is a circular array — contiguous, cache-friendly, O(1) amortised at both ends, and it is what the Javadoc itself recommends. The one thing it cannot do is hold null.

K-th largest with a heap: why a MIN-heap? every round

Keep the k largest seen so far; the smallest of those — the root of a min-heap — is exactly the k-th largest. When a new element beats the root, it replaces it. A max-heap of everything would find the answer too, but with O(n) memory and O(n log n) time instead of O(k) and O(n log k).

Why can't you index into or iterate a PriorityQueue in order? common

It is a heap, not a sorted list: the array satisfies only parent ≤ child, so siblings are in no particular order. Sorted output exists only through repeated poll(). Need random access to sorted data? That is a TreeMap/TreeSet (log n) or a sorted ArrayList (binary search but O(n) insert).

How do two heaps maintain a running median? common

A max-heap holds the smaller half, a min-heap the larger half, sizes differing by at most one. Every insert goes into the max-heap, its top moves to the min-heap (keeping every lo ≤ every hi), then rebalance if the min-heap grew bigger. The median is the top of the larger heap, or the average of the two tops. O(log n) insert, O(1) query.

Why does an int[] not work as a HashMap key, and what do you use instead? common

Arrays inherit Object.hashCode/equals — identity, not content — so two equal arrays land in different buckets. Options: encode to a primitive (r * cols + c for grid cells, or a long packing two ints), use List.of(a, b) (value-based), a record Point(int r, int c), or a String key (slowest).

How would you implement an LRU cache in Java, and what is the O(1) trick? every round

Shortest: LinkedHashMap with accessOrder = true and removeEldestEntry returning size() > capacity. By hand: a HashMap<K, Node> for O(1) lookup plus a doubly linked list for O(1) move-to-front and evict-from-back. A singly linked list would make unlinking O(n); an ArrayList would make moving O(n). The map finds the node, the list reorders it — each does the thing the other cannot.

HashMap says O(1) — when is it not, and what did Java 8 do about it? common

A bad hashCode (or a hash-flooding attack) sends every key to one bucket, making lookups O(n). Since Java 8 a bucket that grows past 8 entries (and the table is ≥ 64) becomes a red-black tree, so the worst case is O(log n). For interview code the practical rule: keys must have a sane hashCode and be immutable.

TreeSet dropped one of my elements — why? common

TreeSet/TreeMap decide equality by the comparator returning 0, not by equals. A comparator on a single field (comparingInt(a -> a[0])) treats two arrays with the same first element as the same key, so the second is silently rejected (or overwrites the value). Add a tiebreak, usually the index, so no two distinct items compare equal.

When is a monotonic stack the right tool, and how do you know it is O(n)? common

Whenever the question is "for each element, the nearest element to the left/right that is greater/smaller" — next greater, previous smaller, span, histogram, remove-k-digits. Each index is pushed exactly once and popped at most once, so the total work across the whole loop is O(n) even though the inner while looks nested.

BFS gives shortest path on an unweighted graph — why does it fail on weighted, and what replaces it? common

BFS assumes every edge costs 1, so the first time it reaches a node is via the fewest edges — not the least weight. Dijkstra replaces the FIFO queue with a PriorityQueue ordered by distance so the cheapest frontier node is expanded first; Java has no decrease-key, so push duplicates and skip stale entries whose distance is worse than the recorded one. Negative weights break Dijkstra too — that is Bellman-Ford.

What does computeIfAbsent buy you over containsKey + put? senior

One hash lookup instead of two, no null check, and the grouping idiom becomes one line: map.computeIfAbsent(k, x -> new ArrayList<>()).add(v). Traps: the mapping function must not modify the same map (throws ConcurrentModificationException since Java 9), and returning null from it stores nothing.

PriorityQueue.remove(obj) is O(n) — how do you delete from a heap in a sliding window? senior

Lazy deletion: keep a HashMap<value, pendingRemovals>; when an element leaves the window, increment its count instead of touching the heap; whenever you peek, first poll away any top whose pending count is positive. Or switch to TreeMap<value, count>, which has real O(log n) removal and gives both min and max.

Top K frequent: heap is O(n log k). Can you do O(n)? senior

Bucket sort on frequency: frequencies are at most n, so create List<Integer>[] bucket = new List[n + 1], put each key at bucket[freq], then walk from index n down collecting until you have k. O(n) time and space. Mention quickselect on the (key, freq) pairs as the third option.

Why seed the prefix-sum map with {0 : 1}? common

It represents the empty prefix before index 0. Without it, a subarray that starts at index 0 and sums to k is never counted, because there is no earlier prefix equal to sum − k = 0. Same idea in "contiguous array" (put 0→−1 for the index variant) and "subarrays divisible by K" (count[0] = 1).

You have 10 million integers and need the 100 largest. Sort, heap or quickselect? senior

Min-heap of size 100: one pass, O(n log 100) ≈ 7n comparisons, 100 ints of memory, and it works on a stream you cannot hold in memory. Quickselect is O(n) average but needs the whole array in memory and is not stable under adversarial input. Sorting is O(n log n) and pointless for 100 out of 10 million.

28Question bank

Theory questions that come up around the coding round. Cover the answer, say it out loud, then open it.

What is Big-O, and how is it different from Ω and Θ?

Big-O is an upper bound on growth, Ω a lower bound, Θ a tight bound (both). In interviews "Big-O" almost always means Θ of the worst case. Drop constants and lower-order terms.

What is amortized complexity?

The average cost per operation over a worst-case sequence. ArrayList.add is O(n) on a resize, but doubling makes n appends cost O(n) in total → O(1) amortized. Same reasoning for the monotonic stack and the sliding window's inner while loop. It is not the same as average-case (no probability involved).

Array vs linked list?

Array: O(1) index, cache friendly, O(n) insert/delete in the middle. Linked list: O(1) insert/delete at a known node, O(n) access, extra pointer memory, poor locality. In Java, ArrayList/ArrayDeque beat LinkedList almost always.

How does a HashMap work, and what is its worst case?

hashCode → spread → bucket index; collisions chained in a list, treeified into a red-black tree past 8 entries; resize ×2 at load factor 0.75. Average O(1); worst case O(log n) per bucket in Java 8+ (O(n) before). Keys need consistent equals/hashCode and should be immutable.

BFS vs DFS — when do you pick which?

BFS: shortest path in an unweighted graph, level-order, "minimum steps". Memory = widest level. DFS: cycle detection, topological sort, connectivity, all paths / backtracking. Memory = deepest path. Both O(V + E).

BFS vs Dijkstra vs Bellman–Ford vs Floyd–Warshall?
  • BFS — unweighted, O(V+E).
  • Dijkstra — non-negative weights, O(E log V).
  • Bellman–Ford — negative weights, detects negative cycles, O(VE); natural for "at most K edges".
  • Floyd–Warshall — all pairs, O(V³).
Why does Dijkstra fail with negative edges?

It finalises a node when it is popped, assuming no later path can be shorter. A negative edge discovered afterwards could make it shorter, but the node is never revisited.

How do you detect a cycle in a directed vs an undirected graph?

Directed: DFS with three colours (white / grey = on the current path / black = done) — an edge to a grey node is a back edge; or Kahn's algorithm leaves nodes unprocessed. Undirected: Union-Find (an edge whose ends are already connected), or DFS where you reach a visited node that is not your parent.

What is topological sort and when does it not exist?

A linear order of a directed graph's nodes where every edge goes forward. Exists iff the graph is a DAG. Kahn: repeatedly remove in-degree-0 nodes. DFS: reverse post-order.

Explain Union-Find and its complexity.

Forest of parent pointers. find follows to the root with path compression; union links roots by rank/size. Together: O(α(n)) amortized — effectively constant. Uses: components, cycle detection in undirected graphs, Kruskal, "accounts merge".

What two properties does a problem need for DP?

Overlapping subproblems and optimal substructure. Without overlap it is plain divide & conquer (merge sort); without optimal substructure, combining sub-answers does not give the answer (longest simple path).

Memoization vs tabulation?

Memoization: top-down recursion + cache, computes only reachable states, risks stack overflow. Tabulation: bottom-up loops, needs an explicit fill order, allows rolling-array space optimisation. Same time complexity.

0/1 knapsack vs unbounded knapsack — what changes in the code?

With a 1-D array: 0/1 iterates capacity backward (so each item is used once — reads come from the previous item's row); unbounded iterates forward (the item can be reused — reads come from the current row).

When does greedy work, and how do you prove it?

When a locally optimal choice is always part of some global optimum (greedy-choice property) plus optimal substructure. Proof: exchange argument or "greedy stays ahead". Counter-example for coin change: {1,3,4}, amount 6.

Greedy vs DP vs backtracking?

Greedy: one choice per step, never undone. DP: tries all choices per state but caches states — for counts/optima. Backtracking: enumerates all solutions with undo — for "list all".

What is a monotonic stack and why is it O(n)?

A stack kept sorted by popping violators before each push. When x pops y, x is y's next greater (or smaller) element. Each index is pushed once and popped at most once → O(n) total.

What does "binary search on the answer" mean?

When the answer is a number in a range and feasible(x) is monotonic (false…false true…true), binary search x and test feasibility with a greedy O(n) check. Total O(n log range). Koko, ship capacity, split array.

Sliding window vs prefix sum + map?

Window needs monotonicity: adding elements can only move the measure one way (all positives, distinct counts). With negative numbers use prefix sums + hash map.

Min-heap or max-heap for the K largest elements?

Min-heap of size k. The root is the smallest of the current top k — the one to evict when something larger arrives. O(n log k), O(k) space.

Why is heapify O(n) when insertion is O(log n)?

Sift-down cost is proportional to a node's height, and most nodes are near the bottom: Σ (n / 2h+1)·h = O(n).

Quick sort vs merge sort? What does Java use?

Quick: in place, not stable, O(n²) worst. Merge: stable, O(n) space, guaranteed n log n, good for linked lists. Java: dual-pivot quicksort for primitives, TimSort for objects.

What is a stable sort and when does it matter?

Equal keys keep their original relative order. Matters for multi-key sorting (sort by secondary key, then stable-sort by primary) and whenever records carry more than the key.

Explain Floyd's cycle detection.

Slow moves 1, fast moves 2; if there is a cycle they meet inside it. Reset one pointer to the head, move both by 1 — they meet at the cycle start (because a = kc − b). O(n) time, O(1) space.

BST vs hash table?

Hash: O(1) average, no order. Balanced BST: O(log n) but supports sorted iteration, min/max, floor/ceiling, range queries. HashMap vs TreeMap.

Trie vs hash set for a dictionary?

Hash set: exact lookup only. Trie: prefix queries, autocomplete, wildcard search, lexicographic traversal, shared-prefix pruning in grid search.

What is Kadane's algorithm?

cur = max(x, cur + x); best = max(best, cur). "Best subarray ending here" either extends the previous one or starts fresh. O(n), O(1).

How do you convert recursion to iteration?

Use an explicit stack holding what the call frame held (node + state). Tail recursion becomes a loop. DP recursion becomes a table filled in dependency order.

How do you approach a problem you have never seen?
  1. Restate it; ask about constraints, duplicates, negatives, empty input.
  2. Work a small example by hand.
  3. State the brute force and its complexity.
  4. Find the repeated work → pick the pattern (constraints hint at the target complexity).
  5. Explain the plan before coding.
  6. Code, then dry-run with an edge case.
  7. State time and space.

void bfs(int src, List<List<Integer>> adj) {
    boolean[] seen = new boolean[adj.size()];
    int[] dist = new int[adj.size()];
    Deque<Integer> q = new ArrayDeque<>();
    q.offer(src); seen[src] = true;
    while (!q.isEmpty()) {
        int u = q.poll();
        for (int v : adj.get(u)) {
            if (seen[v]) continue;
            seen[v] = true;               // mark on enqueue
            dist[v] = dist[u] + 1;
            q.offer(v);
        }
    }
}

// directed cycle detection: 0 = unvisited, 1 = in current path, 2 = done
boolean hasCycle(int u, List<List<Integer>> adj, int[] color) {
    color[u] = 1;
    for (int v : adj.get(u)) {
        if (color[v] == 1) return true;                       // back edge
        if (color[v] == 0 && hasCycle(v, adj, color)) return true;
    }
    color[u] = 2;
    return false;
}

LRU cache

class LRUCache {
    private static class Node { int k, v; Node prev, next; Node(int k, int v) { this.k = k; this.v = v; } }
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0), tail = new Node(0, 0);   // dummies: head.next = most recent
    private final int cap;

    LRUCache(int cap) { this.cap = cap; head.next = tail; tail.prev = head; }

    private void unlink(Node n) { n.prev.next = n.next; n.next.prev = n.prev; }
    private void addFront(Node n) { n.next = head.next; n.prev = head; head.next.prev = n; head.next = n; }

    public int get(int key) {
        Node n = map.get(key);
        if (n == null) return -1;
        unlink(n); addFront(n);
        return n.v;
    }
    public void put(int key, int value) {
        Node n = map.get(key);
        if (n != null) { n.v = value; unlink(n); addFront(n); return; }
        if (map.size() == cap) { Node lru = tail.prev; unlink(lru); map.remove(lru.k); }   // node stores its key for this
        n = new Node(key, value); map.put(key, n); addFront(n);
    }
}
